# 通用混合数字孪生与安全优化：总体方案及开发计划

- 状态：讨论稿 / Architecture Plan（不是已实现功能承诺）
- 日期：2026-09-24
- 目标读者：AgentWorkShop、PLC 模拟器、AML、CAE/工艺建模开发者，以及工艺/设备负责人
- 首选试点：BOPET 双拉薄膜线；CAE 子模型试点：斜拉双轴薄膜设备
- 安全定位：决策支持与受治理的监督控制；不替代 PLC 内的硬实时控制、安全联锁、急停或操作规程

## 1. 执行摘要

目标是让 AgentTeam 面对一条产线时，可以在有证据、有边界的情况下：

1. 读取设备、工艺、配方、DAQ/DCW 节点和历史批次，形成可审查的场景规格；
2. 选择一个已有、经过版本管理的物理模型 / FEM 模型 / 数据残差模型组合；
3. 从真实现场快照初始化虚拟工况，在不写 PLC 的隔离副本里试算候选设定；
4. 用经过验证的模型和受约束的贝叶斯优化提出少量候选，预测质量、守卫量和不确定度；
5. 只有候选落在已验证适用域和安全信任域时，才进入现有 DCW 联锁、HITL/权限、回读和写入节拍；
6. 读取实际 DAQ 结果，与预测对账；保留原始证据，并在校准门禁通过后产生新版本模型；
7. 逐步提升模型质量，不以“模型已经完美”为前提，也不把模型预测当成 PLC 安全证明。

**可行性结论：技术上可行，并且当前项目已经具备相当多的底座；尚未具备的是通用场景契约、从现场状态初始化 FEM、可追溯的物理参数校准、模型不确定度 / OOD 门禁、Twin-in-the-loop Safe BO，以及这些环节与实际写入间的服务端策略闸门。**

“任意场景自动建立完美模型”不现实，也不应作为工程承诺。合理的终态是：**Agent 辅助建模 + 领域模板 / 参数化方程 + 历史数据校准 + FEM 等高保真模型 + 置信度和适用域声明 + 安全优化 + 持续验证**，得到一个在明确产线、产品、配方、工况和误差范围内可作为参考的混合数字孪生。

一句话架构：

> 物理模型负责因果结构与硬约束；DAQ 历史数据负责估计状态、校准参数和学习残差；高保真 FEM 负责必要的空间场复核；Safe BO 负责虚拟搜索；现有 DCW 网关负责唯一真实写入口；实际测量负责检验并更新模型可信度。

## 2. 讨论结论：为什么“物理 + 数据”优于单纯历史拟合，但仍不能保证完美

### 2.1 纯数据模型能做什么

AML 目前能从产线/产品/配方的数据集训练 ONNX 时序模型，并通过单步与滚动预测门禁和 candidate → shadow → production 生命周期管理。它适合做短期预测、滞后估计、质量趋势、异常特征和运行数据分布内的插值预测。

但纯数据模型可能：

- 把相关性误当成因果；
- 在没见过的控制组合、材料批次、扰动或配方外推时仍输出貌似精确的数；
- 不理解守恒关系、温度窗口、拉伸比、设备结构、相变 / 接触等物理边界；
- 因训练分布与当前工况不同，给出不可信的控制响应。

### 2.2 物理模型能做什么

物理模型能提供因果方向、单位一致性、状态演化、守恒关系、空间场、设备边界条件和可解释的反事实试验。FEM 在空间分布、几何、局部应力 / 应变、接触及材料场确实影响决策时很有价值。

但物理模型也会因结构简化、未知参数、边界条件错误、材料差异、机器老化和未建模扰动而失配。数值收敛只说明对应数学问题达到求解条件，**不说明它等于真实设备**。

### 2.3 推荐的混合形式

对场景输入 `x`、控制 `u`、状态 `s`、扰动 `d`：

```text
物理预测:       y_phys = f_phys(s, u, d; θ)
数据残差预测:   Δy      = g_data(history, s, u, recipe, phase)
混合预测:       y_hat   = y_phys + Δy
可信区间:       [y_p05, y_p50, y_p95] 或经校准的预测分布
```

对乘法、正值、角度、概率、守恒量等输出，不必硬套加性残差；需在模型契约里声明变换或结构化组合方式。物理模型的 `θ` 也只允许在可辨识、受先验范围约束、经留出批次验证的参数子集里更新。不要每收到一批数据就自动改全套方程或所有参数。

### 2.4 “best twin”应如何定义

不追求抽象的“最佳孪生模型”或跨所有工况的完美值。模型只能对**有版本、有范围、有数据证据**的适用域声明可信，例如：

```text
产线 / 设备版本 × 产品族 × 配方版本 × 工况阶段 × 控制范围 × 材料批次域
```

每个模型版本应该输出：目标量误差、预测区间覆盖率、守卫量误差、OOD / 分布漂移状态、FEM 收敛 / 网格和时间步信息、校准数据时间窗、验证数据批次、代码与参数指纹、批准状态。

### 3.2 PLC 模拟器已有物理模型

模拟器已有 cast-film、biax、injection、WWTP、anneal 多种模型；它们在控制 SP、模型状态、DAQ 输出之间建立了因果路径，并可同时导出模拟器真值 `truth` 与暴露给协议的噪声值 `exposed`。双拉 `biax-model.ts` 有明确的薄膜物料链和温度 / 缺陷方向；注塑模型有保压压力 / 时间、熔温、模温与克重 / 飞边 / 缩痕的关系。

这些是很有用的**快速 process model / virtual process twin 起点**，但仍是参数化、简化的模型。PLC 模拟器的真值不能冒充真实工厂的 ground truth；真实场景校准应使用来源可追溯、质量合格的实际 DAQ、配方、产品、批次和运行阶段数据。

### 3.3 斜拉 CAE 项目当前定位

参考项目 `D:\belendermodels\oblique-biaxial-film-stretching-equipment` 有 `SimulationEngine`、膜场 / FEM、机构运动、材料 / 取向 / 光学模块、CLI 运行与受限搜索，可作为斜拉工艺的**高保真候选评估器和模型方法参考**。

它目前不是可直接接入生产控制的 Twin API：

- 现有 `scripts/serve.mjs` 是静态文件服务器，不是物理仿真 API；
- `scripts/cae-run.mjs` / `cae-study.mjs` 是 JSON CLI，整机运行时间受限，返回 convergence、provenance、constraints 等；
- 文档将它定位为 physics-consistent CAE prototype，未完成真实机器 / 材料 / 光学的全面校准；
- Q4 membrane / 当前接触近似 / 未完成 shell-solid 和耦合摩擦等限制仍然有效；
- CLI 主要从默认状态和参数启动。将实际工况交给 FEM 前，仍需实现有审计的现场快照→模型初始状态映射，而非只把当前 SP 传入 `--params`。

因此建议通过隔离的 CAE adapter / worker service 调用，先做非生产离线与 shadow 验证；不建议把该仓库的 GUI、static server 或未经校准的 FEM 输出直接等同于生产孪生。

## 4. 产品目标与设计原则

### 4.1 产品目标

让工艺专家和 AgentTeam 能对每个已注册场景构建一个可检查、可版本化的模型包；每个调优候选先在隔离的 Twin trial 中运行；模型给出预测和不确定度；安全策略决定可否进入审批 / 写入；实际 DAQ 回馈后计算预测残差、判断漂移，并在数据和验证门禁通过后发布新模型版本。

### 4.2 设计原则

1. **不承诺完美**：承诺适用域、验证等级、误差和不确定度透明。
2. **模型分层**：快速 lumped process model、数据残差 / surrogate、必要时高保真 FEM；并非每条线都必须有 FEM。
3. **可重放 / 可审计**：一个 trial 固定输入快照、模型与参数版本、算法、随机种子、场景状态；相同版本与输入可重算。
4. **仿真和现场写隔离**：Twin trial API 永不写 PLC；只有现有 DCW gateway 能写现场。
5. **硬约束不交给模型学习**：DCW 安全上下限、联锁、HITL、急停等规则独立于模型和 Agent。
6. **模型拒答是有效结果**：UNVERIFIED、FAILED、OOD、校准过期、关键 DAQ 不新鲜、守卫不完整时拒绝推荐，不用猜值填补。
7. **模型晋升不是自动发生**：候选 → shadow → approved / production → retired 有责任人和证据。
8. **先影子、再建议、再审批控制**：auto-control 是远期能力，不是首个 MVP。
9. **数据和方程的来源都要有 provenance**：物理文献 / 设计假设 / 实验辨识 / 现场回归不能混写成一个“模型参数”。

### 4.3 非目标

- 第一阶段不让 Agent 任意生成代码并直接在线执行 FEM。
- 不把 3D 可视化称为物理仿真。
- 不让贝叶斯优化越过工艺窗口、设备硬联锁或控制器安全逻辑。
- 不试图对任意未知工艺只靠 DAQ 自动发现完整物理方程。
- 不用一个 FEM 模型替代所有没有空间场 / 几何需求的场景。

### 5.1 Twin Model Registry

模型不可只按“场景名字 + 最新代码”引用。每个模型工件需绑定：

- `sceneId`、`lineId` / 设备族、产品族和配方族；
- 控制 / 观测变量 ID、单位、缩放、数据新鲜度策略；
- phase / operating envelope 和 OOD 检查定义；
- physical model package + source hash + 参数及其来源 / 不确定度；
- residual model / estimator 的数据集 ID、manifest hash、训练代码 / weights hash；
- solver、网格、时间步、收敛 / verification 证据；
- 校准窗、按批次划分的 train / validation / test、实际残差指标；
- 可用能力：`simulate`、`calibrate`、`optimize`、`write_eligible`；
- 生命周期：`draft → validated → shadow → approved → retired`；
- owner / reviewer / 工艺负责人批准、创建时间和失效条件。

建议复用 AML model registry 生命周期和 immutable IO contract 思路，但物理 / FEM 模型和 ONNX 时序模型要有不同类型及验证规则；不能把某个 ONNX 模型晋升等同于 FEM 可信。

### 5.2 Generic Scene Contract / Twin DSL

“通用”应是**统一的契约、运行时、数据接口、治理与模型生命周期**，而不是一套万能物理方程。

Agent 可以辅助从模板、设备蓝图、手册和工程师提供的因果信息生成 `SceneDraft`，但 Draft 必须经静态校验、现场映射检查和工艺专家批准后才能发布。最少描述：

```yaml
scene:
  id: biax-pet-film-v1
  domain: film-stretching
  phases: [startup, warmup, steady, grade-change, shutdown]
  assets: [...]                 # 设备 / 子系统 / 协议节点
  controls:                     # 可写 SP，单位，边界，最大步幅，速率限制
    - key: fast-roll-speed
      dcwNodeId: ...
      unit: m/min
      physicalMeaning: MDO 拉伸速度
      safeRange: [..., ...]
      recipeWindow: ...
      maxStepPerWrite: ...
      minWriteIntervalSec: 60
  observations:                 # DAQ PV / 派生指标 / guard
    - key: thickness
      daqNodeId: ...
      unit: um
      quality: [freshness, range, missing]
      target: ...
      hardGuard: ...
  state:
    estimatedStates: [...]      # 热状态、输送滞后、批次状态等
    estimator: ...
  disturbances: [...]           # 原料、环境温度、负荷、速度变化
  topology: [...]               # 物流 / 热 / 机械 / 化学因果边
  modelProviders:
    fastPhysics: ...
    residual: ...
    highFidelity: ...           # optional FEM / CAE
  objectives: [...]             # 多目标 / 成本 / 优先级
  validationEnvelope: ...
```

数值界限须从实际 DCW / PLC / 活动配方 / 安全规程取值，并通过 UI/API 现场读回；不能让 LLM 凭模型名称编造寄存器、上下限、配方窗或 FEM 边界条件。

### 5.3 Twin Runtime / isolated trial

每次仿真必须在副本状态运行：

- 固化现场 `Snapshot`：DAQ 时间窗、DCW SET/ACT、活动配方 / 产品 / run / phase、模型状态估计及质量标签；
- clone model state，不操作 PLC、不改现场 simulator nodes、不写 recipe；
- 对每个候选记录 controls、horizon、disturbance、seed、模型版本和求解状态；
- 返回完整预测轨迹、指标分布、约束距离、模型分歧、OOD、数值收敛与 provenance；
- trial 结束可删除临时计算状态，但审计摘要和引用的不可变输入快照保留。

**当前 CAE 的大缺口之一**：CLI 能从参数 / 默认状态跑整机，但要与真实现场结合，必须设计并验证 snapshot → FEM initial state 的映射、状态初始化/历史变量恢复和过程相位语义。只把 DCW 值传进 CAE，不算现场态数字孪生。

### 5.4 Twin API 建议

第一版可在 AgentWorkShop 暴露版本化内部 API；高保真 FEM 以隔离 worker / sidecar 运行，不在 Nuxt request handler 内做长耗时同步计算。

| API / Agent tool | 作用 | 明确禁止 |
|---|---|---|
| `GET /api/workshop/twin/scenes/:id` / `twin_scene_inspect` | 场景契约、模型版本、绑定、适用域、守卫摘要 | 不修改现场 |
| `POST /api/workshop/twin/snapshots` / `twin_snapshot` | 对齐一份真实 DAQ/DCW/recipe/phase 状态 | 不推导缺失量为“正常” |
| `POST /api/workshop/twin/trials` / `twin_simulate` | 对候选控制轨迹在隔离副本中仿真 | 不能对 PLC 写入 |
| `POST /api/workshop/twin/optimizations` / `twin_optimize` | Safe BO 返回候选集、分布、可行概率和推荐依据 | 不能直接执行推荐值 |
| `GET /api/workshop/twin/trials/:id` | 读完整仿真结果 / 状态 / 日志 | 不覆盖源证据 |
| `POST /api/workshop/twin/trials/:id/actual` / `twin_compare_actual` | 关联真实试验 / DAQ / journal，计算模型误差 | 不自动修改 production 模型 |
| `POST /api/workshop/twin/models/:id/promote` | 经过门禁和审批后晋升版本 | Agent 不可绕过模型生命周期和权限 |

实际写入仍走既有 `dcw_control` → DCW gateway；未来可在**服务端写控入口**要求带 `trialId` / `recommendationId` 并核验 `write_eligible`，但这应是独立、安全评审后的版本化改动。Prompt 不是安全边界。

## 6. 模型构建和持续校准流程

### 6.1 场景建模：Agent 辅助，工程师负责签署

1. Agent 读取已映射的 DAQ/DCW/模板/设备蓝图/单位/当前配方，生成 `SceneDraft` 和证据链接。
2. 系统对拓扑完整性、单位换算、变量重名、方向 / 因果图、上下限、响应时间、可观测性、参数可辨识性做机器检查。
3. 工艺专家补充真实设备机理、材料 / 产线边界、phase 定义和可接受模型误差；unknown 明确标注。
4. Digital-twin engineer 给出模型形式、方程 / FEM / 数据模型组合、参数来源、适用域、验证计划。
5. 人工审核后进入 `draft/validated`；没有所需边界、单位、DAQ freshness 或安全窗时拒绝激活。

Agent 不能仅靠列名或少量相关性“发明”未证实的物理规律；可产出待验证假设，而非把假设发布成工艺事实。

### 6.2 现场数据整理和状态估计

采样要联合：

- DAQ 原始样本 + 时间戳 + driver / 质量位 / 报警 / missing；
- DCW 设定、PLC 回读、每次写请求 / ACK / 回读 / 来源 / hypothesis / task；
- 配方 / 产品 / 批次 / 生产线 run / 工况阶段 / 操作员动作；
- 受控的环境 / 原料 / 扰动变量和变更事件；
- Twin trial、候选、实际应用、rollback / keep 判定。

数据按单位 / 时钟对齐、相位 / recipe 分段、传感器范围和 freshness 清洗；不得把空值填成 0，不得把 PLC simulator `truth` 与真实 DAQ 混为一个训练标签。输入快照包含缺失率、延迟、校准状态和数据集 hash。

先分别估计：

1. **状态**：热惯性 / 物流滞后 / 当前物料 / phase 等（状态估计，可用 EKF/MHE 或经验证的简化 observer）；
2. **静态 / 慢变参数**：增益、热时间常数、摩擦、效率、传感器偏置等；
3. **未建模残差**：物理模型残差；
4. **不确定度和漂移**：参数后验、预测区间、域外分数、模型分歧。

不要只用参数优化去吸收传感器故障或控制系统逻辑错误；DAQ/DCW 数据质量异常应先停在质量门。

### 6.3 验证 / 校准方法

- 按**批次 / 时间 / 产品 run** 划分 train / validation / held-out test，避免随机切分造成相邻时序泄漏；
- 至少与 persistence baseline、当前快速物理模型、纯数据模型进行比较；
- 分别报告一步误差、多步 rollout 误差、目标量 MAE/RMSE、守卫量 false-safe / false-unsafe、预测区间覆盖率和 OOD；
- 做未参与拟合的批次、recipe、启动/稳态/切换 phase 验证；
- 验证因果方向、质量守恒 / 能量平衡 / 物理可行域等硬 invariant；
- FEM 额外记录网格 / 时间步 / 容差 / residual / convergence / energy balance / 接触状态和资源上限；
- 统计置信区间和适用域，不只给一个平均分。

AML 现有的 NRMSE / rollout / 泛化差 / 行数 / 工件门禁是可复用的起点，但不足以直接构成 FEM 或写控安全门。尤其 safety metric 应单独计算：危险候选被误标安全的频率，比整体 RMSE 更重要。

### 6.4 从真实结果到下一版本

每个真实执行 trial 记录：

```text
snapshot → model version → candidate → predicted distribution → write approval
→ actual DCW ACK/readback → DAQ response window → dcw_judge / rollback
→ prediction residual → calibration candidate
```

回馈只生成 `calibration candidate`。通过 held-out / drift / physics / residual gates，再由审批人提升模型版本。生产模型工件 immutable；任何校准更新都产生新版本并保留前一版、差分、证据和回滚点。

## 7. FEM / CAE 与快速模型的分工

### 7.1 不是每条线都需要 FEM

- 注塑成型：初期适合动态 lumped process model + 历史残差；FEM 仅在模腔充填 / 保压 / 冷却 / 翘曲等空间问题被证明影响决策时引入。
- A2O 污水：适合过程机理 / 质量平衡 / 反应动力学 + 数据校准；通用结构 FEM 通常无直接价值。
- BOPET / 薄膜斜拉：宽幅厚度 / 温度 / 应力 / 取向高度空间相关时，CAE/FEM 更有价值；可用快过程模型先筛选，再用高保真模型复核。
- 连续退火：先用分区热惯性 / 传动 / 冶金动力学模型；在炉内空间温度和材料组织分布成为瓶颈时再加 FEM/热场模型。

### 7.2 高保真模型服务化

建议把 `oblique-biaxial-film-stretching-equipment` 作为隔离的 adapter，而非先搬入主平台：

- 第一期：CLI worker 接受严格 JSON request，返回 JSON result；验证 time / mesh / wall-clock / cancellation / memory budget；
- 第二期：加 HTTP/gRPC wrapper 与 job queue；运行在有资源配额的 worker process / container；
- 第三期：实现 TwinSnapshot ↔ CAE initial state / boundary mapping 和真实 DAQ 对账；
- 每次 response 强制回传 CAE source hash、model version、参数、网格、时间、收敛、constraints、provenance；
- `FAILED`、`UNVERIFIED`、`UNCALIBRATED` 或未到目标 horizon 的结果永远不能成为 write-eligible 建议。

高保真计算不必每个 BO 候选全跑：使用 multi-fidelity / active learning，快速模型筛绝大多数点，只让高不确定或靠近硬边界的少量点进入 FEM。

## 8. Safe Bayesian Optimization 与写控策略

### 8.1 优化问题

每个场景按工艺定义目标和硬约束，例如：

```text
目标: 目标质量误差 + 缺陷 + 能耗 + 产能 / 成本权衡
硬约束: 质量上下限、温度 / 压力 / 张力 / 设备限制、活动配方窗
步幅约束: 每个控制量最大变化
速率约束: 任意 DCW 写之间的最小间隔；本场景当前要求至少 60 秒
chance constraint: 对预测分布要求 P(全部硬守卫满足) ≥ 经工艺批准的阈值
trust region: 本地模型已验证的控制域附近逐步探索
```

目标、权重、机会约束门槛均按场景明确；不得给所有行业使用一个默认为安全的目标函数。

### 8.2 建议算法序列

1. 先做物理模型 DOE / sensitivity，确认控制量能影响目标、参数可辨识；
2. 把可行物理模型输出作为 prior / mean，把高斯过程、ensemble 或其它校准残差作为数据校正及不确定度；
3. 只在 safety filter 后的候选中计算 acquisition；
4. 采用 constrained / safe BO，限制信任域、每次最大步幅、最大实际写入数、试验预算与早停；
5. 输出多个候选及 P05/P50/P95、可行概率、敏感度、物理 / residual 分歧、拒绝原因；
6. 虚拟试验通过仍只是“准入建议”，实际下发仍需 DCW gateway / recipe interlock / binding / HITL policy；
7. 写入后按过程动态和 settling criteria 等待，不把 `writeLockSeconds=60` 误解成过程已稳定；写间隔和响应观察窗是两个不同要求。

### 8.3 不可妥协的安全边界

- PLC 内安全联锁、硬上/下限、急停、伺服 / 秒级以下闭环始终由 PLC / SIS 实现；AI/Twin 不能绕过。
- 仿真服务没有 PLC write credentials；trial API 网络 / IAM 只读。
- Agent 可调用 `twin_simulate` / `twin_optimize`，但不能将任意 trial JSON 伪造成已审批 recommendation。
- Server 重新计算 / 校验 trial hash、model stage、snapshot freshness、recipe version、binding、步幅、最小写间隔、HITL 和 control lock。
- 数值模型输出的安全范围不能扩宽真实 DCW / 配方 / PLC 硬限制，只能更严格地拒绝。
- 候选越出验证 envelope、OOD 高、不确定度大、求解不收敛、监测量不新鲜、守卫缺失或模型漂移时 fail closed。
- 写后自动获取回读 / DAQ，允许 `keep` / `rollback` / `uncertain`；rollback 本身仍过当前写控安全策略并保留审计。
- 先 shadow、再仅建议、再人工批准小步写、最后才讨论有限自动化；严禁第一阶段全自动无限寻优。

## 9. AgentTeam 推荐职责与任务树

| 角色 | 能力 | 不能做什么 |
|---|---|---|
| Twin / Scene Architect | 建 SceneDraft、列缺失映射 / 物理参数 / 适用域、请求领域审核 | 不能自行把未验证公式发布为生产模型 |
| 数据质量 / 状态估计 worker | 检查 DAQ freshness、时钟、缺值、批次 / phase，生成 snapshot 和状态估计证据 | 不能写 DCW 或用无效样本校准 |
| 物理 / FEM worker | 构建 / 调用物理模型，验证公式、边界条件、收敛和约束 | 不能把 FAILED / UNVERIFIED 当成通过 |
| Model Calibration worker | 拟合可辨识物理参数和 residual / uncertainty，做按批次留出验证 | 不能直接晋升 production 模型 |
| BO / Virtual Experiment worker | 生成候选、试验、敏感度与安全可行概率 | 不能直连 PLC；不能改变硬联锁 |
| Process Optimization worker | 比较候选、提出控制意图、按审批后的参数走现有 DCW 工具 | 不能越过 trial / recipe / 权限 / 写入间隔 |
| Leader | 任务分解、选择 worker、核验模型与过程证据、收口 | 不持有 DCW 写授权；不接受无证据的模型推荐 |
| Human / Process Owner | 签署工艺约束、scene / model 版本与有风险的实际控制 | 不需要人工批准纯离线仿真，但必须批准生产写权限策略 |

推荐一个 Goal 的阶段：

```text
质量 / 产能目标
  ├─ 数据质量与现场状态快照
  ├─ 物理机理 / 适用域 / 模型健康核验
  ├─ Twin 虚拟试验 + Safe BO 候选
  ├─ Leader 独立审查目标、guard、模型不确定度和 DCW binding
  ├─ HITL / policy 批准一个小步候选
  ├─ 实际 DCW 写入 → 回读 → 等待工艺响应 → DAQ 窗复测
  ├─ 预测 vs 实际偏差对账 → keep / rollback / uncertain
  ├─ 校准候选版本，不自动覆盖 production
  └─ 汇总交付：试验、模型版本、误差、写入、守卫、任务状态
```

## 10. 分阶段开发计划

### Phase 0 — 术语、责任和数据边界

**交付**：本文件；场景术语 / model status vocabulary；当前组件 owner；PLC/Twin 网络与 credential 信任边界。

**完成门**：团队区分 visual twin、protocol simulator、fast physical model、statistical model、FEM/CAE；写明“非安全系统、无完美保证”。

### Phase 1 — Scene Contract 与不可变现场快照

**开发**：

- `sceneId`、asset topology、control/observation/guard、units、recipe / phase / product / run 标准 schema；
- API 对 simulator blueprint 和实际 DAQ/DCW 节点做差异核对，读回 id、driverConfig、单位、量程、freshness；
- `TwinSnapshot` 规范：DAQ window IDs、DCW SET/ACT、recipe version、phase、扰动、时间范围、data-quality summary、hash；
- agent 只生成 draft，服务端 validator + domain owner 批准后激活。

**验证**：单位 / id / 映射 / 缺失 / stale 检查；不能在没有完整 guard 的场景建 write-eligible twin；snapshot 可重放。

### Phase 2 — Simulator ModelProvider 契约与快速虚拟试验

**开发**：

- 建通用 `ModelProvider` interface：`initialize(snapshot)`, `simulate(controls, horizon, disturbances)`, `health()`, `provenance()`；
- 将 PLC simulator 现有 injection / biax 等模型封成隔离 clone-state provider；
- `POST /twin/trials` 运行时不得调用协议写入、不得 mutate 当前 simulator node / recipe；
- result 包含 time series、summary、constraints、status、uncertainty（早期可先物理参数区间 / ensemble）。

**验证**：物理趋势测试、同输入确定性、隔离性、超时 / cancel、越界拒绝、失败和未收敛返回明确 status；和 simulator 现有协议链路解耦。

### Phase 3 — 物理参数辨识、DAQ 校准与残差模型

**开发**：

- 从真实批次提取输入轨迹 `u(t)`、DAQ `y(t)`、阶段 / 配方 / 扰动；
- 先辨识时间对齐、死区、纯滞后、状态变量、可辨识的低维参数；
- 增加 constrained parameter estimation；同一训练窗拟合不能作验证；
- 用 AML 学习物理 residual 或从物理特征预测残差及不确定度；保留物理 baseline；
- 记录 `calibrationCandidate`，严格按 lot / run 做 train / val / test。

**验证**：和 persistence、原始 physics、data-only baseline 比较；报告 1-step、rollout、guard false-safe rate、区间 coverage、产品 / phase 分层误差。

### Phase 4 — CAE/FEM adapter 与多保真预算管理

**开发**：

- 把斜拉 CAE CLI 接成受资源限制的 sidecar job service；统一 scene/model/snapshot 输入和 JSON result；
- 首先只支持斜拉场景定义的参数、物理 horizon 和固定已批准 mesh；
- 解决现场快照状态、材料历史 / orientation history、边界条件的合法映射；映射做不到时明确报告 unavailable，而非用默认初态伪装现场初始态；
- FEM results 保留 mesh/time/residual/convergence/energy/contact limitations；未完成验证返回 `UNVERIFIED`；
- 快模型广筛，高保真 FEM 只复核高风险、高分歧或边界候选。

**验证**：有界运行时间 / 内存、并发配额、进程隔离、异常取消、跨网格 / 时间步研究，以及模型限制随 result 一起暴露。

### Phase 5 — Shadow mode / 只预测、不写入

**开发**：

- 每个候选写入意图先跑 Twin，但真实 PLC 不受影响；
- 后台记录预测轨迹、实际后续 DAQ、残差 / 区间 coverage、模型分歧、OOD；
- 不向生产自动推荐，只让工程师查看“如果当时采取该动作，模型预测与实际有何差异”；
- 建 drift detection / 数据质量冻结 / 模型过期策略。

**退出门**：在代表性批次 / recipe / phase 的留出数据上持续达到经业务批准的误差和覆盖目标；安全守卫误报漏报经独立审核。

### Phase 6 — Safe BO 与受审批的小步建议

**开发**：

- 多目标 / constrained BO；目标包括质量、缺陷、能耗、产能、动作成本；
- acquisition 只从通过 physical constraints、recipe bounds、write step、trust region、uncertainty 和 OOD filter 的候选取；
- output candidate certificate：trialId、snapshotHash、modelVersion、控制差分、预测区间、feasibility probability、拒绝项；
- AgentTeam 分析候选，Leader 校验；HITL / operate permission 后仍走既有 `dcw_control`；
- 第一个版本每次只批准一个小步，不允许一个 BO 批次把多个参数瞬时打进 PLC。

**退出门**：shadow / 历史回放证明候选可行性优于 baseline；actual writes 已有回读和 DAQ 闭环证据；rollback / stop path 演练完成。

### Phase 7 — 有限自动闭环与产品设计迭代

只有前序门禁逐线通过才讨论开启：

- 自动运行低风险、有充分数据的 operating envelope；
- 每次只授权受限 setpoint、明确上限、最长运行窗、最大动作预算和人工 stop；
- 任何模型漂移、非新鲜 DAQ、预测区间跨硬 guard、两模型高分歧、solver 非收敛即退回只读 / HITL；
- 产品 / 模具 / 材料设计阶段使用同一场景资产与批次证据，做虚拟 DOE → CAE → 实验室样品 → pilot run → 量产版本对账；分开报告模拟数据和真实数据。

“不断作业优化”是这个版本治理与反馈循环，不是无限自动写；控制优化、模型校准和新产品设计三个 loop 必须分别留痕和审批。

## 11. 当前阶段开发指南 / 建议第一批任务

当前不要先把 Agent 接到 CAE CLI 或上 BO。建议首批实现顺序：

1. **先冻结 Contract**：SceneDraft、TwinSnapshot、ModelManifest、TrialRequest、TrialResult、RecommendationCertificate 六个 schema；确认单位、时间、phase、recipe、guard、status vocabulary。
2. **先建只读 Snapshot Service**：从 actual DAQ/DCW/recipe 取值；附 `lastAt`、source IDs、qualities、freshness、unit、line/product/run/recipe；统一持久快照和 hash。
3. **复用现有 simulator 双拉快模型**：新增纯 clone `simulate` API；同一候选多次运行不能改动 `simulator /api/nodes`、实际 PLC config、recipe 或当前物理模型状态。
4. **建立 replay parity**：对 simulator 本身，把真实参数序列 replay 到 fast model，比较 `truth`、`exposed`、平台 DAQ；truth 是模拟器内部验证来源，不混进现场生产模型训练集。
5. **加参数校准第一版**：只选少量物理可辨识参数，按批次留出，输出 parameter posterior / residual / fit report；不自动 promote。
6. **先 shadow endpoint / dashboard**：记录模型 forecast 与之后真实 DAQ；先测模型是否校准，再向工艺专家展示建议。
7. **最后才 Safe BO**：试验数限制、单步范围、最小写间隔、recipe window、模型分歧阈值、stop / rollback 全由服务端执行。
8. **CEA sidecar 单独验证**：先做只读离线 adapter conformance，不能共享 PLC 凭据；不把 `recommended=true` 误认为生产审批。

第一条端到端工程 slice 建议选 **BOPET 双拉厚度控制**：当前快速模型、控制点和质量量已完整；再把斜拉 CAE 用于候选复核。注塑场景近期的 AgentTeam 闭环可作为协议 / DAQ / DCW / Team orchestration 的 smoke path，但它本身不证明斜拉 FEM 校准。

## 12. 初始验收指标（阈值应由工艺 owner 最终批准）

以下是方案设计的初始门，不是全行业标准值：

- Snapshot 节点映射：写控节点和全部硬守卫的 `id / unit / source / readback / freshness / recipe` 均可对账；关键变量缺失率 0 才允许运行 write-eligible trial。
- Repeatability：固定模型 hash、snapshot hash、control / disturbance、seed 时可复现到模型声明的数值容差。
- Calibration: 按 batch/run 的 holdout rollout 误差优于 persistence 和未校准 physical baseline；低样本不得晋升；报告 critical guard 的 false-safe 事件数，默认要求零关键遗漏。
- Uncertainty: 预测区间 coverage 在独立留出集检验；OOD/分布外必须拒绝，而非只扩大置信区间继续写。
- FEM: `FAILED` / `UNVERIFIED` / 适用域外比例必须可见；网格 / 时间步 / solver 运行配置随输出归档；不存在“只用 FE 收敛即代表真实”。
- Safe BO: 所有候选均能追溯到 trial + snapshot + model version；任何硬约束候选通过率 = 0（即全拒）；至少一条完整实际 verify / rollback path 演练通过。
- Online change: 每次 DCW 写入必须双向关联 actor、task、node、trial、model、hypothesis、old/requested/accepted/readback、recipe、安全决策、DAQ before/after、judge；证据缺失不能收口为成功。
- Shadow 前到现场前至少分级：`offline replay → shadow → recommendation only → HITL small-step → bounded auto`；每级单独签署，无跨级自动晋升。

## 13. 主要风险和应对

| 风险 | 后果 | 应对 |
|---|---|---|
| SceneDraft 虚构节点含义 / 单位 / 因果 | 错模型和危险建议 | Agent 只草拟；蓝图、接口实测、工艺 owner 签署；未知字段阻断激活 |
| 同一个参数同时代表 model input 和 PLC register 值 | 单位 / 标定错，回读假成功 | semantic key 与 node ID 解耦，显式 transform / unit / scale provenance，现场 round-trip 检查 |
| DAQ stale / 旧批次拼入当前快照 | 误判当前状态 | 时间窗 / run / recipe / phase 强关联，staleness gate，原始样本 IDs 可重放 |
| 把模拟器 truth 当成实厂标签 | 虚假 accuracy | source class 分离：sim-truth / actual-DAQ / lab-test / FEM;训练集禁止隐式混合 |
| physics 或 FEM 结构错误 | 过度信任错误结果 | discrepancy report、holdout、cross-model disagreement、human review、安全界限独立于模型 |
| FEM 未收敛或时间太久 | 延时 / 错误推荐 | 资源配额、异步 trial、deadline、取消、显式 `UNVERIFIED` / `FAILED` |
| 参数不可辨识 / 多参数共线 | 校准不稳定 | 敏感度与可辨识性诊断、分步 DOE、冻结弱可辨识参数、收集设计良好的安全试验 |
| Data residual 抵消物理硬约束 | 外推“拟合好但不守恒” | residual 限幅 + invariant projection / hard feasibility rejection，残差模型不能写安全边界 |
| BO 利用模型漏洞 | 在仿真好、现场坏的 adversarial candidate | conservative trust region、penalize uncertainty、multi-fidelity、OOD filter、每步小幅、actual feedback |
| 运行期间校准模型变化 | forecast 不可重现 | immutable versions、trial pin model hash、candidate vs production stage、审计与 rollback |
| 误认为 60s 写保护就是充分 settling | 过程响应未达稳态 | min write spacing 与 settling policy 独立，按工艺时间常数 / DAQ stability 判定 |
| CAE 初态和现场状态不一致 | 场模型初值失真 | TwinSnapshot→CAE state mapping/证据为上线硬门；当前不能只把 SP 当初始状态 |

## 14. 尚待产品 / 工艺决策的问题

实施时必须由用户 / 工艺 owner 给出，文档暂不替用户假定：

1. 第一条“真实产品设计”流程对接哪类产品 / 线体？推荐 BOPET 双拉，但确认产品质量目标及用户价值后定。
2. 允许自动控制到哪一级？首个 production 版本默认仍为人工审批小步写，不自动化全流程。
3. 每个场景的目标函数和硬 guard 谁批准、如何版本化？建议由 process owner + controls / safety reviewer 共签。
4. 哪些 DAQ 质量标记、freshness 和校准周期算可用？按传感器 / 工艺分开定。
5. Twin result 和候选 certificate 的保留 / 隐私 / 存储期限？原始 DAQ、材料批次、配方可能受生产数据治理规则约束。
6. 斜拉 CAE service 部署在哪里、计算预算和许可证如何处理？当前是独立项目，需要明确维护边界。
7. 实际 MES / lab / QMS / historian 批次标签是否可用？没有这些标签，产品设计 / 批次级校准会受限。

## 15. 术语和成功定义

- **Digital representation / 3D twin view**：设备、工位、Agent 和遥测的可视化；不意味着物理仿真。
- **Protocol simulator**：可用真实协议栈与 DAQ/DCW 接入的虚拟设备；不是真实工厂数据。
- **Fast physical/process model**：快速、可用于多候选虚拟试验的低阶方程 / 动态模型。
- **Statistical residual / surrogate**：基于真实数据学习物理模型差额、预测分布或局部 response 的模型。
- **FEM/CAE**：用于空间场问题的数值模型；有收敛性和适用域闸门。
- **Twin trial**：固定快照、模型版本、控制轨迹、假设和结果的隔离虚拟试验。
- **Safe recommendation**：trial 通过所有模型状态、数据质量、约束、配方、权限和置信度门后的候选建议；不等于写入许可证。
- **Useful twin / 相对有参考价值的孪生**：在被测适用域内经独立数据校准、误差 / 不确定度量化、可重放、对决策有增益，且出域时会拒绝的版本化模型。并不声称完美或 universally accurate。

真正的成功不是“优化器找出数值最大的模型输出”，而是：**模型预测有留出证据、虚拟候选有安全证书、实际动作有权限和硬限界、DAQ 实际结果可以解释 / 对账，发现失配会降低模型权限而不是隐藏。**
