\section{Introduction}
\IEEEPARstart{L}{arge} language models (LLMs) are being explored for industrial diagnosis, engineering assistance, and control-program generation \cite{raza2025industrial,sabetta2025assistant,liu2026agents4plc,fakih2024llm4plc}. Recent systems also connect agents to simulated controllers or real machines \cite{vyas2026ftc,hofmann2025nlc}. The question is therefore not simply whether an LLM can issue a command. For a production-line deployment, the engineering problem is to preserve the meaning, authority, and history of that command across heterogeneous equipment, multiple agents, and changing operating recipes.

Consider a team asked to correct film thickness while maintaining pressure and temperature limits. One member may inspect telemetry, another propose a setpoint, and a lead coordinate the task. A protocol connection alone does not identify which member may change which node, which recipe applies to the current batch, whether a human must approve, or whether the subsequent observation measures the commanded register or the process response. Implementing these associations separately for each application introduces duplicated configuration and makes failures difficult to reconstruct. Conversely, putting every function behind one interface does not by itself establish atomic execution, physical safety, or valid optimization.

We present \system{}, a configurable framework for this supervisory integration problem (Fig.~\ref{fig:intro}). An industrial node combines its acquisition or setpoint interface with engineering semantics; an explicit binding grants a deployed channel member access to that node. A line/product/recipe/run model supplies the production context shared by observations and actions. The platform core hosts agent orchestration and industrial supervision together, while engine subprocesses, optional external stores, and field endpoints retain their own boundaries. This organization reduces application-specific routing within the supported driver set without equating shared state with an end-to-end transaction.

The agent loop operates at supervisory, seconds-to-minutes timescales. Regulatory control and plant-side protective functions remain in PLCs. Within the platform, proposal, admission, device execution, and outcome assessment are distinct operations. Manual bindings require an approval decision; automatic bindings omit that wait but retain the applicable execution checks. The system records write attribution and supports separately triggered compensation. This separation makes it possible to inspect a failed proposal, a failed write, and an unsuccessful process adjustment as different events.

The contributions are threefold:
\begin{enumerate}
\item A \textbf{node-native integration model} connecting heterogeneous acquisition and control nodes, deployed agent teams, and versioned production runs through explicit capabilities and shared identifiers (Sec.~\ref{sec:arch}).
\item An \textbf{implemented supervisory workflow} that separates team coordination, source-dependent write checks, agent-submitted judgments, physical compensation, and human decisions. Its six mechanisms and cross-cutting HITL boundary are described with their actual scopes and exceptions (Sec.~\ref{sec:mech}).
\item A \textbf{traceable, layered evaluation}: two simulated plant scenarios over real protocol transports, lifecycle and fault probes, fixed-controller closed-loop trajectories, a governance ablation, and four exploratory LLM campaigns. The results distinguish integration coverage from control quality and disclose incomplete observations and reproduction limits (Sec.~\ref{sec:eval}).
\end{enumerate}
The paper's central claim is reusable supervisory integration within these tested settings, not certified safety, general industrial autonomy, or superiority of an LLM controller.
