\section{System Architecture}
\system{} (v0.7.39) is an integration framework, not an application: it ships the two halves that industrial agent deployments otherwise bolt together by hand as a single Node.js process---a REST and WebSocket API, an MCP server with 25 tools \cite{mcp2024}, an A2A agent interface \cite{a2a2025}, and a plugin host with hot-reload and error isolation---all under one authentication layer. Operators enter through the web console or a terminal (TUI) workbench sharing the same approval queue. Fig.~\ref{fig:arch} shows the complete architecture.

\subsection{Design Principles}
\emph{P1, node-native integration}: the agent runtime and the industrial runtime execute in one process and one data domain---binding, telemetry, and write control share invariants rather than APIs. The consequence that matters is \emph{check-then-actuate integrity}: the interlock test and the driver call run in one event-loop turn over the same process-local recipe-run state, so the window that authorizes a write cannot change between check and actuation, and no IPC or serialization boundary sits between them; a window change after the frame is sent is bounded by the backstop, not by the check. Co-residency governs the platform-internal path; it does not contain the harness engines, which remain privileged local processes---their containment is a deployment property (availability probe, least privilege, zoning; Sec.~IV-D). Gateway-style integrations, by contrast, must trust a translation layer they do not control.
\emph{P2, supervisory positioning}: \system{} occupies the supervisory, soft-real-time tier; hard real-time control and safety functions remain in PLCs, mirroring the IEC~61511 separation of basic control from safety instrumented functions \cite{iec61511}.
\emph{P3, configuration-driven, down to the plant scenario}: a typed configuration schema drives acquisition intervals, approval policies, retention, and memory budgets; driver configurations are derived from each device's integration export rather than hand-written, and a named \emph{plant scenario}---devices, signal semantics, dynamics, recipes---re-instantiates the full deployment, so adapting to a new line is a configuration task (measured in Sec.~\ref{sec:port}: the same instance is recommissioned onto a second scenario by switching one identifier, with zero platform code changes).
\emph{P4, engine-agnostic governance}: agent intelligence is a replaceable component; the governance pipeline of Sec.~IV is defined at the tool boundary and is therefore identical for every engine.


\subsection{Industrial Half}
Five protocol drivers spanning four protocol families---Modbus TCP, Modbus RTU (over TCP), OPC UA \cite{iec62541}, MQTT, and HTTP/REST---sit behind a uniform driver interface and are plugin-registerable at runtime (\texttt{ctx.daq.registerDriver}); a mock driver supports deterministic testing. Each acquisition node runs an \emph{edge runtime} that owns its sampling schedule and in-flight mutual exclusion, organized around three decoupled intervals per node: acquisition (default 5\,s, floor 1\,s, hard clamp $[0.1, 60]$\,s; sub-tick intervals are served on the next 250\,ms sweep tick), WebSocket publish (default 1\,s), and display/trend (default 5\,s)---decoupling acquisition from delivery prevents downstream consumers from starving the plant-facing schedule. Nodes are sampled by a gateway sweep with a 250\,ms tick and a non-accumulating budget of 64 in-flight samples per tick; a \emph{rotating cursor} plus a per-node \emph{due check} prevents budget from being consumed by not-yet-due nodes ahead of due ones, so tail nodes are never starved.

Each node also runs an alarm state machine over \texttt{ok}/\texttt{warn}/\texttt{alarm}/\texttt{offline}: an 8\,\% warn band, 2\,\% hysteresis, three-frame debounce on \texttt{ok}$\leftrightarrow$\texttt{warn}, watermark-based out-of-order defense, and recipe-window violations overlaid as edge-triggered \texttt{alarm}; acknowledgment is a human step with escalation (default 15\,min). Time series persist to TimescaleDB (batched 500\,ms flushes, with tiered retention) and frames to MinIO with degraded fallback to local disk; platform state persists to SQLite in WAL mode with an FTS5 index, and every alarm, write, recipe change, and rollback row carries line, product, and recipe dimensions, enabling the metric slices of Sec.~\ref{sec:eval}.

\subsection{Agent Half}
Fourteen engines are registered with a capability matrix (mid-task steering, supervision, human-in-the-loop, terminal access, context statistics, compaction), spanning an in-process deterministic mock (used for the experiments of Sec.~\ref{sec:eval}), a first-party RPC engine (omp), and vendor or open-source CLI/SDK agents (codex, claude, opencode, qwen, gemini, pi, hermes, dsh); capabilities are asserted per engine, verified by the static audit (Sec.~\ref{sec:static}), and dispatch happens only after an availability allow-list probe that resolves each engine's executable and validates its response.

The collaboration unit is the \emph{channel}: a named room that hosts one lead, that lead's workers, the task tree, and the message history; teams deploy into a channel as a unit, and every industrial binding a team holds is scoped to its channel membership. Work is organized as a task tree whose seven states are \textsc{submitted}, \textsc{assigned}, \textsc{working}, \textsc{waiting} (a parent blocked on children), \textsc{failed}, \textsc{cancelled}, and \textsc{completed}. Each team's lead runs a supervision loop on a 1\,s tick with exponential idle backoff and event wake-up. Each tick first assembles a state fingerprint---a sorted digest of the task tree, member states with queue depths, and the newest mailbox message; if the fingerprint is unchanged the LLM call is skipped, so an idle plant costs no tokens, except when a parent task has become closeable. When consulted, the LLM owns goal judgment, completion, and escalation; the mechanical decisions are taken on every tick by a deterministic rule engine regardless of the LLM---FIFO dispatch of unassigned proposals to the worker with the shortest queue (ties broken by longest idle), reassignment of failed tasks while retries remain (limit 3), and a 300\,s stall watchdog that treats tool activity as liveness---so progress is guaranteed if the LLM abstains, errors, or returns nothing actionable. Both mechanisms are ablated as E2/E3 (i.e., B6/B7) in the released protocol, and their constants are anchors of the static audit (Sec.~\ref{sec:static}).

Agents accumulate typed memories (session, task, peer, team chronicle, reflection, semantic) in SQLite with FTS5 and an optional vector index. Retrieval fuses a lexical channel (FTS5 with CJK-aware unigram segmentation) and a dense vector channel by reciprocal-rank fusion \cite{cormack2009rrf} ($k{=}60$), scores candidates by $0.5\,\rho + 0.3\,\phi + 0.2\,\iota$---normalized relevance, kind-aware recency with 3--14\,d half-lives, and access-weighted importance---diversifies by maximal-marginal-relevance \cite{carbonell1998mmr} ($\lambda{=}0.7$), and injects the result in three layers (session primer, task and peer history, semantic and chronicle context) under an explicit 500-token budget. Compaction triggers at 70\,\% of the context window and harvests summaries back into memory.

\subsection{The Governed Bridge}
The bridge is where the integration claim becomes concrete: a commissioning engineer binds plant nodes to agents (a single agent or a whole team), the platform injects physical semantics into the bound agents' context, and the bound agents' tool surface is derived from the binding---there is no separate integration layer to build or maintain. A bound node yields a \emph{semantic card} in the agent's context: physical quantity, unit and display precision, the \emph{hard interlock} range, the \emph{soft interlock} recipe window, warn band, live value with freshness, and an operating rule limiting any single step to 2\,\% of span. Bindings carry an operating mode: \emph{manual} (every agent write is approval-gated), \emph{auto} (writes proceed under the interlock and backstop), or \emph{unbound} (no write path); a team's members can share one node set, so a lead-dispatched task and a worker's actuation share one authorization scope. Agents never see register addresses.

Agents act through a host-tool surface of 48 tools, 23 of them industrial or automated-ML (the MCP server exposes a 25-tool subset): setpoint control (\texttt{dcw\_control}), reading, frame retrieval, judgment, rollback execution, audit views, and recipe editing under approval. Two separations are enforced architecturally: \emph{judgment is not execution}---\texttt{dcw\_judge} records a keep/rollback/uncertain verdict but cannot actuate---and \emph{lead-only tools} are restricted to lead agents with approval. Sec.~IV formalizes the single write path.

\subsection{Digital Twin and Node-Binding Rendering}
Rendering binding is part of the integration model, not a visualization afterthought. A \emph{device-twin registry} persists, per scene entity, the bound 3D asset (\texttt{modelRef}), the agent in charge (\texttt{boundAgentId}---a virtual operator avatar acting through MCP \texttt{device.*} tools), an entity kind (device, environment, asset, or procedural sensor mesh), and the three state planes of the twin contract (the device-shadow pattern \cite{ditto2024}): \emph{telemetry} (live fields from acquisition or simulation), \emph{desired} (the agent's intent), and \emph{state} (the reconciled value), plus the command set. A WebSocket event bus broadcasts device lifecycle events and every acquisition reading, so the scene re-renders live values without polling; conversely, scene edits write transforms back to the node registry, so the scene doubles as a commissioning editor while never becoming a source of actuation: \emph{desired}-to-\emph{state} reconciliation itself traverses the governed write path when it actuates (Sec.~IV).

\subsection{Production-Line Management}
The framework models a production line as a four-level object tree---line, product, recipe, \emph{run}---because every governance object of Sec.~IV hangs off it: the recipe window constrains writes jointly with the hard range while a run is active (Eq.~\eqref{eq:constraint}), acquisition samples only nodes whose line has an active batch (between batches, PLC-side protection persists per P2), and the backstop scores open records against the record parameter's active recipe window (Sec.~IV-C). The recipe lifecycle is versioned and non-destructive: editing creates version $n{+}1$; marking the active run \emph{known-good} freezes the rollback baseline; reverting to an earlier version creates a new version rather than rewriting history; \emph{known-good rollback} re-dispatches the frozen parameter set to the PLC; and one-click \emph{apply} opens a fresh batch. An active run therefore binds exactly one recipe version to one batch, giving every write a unique governance context---the window $W_r(p)$ of Eq.~\eqref{eq:constraint}---and giving every alarm, journal anchor, and backstop evaluation an unambiguous owner. The lifecycle has two bounded exits from an off-window excursion: automatic rollback while the node's executed-rollback count is below $K{=}2$ (Sec.~IV-C), and mandatory human escalation afterwards. Every operation lands in a central audit log with typed actor attribution (user, agent via channel/member badge, system) and line/product/recipe dimensions; write operations are additionally anchored in a signed journal with previous/new values, source, approval, and record identifiers---the substrate for the per-write attribution metric of \bench{} (Sec.~\ref{sec:bench}) and the forensic queries used in the case study (Sec.~\ref{sec:case}).
