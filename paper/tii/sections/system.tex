\section{System Architecture}
\label{sec:arch}
\system{} (v0.7.39) is an integration framework, not an application. In one Node.js process it ships the two halves that industrial deployments otherwise bolt together by hand---a REST and WebSocket API, an MCP server with 25 tools \cite{mcp2024}, an A2A agent interface \cite{a2a2025}, and a hot-reloading, error-isolated plugin host---under one authentication layer. Operators enter through a web console or a TUI workbench; agents enter through MCP or A2A; both meet on the same objects and the same approval queue. Fig.~\ref{fig:arch} shows the architecture; the rest of this section explains what holds it together, and Sec.~\ref{sec:mech} details each mechanism.

\subsection{Design Principles}
\emph{P1, node-native integration}: the agent and industrial runtimes execute in one process and one data domain, so binding, telemetry, and write control share invariants rather than APIs. This yields \emph{check-then-actuate integrity}: the interlock test and the driver call run in one event-loop turn over the same process-local recipe-run state, and the window that authorizes a write cannot change between check and actuation. Co-residency governs the platform-internal path but does not contain the harness engines, which remain privileged local processes (containment is a deployment property; Sec.~\ref{sec:hitl}).
\emph{P2, supervisory positioning}: \system{} occupies the supervisory, soft-real-time tier; hard real-time control and safety functions remain in PLCs, mirroring the IEC~61511 separation of basic control from safety instrumented functions \cite{iec61511}.
\emph{P3, configuration-driven, down to the plant scenario}: a typed configuration schema drives acquisition intervals, approval policies, retention, and memory budgets; driver configurations derive from each device's integration export, and a named \emph{plant scenario}---devices, signal semantics, dynamics, recipes---re-instantiates the full deployment, so adapting to a new line is a configuration task (measured in Sec.~\ref{sec:port}).
\emph{P4, engine-agnostic governance}: agent intelligence is a replaceable component; the governed write path of Sec.~\ref{sec:writepath} is defined at the tool boundary and is therefore identical for every engine.

\subsection{Three Planes and a Governed Bridge}
The architecture has three planes. The \emph{agent half} couples 14 interchangeable LLM harness engines with lead-supervised teams (channels) and typed episodic--semantic memory, so team organization, supervision, and learning are platform services rather than per-application code (Sec.~\ref{sec:channel}). The \emph{industrial half} terminates five protocol families in per-node edge acquisition runtimes, a starvation-free gateway sweep, an alarm chain, and line/recipe management---the supervisory data and control substrate (Secs.~\ref{sec:nodes} and \ref{sec:lineops}). The \emph{governed bridge} between them is this paper's object: binding a node to an agent injects physical semantics as a semantic card and derives a tool surface whose only write path is the governed pipeline of Sec.~\ref{sec:writepath}---48 host tools, 23 of them industrial or automated-ML, with the MCP server exposing a 25-tool read-oriented subset for external clients. Two separations hold across the whole system: \emph{judgment is not execution}, and \emph{lead-only tools} are restricted to lead agents with approval (Sec.~\ref{sec:hitl}).

Beneath all three planes lies \emph{one data domain}: time series, frames, platform state, and a signed audit journal with typed actor attribution, all carrying line/product/recipe dimensions (Sec.~\ref{sec:lineops}). The device-twin registry lives here too, feeding a three.js scene that renders live state over a WebSocket bus but never actuates (Sec.~\ref{sec:lineops}).

\subsection{One Loop, End to End}
A single walk makes the collaboration concrete; Sec.~\ref{sec:mech} revisits each station in order. An engineer connects a temperature controller on line~3: export its integration descriptor, test connectivity over Modbus TCP, create the node, provision line/product/recipe, and bind the node to a team (Sec.~\ref{sec:nodes}). The node now exists twice---as a physical endpoint sampled by its edge runtime, and as a \emph{semantic card} (unit $^\circ$C, hard range, recipe window, freshness) through which agents see it. A team deploys into a channel and the binding mode fixes what its writes may do unaided (Secs.~\ref{sec:channel} and \ref{sec:hitl}).

The plant then runs. The lead's supervision tick notices a drift task and dispatches it; a worker agent queries fresh values (\texttt{daq\_query}), reads $187\,^\circ$C against a recipe window of $[176, 188]\,^\circ$C, and proposes a setpoint move to $185\,^\circ$C through \texttt{dcw\_control} (Sec.~\ref{sec:loop}). That proposal becomes a \emph{governed write} (Sec.~\ref{sec:writepath}): the interlock checks $185$ against the window, the driver writes and reads back $185$, and a signed journal anchor records previous value, new value, source, and actor. Fresh acquisition confirms the controller followed; \texttt{dcw\_judge} inspects the record and returns \emph{keep}; the outcome lands in team memory (Sec.~\ref{sec:channel}). Had the process instead drifted out of window and stayed there, the backstop would have scored the open record against the window, and after three out-of-window samples rolled the node back to its recorded baseline---at most twice per node, then a human decides (Secs.~\ref{sec:loop} and \ref{sec:recipe}). Every station of this walk is configuration or platform code, none line-specific glue; Sec.~\ref{sec:eval} measures each of them on a live instance.
