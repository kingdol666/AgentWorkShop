\section{System Architecture}
\label{sec:arch}
\system{} separates team coordination from plant interaction while linking
both through industrial nodes and production context (Fig.~\ref{fig:arch}). A
node is an acquisition or control endpoint with engineering semantics,
connection settings, line membership, and agent bindings. Channels coordinate
agents; controller services mediate node operations. This separates three responsibilities: deciding what to change, authorizing
and executing the change, and recording what followed.

\subsection{A Shared Supervisory Core}
The Node.js core hosts team routing, industrial services, and protocol
adapters. Operator and integration interfaces share objects but differ in
permissions; agent-tool authority comes from node bindings, not channel access
or endpoint availability. Engine subprocesses and persistent stores remain
external to the core. Connections, protocol queues, and readback are
asynchronous; fast regulation and protection remain with the plant controller
and its safety equipment.

\subsection{Reasoning, Plant Interaction, and Operational Context}
A channel coordinates deployed agent instances, called members, through a
lead, workers, a task tree, messages, and retrievable memory. An agent
proposes actions; its engine is the runtime implementation that executes it.
Engine adapters preserve node identity and the controller interface across
runtime implementations; the benchmark harness scripts these interactions for
evaluation.

Acquisition nodes (DAQ) convert protocol readings to engineering quantities;
control nodes (data-control-write, DCW) translate setpoints into device
commands and readback results. Per-node runtimes manage timing and in-flight
operations; controller services supply gateway state, recipe context, and
write bookkeeping. Many-to-many node--device associations describe
configuration, not execution routing: each control write uses the node's
configured driver and connection.

\subsection{Logical Continuity Across a Production Run}
Lines, products, recipes, and runs organize production context. Acquired data
carry active-context tags resolved at ingestion. Optimization records retain
line, node, recipe, and actor references, but no run identifier; their
baseline and response queries use node, line, and time rather than enforce
run-isolated observations, so a baseline can overlap an earlier run. Platform
state uses SQLite and file-backed repositories; configured measurement and
object backends are TimescaleDB and MinIO, with SQLite and disk fallbacks.
These links support attribution across stores, not a single transaction
domain.

A BOPET thickness adjustment illustrates how the objects work together. The
channel carries one production objective and delegates a task to a worker;
the worker queries a thickness-acquisition node, then addresses casting
speed, fast-roll speed, or rail width through bound control nodes. Each node
resolves its own protocol and engineering units, while the production
objects identify the operating context. An optimization record associates an
executed change with its actor and later judgment, so the task can span
protocols without treating a channel message as write authority or a
task-board completion as a device acknowledgment; Sec.~\ref{sec:agentloop}
follows this sequence in the recorded mission.
