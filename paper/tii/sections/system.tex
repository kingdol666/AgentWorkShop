\section{System Architecture}
\label{sec:arch}
\system{} integrates multi-agent reasoning with industrial supervision around a common representation of production assets and their operating context. Its organizing object is the node: an acquisition or control endpoint with engineering semantics, device connections, line membership, and explicit agent bindings. A channel organizes the agents that interpret these endpoints, while controllers mediate their interactions with the plant. Fig.~\ref{fig:arch} locates these components and their execution boundaries. The architecture brings reasoning and operational state together without treating either an agent decision or a database update as a physical control transaction.

\subsection{A Shared Supervisory Core}
The Node.js core hosts channel routing, task scheduling, industrial services, protocol adapters, and platform interfaces. REST and WebSocket endpoints serve operator applications; MCP and A2A interfaces support external integration; the plugin host extends platform capabilities. These surfaces reuse platform objects, but their exposed operations and permission checks differ. In particular, an agent's industrial authority derives from its node bindings rather than from access to the channel or from the mere availability of a protocol endpoint.

Co-residency reduces the need to synchronize duplicate representations of nodes, bindings, and active runs across separately assembled applications. It does not place the entire deployment in one process. CLI engines and the OMP engine can execute in spawned processes; TimescaleDB and MinIO are external services. Nor does a common event loop make constraint checking atomic with actuation: connection establishment, queued protocol operations, and readback introduce asynchronous boundaries. The architecture therefore provides supervisory coordination, not a lock spanning software state and the physical process. Fast regulation and protective functions remain responsibilities of the plant controller and its safety equipment.

\subsection{Reasoning, Plant Interaction, and Operational Context}
On the reasoning side, a channel combines a lead, worker instances, a task tree, messages, and retrievable memory. The scheduler couples model-based supervision to deterministic dispatch and progress tracking. Engine adapters allow different reasoning implementations to participate without changing the identity of a bound node or the controller interface. This separates task organization from device authority: assigning a worker a task does not itself grant permission to execute the associated industrial action.

On the plant side, acquisition nodes turn protocol readings into engineering quantities, while control nodes translate engineering setpoints into device commands and readback results. Per-node runtimes manage timing and in-flight operations; controller services supply gateway state, recipe context, and write bookkeeping. Nodes and devices have many-to-many configuration associations: one device can supply several semantic nodes, and a node can reference several devices. Association is distinct from execution routing. A control-node write invokes its configured driver and connection settings rather than iterating over its associated devices. The reasoning interface thus follows process meaning without implying multi-device actuation by one write.

The bridge between these sides consists of semantic cards, instance-specific bindings, industrial tools, and source-dependent controller checks. Cards expose units, ranges, current values, and relevant process context. Bindings determine whether a channel member can request an operation and whether human approval is needed. Controllers then apply the checks appropriate to that request's origin. The resulting separation is important: semantic guidance helps an agent propose a sensible action, whereas executable checks determine which requests reach a driver. Prompt guidance, including the suggested small adjustment step, is not an additional enforced interlock.

\subsection{Logical Continuity Across a Production Run}
Lines, products, recipes, and runs provide the context in which measurements and interventions become comparable. Their identifiers connect platform state, time series, image frames, operational events, and optimization records across heterogeneous stores. SQLite and file-backed repositories support platform state, TimescaleDB supports historical measurements, and MinIO supports object storage. Together these constitute one logical data model, not one transaction domain. The journal records attributable changes and judgments; it is not a cryptographically signed ledger, and bookkeeping failure does not necessarily undo an already completed write.

An end-to-end interaction begins when an engineer connects devices, defines nodes, associates production context, and binds channel members. Starting a line establishes an active run and initiates its parameter writes. Agents inspect the resulting observations, exchange evidence, and propose adjustments through their bound tools. Accepted requests proceed to device communication and readback; subsequent observations inform an agent-supplied judgment and an independent rule-based backstop. Recovery may require a further physical write rather than merely changing a recipe definition.

Operators participate throughout this sequence through approvals, line operations, and monitoring. The device-twin renderer visualizes state without directly performing protocol I/O, but controls in the Town interface can request API writes. Visualization is thus separated from device transport, not from all operator actuation.
