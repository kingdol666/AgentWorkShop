\section{System Architecture}
\system{} (v0.7.39) is an integration framework, not an application: it ships the two halves that industrial agent deployments otherwise bolt together by hand as a single Node.js process---a REST and WebSocket API, an MCP server with 25 tools \cite{mcp2024}, an A2A agent interface, and a plugin host with hot-reload and error isolation---all under one authentication layer. Operators enter through the web console or a terminal (TUI) workbench sharing the same approval queue. Fig.~\ref{fig:arch} shows the complete architecture.

\subsection{Design Principles}
\emph{P1, node-native integration}: the agent runtime and the industrial runtime execute in one process and one data domain---binding, telemetry, and write control share invariants rather than APIs. This is what makes the write-path contract of Sec.~IV \emph{enforceable}: gateway-style integrations must trust a translation layer they do not control, whereas here the governance checks run in the same process as the driver calls they guard.
\emph{P2, supervisory positioning}: \system{} occupies the supervisory, soft-real-time tier; hard real-time control and safety functions remain in PLCs, mirroring the IEC~61511 separation of basic control from safety instrumented functions \cite{iec61511}.
\emph{P3, configuration-driven, down to the plant scenario}: a typed configuration schema drives acquisition intervals, approval policies, retention, and memory budgets; driver configurations are derived from each device's integration export rather than hand-written, and a named \emph{plant scenario}---devices, signal semantics, dynamics, recipes---re-instantiates the full deployment, so adapting to a new line is a configuration task (measured in Sec.~\ref{sec:port}: the same instance is recommissioned onto a second scenario by switching one identifier, with zero platform code changes).
\emph{P4, engine-agnostic governance}: agent intelligence is a replaceable component; the governance pipeline of Sec.~IV is defined at the tool boundary and is therefore identical for every engine.


\subsection{Industrial Half}
Five protocol drivers spanning four protocol families---Modbus TCP, Modbus RTU (over TCP), OPC UA \cite{iec62541}, MQTT, and HTTP/REST---sit behind a uniform driver interface and are plugin-registerable at runtime (\texttt{ctx.daq.registerDriver}); a mock driver supports deterministic testing. Each acquisition node runs an \emph{edge runtime} that owns its sampling schedule and in-flight mutual exclusion, organized around three decoupled intervals per node: acquisition (default 5\,s, floor 1\,s, hard clamp $[0.1, 60]$\,s; sub-tick intervals are served on the next 250\,ms sweep tick), WebSocket publish (default 1\,s), and display/trend (default 5\,s)---decoupling acquisition from delivery prevents downstream consumers from starving the plant-facing schedule. Nodes are sampled by a gateway sweep with a 250\,ms tick and a non-accumulating budget of 64 in-flight samples per tick; a \emph{rotating cursor} plus a per-node \emph{due check} prevents budget from being consumed by not-yet-due nodes ahead of due ones, so tail nodes are never starved.

Each node also runs an alarm state machine over \texttt{ok}/\texttt{warn}/\texttt{alarm}/\texttt{offline}: an 8\,\% warn band, 2\,\% hysteresis, three-frame debounce on \texttt{ok}$\leftrightarrow$\texttt{warn}, watermark-based out-of-order defense, and recipe-window violations overlaid as edge-triggered \texttt{alarm}; acknowledgment is a human step with escalation (default 15\,min). Time series persist to TimescaleDB (batched 500\,ms flushes, retention 168\,h/720\,h) and frames to MinIO with degraded fallback to local disk; platform state persists to SQLite in WAL mode with an FTS5 index, and every alarm, write, recipe change, and rollback row carries line, product, and recipe dimensions, enabling the metric slices of Sec.~\ref{sec:eval}.

\subsection{Agent Half}
Fourteen engines are registered with a capability matrix (steer, supervise, hitl, terminal, context statistics, compaction), spanning an in-process deterministic mock (used for the experiments of Sec.~\ref{sec:eval}), a first-party RPC engine (omp), and vendor or open-source CLI/SDK agents (codex, claude, opencode, qwen, gemini, pi, hermes, dsh); capabilities are asserted per engine, verified by the static audit (Sec.~\ref{sec:static}), and dispatch happens only after a three-stage availability probe. Work is organized as a seven-state task tree: each team's \emph{lead} runs a supervision loop (1\,s tick with idle backoff; event wake-up) whose LLM decisions are throttled by a state fingerprint---an unchanged world state skips the LLM call---and always shadowed by a deterministic rule engine (FIFO dispatch, shortest-queue-then-longest-idle selection, retry limit 3, 300\,s stall watchdog with tool-activity liveness) that guarantees progress if the LLM abstains, errors, or produces nothing actionable; both mechanisms are ablated as E2/E3 in the released protocol. Agents accumulate typed memories (session, task, peer, team chronicle, reflection, semantic) in SQLite with FTS5 and an optional vector index, retrieved by reciprocal-rank fusion \cite{cormack2009rrf} ($k{=}60$), scored by $0.5\rho + 0.3\phi + 0.2\iota$ (relevance, recency, importance), diversified by maximal-marginal-relevance \cite{carbonell1998mmr} ($\lambda{=}0.7$), and injected in three layers under an explicit 500-token budget; compaction triggers at 70\,\% of the context window.

\subsection{The Governed Bridge}
The bridge is where the integration claim becomes concrete: a commissioning engineer binds plant nodes to agents (a single agent or a whole team), the platform injects physical semantics into the bound agents' context, and the bound agents' tool surface is derived from the binding---there is no separate integration layer to build or maintain. A bound node yields a \emph{semantic card} in the agent's context: physical quantity, unit and display precision, the \emph{hard interlock} range, the \emph{soft interlock} recipe window, warn band, live value with freshness, and an operating rule limiting any single step to 2\,\% of span. Bindings carry an operating mode: \emph{manual} (every agent write is approval-gated), \emph{auto} (writes proceed under the interlock and backstop), or \emph{unbound} (no write path); a team's members can share one node set, so a lead-dispatched task and a worker's actuation share one authorization scope. Agents never see register addresses.

Agents act through a host-tool surface of 48 tools, 23 of them industrial or automated-ML (the MCP server exposes a 25-tool subset): setpoint control (\texttt{dcw\_control}), reading, frame retrieval, judgment, rollback execution, audit views, and recipe editing under approval. Two separations are enforced architecturally: \emph{judgment is not execution}---\texttt{dcw\_judge} records a keep/rollback/uncertain verdict but cannot actuate---and \emph{lead-only tools} are restricted to lead agents with approval. Sec.~IV formalizes the single write path.

\subsection{Digital Twin and Node-Binding Rendering}
Rendering binding is part of the integration model, not a visualization afterthought. A \emph{device-twin registry} persists, per scene entity, the bound 3D asset (\texttt{modelRef}), the agent in charge (\texttt{boundAgentId}---a virtual operator avatar acting through MCP \texttt{device.*} tools), an entity kind (device, environment, asset, or procedural sensor mesh), and the three state planes of the twin contract (the device-shadow pattern \cite{ditto2024}): \emph{telemetry} (live fields from acquisition or simulation), \emph{desired} (the agent's intent), and \emph{state} (the reconciled value), plus the command set. A WebSocket event bus broadcasts device lifecycle events and every acquisition reading, so the scene re-renders live values without polling; conversely, scene edits write transforms back to the node registry, so the scene doubles as a commissioning editor while never becoming a source of actuation: \emph{desired}-to-\emph{state} reconciliation itself traverses the governed write path when it actuates (Sec.~IV).

\subsection{Production-Line Management}
The framework models a production line as a four-level object tree---line, product, recipe, \emph{run}---because every governance object of Sec.~IV hangs off it: the recipe window constrains writes jointly with the hard range while a run is active (Eq.~\eqref{eq:constraint}), acquisition samples only nodes whose line has an active batch (between batches, PLC-side protection persists per P2), and the backstop scores open records against the run's monitoring window. The recipe lifecycle is versioned and non-destructive: editing creates version $n{+}1$; marking the active run \emph{known-good} freezes the rollback baseline; reverting to an earlier version creates a new version rather than rewriting history; \emph{known-good rollback} re-dispatches the frozen parameter set to the PLC; and one-click \emph{apply} opens a fresh batch. An active run therefore binds exactly one recipe version to one batch, giving every write a unique governance context---the window $W_r(p)$ of Eq.~\eqref{eq:constraint}---and giving every alarm, journal anchor, and backstop evaluation an unambiguous owner. The lifecycle has two bounded exits from an off-window excursion: automatic rollback while the per-node chain counter is below $K{=}2$, and mandatory human escalation afterwards. Every operation lands in a central audit log with typed actor attribution (user, agent via channel/member badge, system) and line/product/recipe dimensions; write operations are additionally anchored in a signed journal with previous/new values, source, approval, and record identifiers---the substrate for the per-write attribution metric of \bench{} (Sec.~\ref{sec:bench}) and the forensic queries used in the case study (Sec.~\ref{sec:case}).
