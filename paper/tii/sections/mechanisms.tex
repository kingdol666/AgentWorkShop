\section{Core Mechanisms}
\label{sec:mech}
A supervisory intervention passes through three decisions: whether the
request may execute, what the device reports, and how the resulting process
response should be judged. The platform represents these decisions separately
so that neither a completed team task nor an accepted command stands in for
process success. Fig.~\ref{fig:chanloop} summarizes this sequence; the operator console
exposes its commissioning, approval, and audit objects.

\subsection{Optimization Objective and Search Space}
\label{sec:objective}
The supervisory task is to adjust recipe parameters toward a product
objective under configured operating constraints. The strategy chooses the
next proposal and its stopping rule; the platform governs execution and
retains the evidence needed to inspect each iteration.

\emph{Decision variables.} The decision variables are recipe parameters bound to a line's control
nodes, such as screw speed, line speed, and zone temperatures for cast film.
A parameter is written in engineering units and resolved to a register only
inside the controller (Sec.~\ref{sec:nodeexec}), so a proposal carries
physical meaning rather than an address. A commissioned node defines the
quantity, units, calibration, limits, and line membership; protocol
differences remain inside its driver. Member--node bindings, not channel
access or protocol connectivity, grant agent-tool authority; they name
deployed member instances rather than templates. Newly instantiated members
do not inherit existing bindings; the bindings themselves remain
administratively mutable.

\emph{Objective and feasible set.} A strategy defines its product objective and process constraints using
acquisition data and engineering quantities. The team mission targets a film
thickness band; the fixed-controller experiment combines thickness, defects,
and setpoint-based energy and throughput proxies, subject to temperature and
pressure constraints (Sec.~\ref{sec:clbench}). Process effects require
observations rather than write acknowledgments; freshness is exposed, but
observation-quality gating is not enforced. The admissible setpoint interval
is the intersection of the node's hard range, active recipe window, and
applicable product or baseline limits (Sec.~\ref{sec:writepath}). This
interval constrains proposals; satisfying it neither certifies process
feasibility nor discovers a new recipe window.

\emph{Iteration and termination.} A hypothesis record links a proposal and
write to an observation window and a submitted judgment. The supervisory
strategy may stop at its acceptance band, on a favorable judgment, or at its
write budget; these are policy decisions, not proofs of convergence.

\subsection{The Agent Channel and Operator Surfaces}
\label{sec:channel}
Channels route tasks among deployed members and retain messages and
rationale. Task completion neither grants authority nor proves device
execution. Industrial tools resolve the invoking member's bindings for
writes, judgments, and rollback; channel access and retrieved memory are not
authorization. The scripted \texttt{agent-param-tools} check tests binding
denial on the parameter layer (Sec.~\ref{sec:port}).

\subsection{Node Control Execution and the Parameter Layer}
\label{sec:nodeexec}
\label{sec:writepath}
\label{sec:paramlayer}
The parameter layer resolves semantic keys and units to control nodes and
optional baseline limits, with active-product and recipe limits resolved
dynamically, so agent operations need no register address, data type, or
driver configuration. The semantic card supplies the engineering
context---quantity, unit, precision, range, current value, freshness, and
available recipe information---and its suggested step size is advisory, not
an admission rule. Acquisition runtimes track due times and in-flight samples
under a rotating gateway sweep, providing supervisory rather than hard
real-time sampling.

For an ordinary agent setpoint request, the allowed value lies in
\begin{equation}
\mathcal{I}_n(t)=\mathcal{H}_n\cap\mathcal{B}_n
                 \cap\mathcal{P}_n(t)\cap\mathcal{R}_n(t),
\label{eq:admission}
\end{equation}
where $\mathcal{H}_n$ is the node engineering range and the other intervals
are applicable parameter-baseline, active-product, and active-recipe limits.
An absent optional limit adds no restriction. This notation describes the
implemented interval checks, not a model of plant feasibility. Entry routes differ: recipe dispatch supplies a run identifier and omits
the recipe-window layer, while hold heartbeats bypass controller admission
but share runtime write exclusion.
Agent-origin ownership and directional cooldown checks are not universal
guards. Line start installs an active run before dispatching recipe
parameters individually. Stop clears that context, prevents subsequent
acquisition dispatch, closes up to 500 open optimization records, and
requests acquisition-offline status; it does not cancel in-flight samples,
stop an already-running recipe dispatch, or block all control writes. Run
tags are resolved at ingestion, so this command is supervisory batch
management, not a PLC emergency stop.

Calibration maps engineering setpoints into the driver domain and available
readback into physical units. Modbus and OPC UA drivers check readback using
\begin{equation}
\tau_n=\max\!\left(0.5\cdot 10^{-d_n},\;0.005(u_n-l_n)\right),
\qquad |v_{\rm rb}-v|\leq\tau_n,
\label{eq:tolerance}
\end{equation}
where $[l_n,u_n]$ is the node range and $d_n$ its display precision. For a
nonzero linear calibration scale $a$, the driver receives $\tau_n/|a|$.
Driver success is protocol-dependent: HTTP accepts a successful response
without tolerance-checking an optional returned value, whereas MQTT
publication supplies no readback. Only a validated readback supports setpoint
agreement; neither that agreement nor request acceptance establishes process
success. A failed readback can follow an already executed write; it does
not establish that the device was left unchanged.

Agent setpoint tools resolve bindings and obtain any required approval before
controller admission, rechecking binding existence after approval. Admission
checks pause and disable state, applicable ownership and directional
cooldown, and the limits above; the runtime then handles write exclusion,
connection, write, and readback. REST, recipe, and recovery routes have
distinct entry authorization. Asynchronous connection and protocol queues
prevent check--act atomicity against recipe changes, and write bookkeeping
can fail without reversing device execution, so attribution is not an atomic
commitment across storage and the device.

\subsection{Agent Closed-Loop Control}
\label{sec:loop}
An intervention connects observation, proposal, execution, judgment, and
possible compensation. The agent may attach an
expected effect to its request, but the hypothesis field is optional. After
driver-reported success, bookkeeping attempts to retain a change anchor.
Agent- and rollback-origin writes can additionally open an optimization
record with asynchronous baseline statistics; manual and recipe writes do
not. The evidence associates a change with later observations; it is neither
a causal experiment nor a guarantee that every accepted write was captured.

\emph{Recording and coordination.} The five-second same-target rule
suppresses bookkeeping, not the physical command: the driver has already executed when the latest node anchor is
checked. Otherwise, the node's previous open record is closed before
unchanged-value suppression; an unchanged command can therefore close a
record without replacing it. Ownership is node-scoped: an agent-origin write
can be blocked by another agent's non-stale open record. Directional cooldown
restricts immediate movement away from a recently restored value; it does not
exclude all manual, recipe, or system interventions. Defaults are a 600-s
baseline lookback, a 300-s cooldown, and a 30-min stale-record interval. A
missing prior value or a bookkeeping failure can leave recovery or
attribution incomplete even when the driver accepted the request.

\emph{Judgment.} The judgment tool records the agent's reading of that comparison; it does not
establish process success. An invocation of \texttt{dcw\_judge} supplies a
record identifier, verdict, and reason. A \emph{keep} closes the record; for
non-takeover judgments it also attempts to mark the currently active run as
good, which is bookkeeping status rather than a certified snapshot of the
operating point. \emph{Rollback} and \emph{uncertain} leave the record open.
Setpoint restoration requires a separate rollback operation, and the
strategy, not this status alone, decides whether to stop.

\emph{Rule-based backstop.} While the control gateway is running, its sweep
schedules asynchronous checks
of open records whose stored policy is not observe-only, by default no
earlier than 120 s after the record is set and no more often than every 30 s.
The manager prefers acquisition streams sharing the control node's
primary-device alias, falling back to the line. It queries from the record's
set time to now and sums out-of-window returned points or bucket averages
across channels; a total of at least $b=3$ triggers a rollback judgment.
These need not be consecutive points, and $b$ counts neither evaluator
invocations nor raw sensor samples. Automatic recovery is attempted only
while fewer than $K=2$ retained records for the node have status
\texttt{rolled-back}; the count spans retained history, not the current run,
and does not bound every rollback route. At the threshold, or under an
approval-required policy, the backstop records escalation rather than
writing. Query aggregation, asynchronous execution, and later record-state
changes prevent these rules from establishing a worst-case recovery deadline
or cancelling already-pending recovery.

\subsection{Recipe Management and Physical Rollback}
\label{sec:recipe}
Recipe history preserves intended operation, not achieved device state.
Versioned edits and known-good snapshots retain parameter sets and
provenance, but reverting a definition creates a version with restored
metadata without restoring PLC values. Applying a recipe creates a run and
dispatches parameters; starting a line also installs the active context, so
definition, run metadata, and physical parameters need not agree
transactionally. Physical rollback issues a new, rejectable write to a
recorded baseline or anchor-derived target; the run-related route uses the
previous value of the last retained pre-start changed anchor, which need not
be the actual setpoint at run start. The rollback operation closes an originally open record before dispatch,
marks it \texttt{rolled-back} on success, and may open a new record for the
compensating write. A failed restoration does not reopen the original for
sweep-based retry. Across nodes, compensation can partially succeed and
cannot erase intermediate process states; restoring metadata, restoring a
setpoint, and recovering the process are distinct outcomes.

\subsection{Human-in-the-Loop Control}
\label{sec:hitl}
Manual bindings add a timed approval wait to agent setpoint and physical
rollback requests; auto bindings omit the wait but retain applicable execution checks.
Reads, verdict recording, and bound-node recipe-window editing do not
require this physical-write approval. Setpoint requests
show the member, node, requested value, request-time effective interval, and
remaining time; rollback requests describe the target record or anchor.
Approval reserves neither limits nor device state: binding existence and
controller admission are checked again before execution. Expiry prevents
execution and is recorded separately from refusal; duplicate pending requests
for the same agent and node are suppressed, and unbinding can cancel
outstanding requests. The decision endpoint authenticates a user but does
not enforce a line- or owner-scoped approver role. Existing optimization
records retain their creation-time recovery policy; changing a binding to
manual does not retroactively change that policy. Tool approval differs from an optimization record
awaiting human action: escalation does not execute recovery, and neither path
covers an absent operator when $K=2$ is reached. External engines still need
deployment-level privilege and network restrictions: bindings govern
sanctioned tool calls, not arbitrary I/O by a compromised process.
