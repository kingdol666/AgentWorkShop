\label{sec:mech}

The six core mechanisms below are node connection and creation (Section~\ref{sec:nodes}), the agent channel (Section~\ref{sec:channel}), node control execution (Section~\ref{sec:writepath}), production-line operations (Section~\ref{sec:lineops}), agent closed-loop control (Section~\ref{sec:loop}), and recipe management and rollback (Section~\ref{sec:recipe}), together with the cross-cutting HITL boundary (Section~\ref{sec:hitl}). Fig.~\ref{fig:teamloop} introduces their organizational setting; Section~\ref{sec:loop} details the feedback mechanism rather than equating the channel loop with process control. The evidence suites are matched to mechanisms as follows: out-of-bound write probes exercise the hard-range and recipe-window checks; lifecycle probes and the team mission exercise rollback and approval, with ownership and cooldown checks traversed by every governed agent write (Secs.~\ref{sec:port}, \ref{sec:e1a}, and \ref{sec:agentloop}); the probes are fixed protocol cases, not LLM-generated adversarial inputs, consistent with the evidence boundary of Sec.~\ref{sec:repro}.

\subsection{Node Connection and Creation}
\label{sec:nodes}
A node separates the meaning of an industrial variable from its transport address; commissioning associates device integration information with acquisition or control configuration, tests connectivity, and supplies units, calibration, limits, and production-line membership. Drivers support Modbus TCP, Modbus RTU over TCP, OPC UA \cite{iec62541}, MQTT, and HTTP/REST, plus a mock implementation for testing. Device associations are many-to-many metadata, not a write fan-out across connections.

Creation also differs from authorization to operate: operator APIs and agent-facing creation paths have different permission conditions, and industrial-tool bindings refer to concrete channel-member instances, not reusable templates, so deploying a template elsewhere does not transfer a binding---membership alone is not write permission.

The semantic card presents the node's physical quantity, unit, precision, range, current value, freshness, and available recipe context. The recommendation to change a setpoint by at most 2\,\% of its span is prompt guidance, not a controller-enforced step limit. Per-node acquisition runtimes manage due times and in-flight sampling; a rotating gateway sweep apportions that work across intervals. This scheduling supports supervisory observation, not hard real-time sampling.

\subsection{The Agent Channel: Team, Supervision, and Memory}
\label{sec:channel}
A channel contains a lead, worker instances, a task tree, and message history; routing resolves recipients within the channel, loads runtimes when necessary, and delivers messages through mailboxes or supported steering interfaces. The task tree distinguishes submitted through completed work; these states describe collaboration progress, not device execution: task completion is neither permission to write nor evidence of physical intervention.

The scheduler combines periodic supervision with event wake-up and idle backoff, summarizing tasks, queues, member activity, and recent messages. Deterministic rules handle dispatch, retry, and stalled work, with recent tool activity contributing to liveness detection; scheduler progress cannot resolve uncertainty about a plant response, which requires observations and an explicit judgment.

Engine adapters support interchangeable reasoning implementations, including process-external engines. Channel memory preserves task experience, reflections, and reusable knowledge for later retrieval; its function is informational continuity, so a later worker recovers earlier rationale and outcomes rather than inferring them from a current setpoint alone. Retrieved memories remain contextual evidence, not an authorization mechanism or executable safety specification; industrial tools still resolve the invoking member's bindings at request time.

\subsection{Node Control Execution}
\label{sec:writepath}
The execution path separates an authorized request from a verified device result: an ordinary agent setpoint request resolves a control-node binding and, in manual mode, waits for approval. The controller rejects requests when its gateway or the node is paused, and agent-origin requests additionally encounter optimization ownership and directional cooldown checks. The node runtime validates the engineering range and blocks overlapping writes before protocol execution.

Let $S_n=[l_n,u_n]$ be the node range, $r$ the recipe identifier ($r\neq\varnothing$ when the request carries an active recipe context), $W_{r,n}$ the parameter window that recipe $r$ prescribes for node $n$, $q$ the optional recipe-run identifier supplied with a request, and $P_r$ the nodes with a parameter in that recipe. The effective numerical constraint at controller entry is
\begin{equation}
C(n,r,q)=
\begin{cases}
S_n\cap W_{r,n}, & r\neq\varnothing,\ q=\varnothing,\ n\in P_r,\\
S_n, & \text{otherwise}.
\end{cases}
\label{eq:constraint}
\end{equation}
An unspecified window endpoint is unbounded. This formula describes normal controller requests, not every low-level executor invocation: recipe application supplies $q$, bypassing the active-window branch. Hold heartbeats share write exclusion but call the executor directly, without re-entering all controller checks; configuring them is an operator-level operation outside the agent tool surface. Ownership and cooldown checks likewise depend on source metadata, not universal application.

Calibration maps engineering values to the device domain and readback into physical units. The runtime's tolerance is
\begin{equation}
\tau_n=\max\!\left(0.5\cdot 10^{-d_n},\;0.005(u_n-l_n)\right),
\qquad |v_{\rm rb}-v|\leq\tau_n,
\label{eq:tolerance}
\end{equation}
where $d_n$ is display precision. For linear calibration, the executor converts this tolerance to the absolute scale before comparison. A successful readback supports agreement with the commanded value, not proof that the process reached its desired operating condition, so communication failure or readback mismatch stays distinct from process-effect judgment. If a driver provides no readback, displaying the commanded value as a fallback does not establish measured agreement.

\begin{algorithm}[!t]
\caption{Ordinary bound-agent setpoint request}
\label{alg:write}
\begin{algorithmic}[1]
\Require Member $a$, node $n$, engineering target $v$
\State $b\gets\textsc{FindBinding}(a,n)$; reject if absent
\If{$b.\mathrm{mode}=\mathrm{manual}$}
  \State Await approval; reject on denial or timeout
  \State Recheck binding; reject if removed
\EndIf
\State Reject if gateway paused or node disabled
\State Check agent ownership and directional cooldown
\State Reject if $v\notin C(n,r,\varnothing)$
\State Validate range; acquire node write exclusion
\State Await connection, protocol write, and readback
\State Release exclusion; preserve execution outcome
\If{execution reports success}
  \State Attempt anchor, record, and operations bookkeeping
\EndIf
\State \Return execution result and available record identifiers
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:write} summarizes this ingress; asynchronous connection and protocol queuing separate checks from device action, so neither co-residency nor node write exclusion supplies check--act atomicity against changing recipe state. Successful writes trigger journal anchors and, for relevant sources, optimization records; bookkeeping errors are caught without reversing the write result, so attribution is traceability, not an atomic commitment spanning storage and the PLC.

\subsection{Production-Line Operations Management}
\label{sec:lineops}
Line operations associate products, recipes, and runs with the nodes that generate measurements or accept setpoints; the run gives a batch identity for historical interpretation, so a temperature observed under one product's recipe should not become evidence about another product's operating window.

Starting a line validates its recipe and product, creates a run, and installs it as active before writing its parameters individually; an active run is not a certificate that all parameters applied successfully, and individual outcomes must be examined, especially when communication fails partway through initialization. Acquisition is gated by active batches, so opening a run establishes the context in which its line's measurements are collected; stopping the line clears it, closes up to 500 open optimization records through the current stop hook---closure beyond that limit is not guaranteed---and requests acquisition-offline status, a supervisory batch operation rather than a PLC emergency stop.

Monitoring combines live values, node conditions, alarms, and events with historical measurements and frames, so responses can be inspected over time, not only as single values. The device-twin scene renders these states without issuing protocol commands, though controls in the Town operator web interface can submit API writes; neither the scene nor a stopped batch is a physical safety barrier, and between batches the run gate limits acquisition while plant-side protection remains independent.

\subsection{Agent Closed-Loop Control}
\label{sec:loop}
The feedback sequence is observation, hypothesis, intervention, judgment, and retention or recovery: the agent inspects bound-node context and acquisition history, states an expected effect, and proposes an engineering setpoint. After a successful value-changing write, the rollback manager creates an anchor and an optimization record containing the node, actor, hypothesis, parameter change, and applicable policy, with baseline statistics filled asynchronously from preceding observations. After a five-second same-target deduplication check, a subsequent successful write supersedes the node's open record; an unchanged-value write creates no replacement anchor or record, while a value-changing agent or rollback write starts a new observation record. This is node-scoped bookkeeping, not one experiment per agent across the plant.

Before an agent write, an open record belonging to another agent blocks entry unless it has become stale and is superseded, and a recent rollback prevents an agent from immediately moving in the same direction away from the restored value. These source-specific checks reduce conflicting interventions but do not exclude manual or recipe-origin writes. Defaults include a 600\,s baseline lookback, a 300\,s cooldown, and a 30\,min stale-record interval.

The agent then invokes \texttt{dcw\_judge} with a record identifier, verdict, and reason. The tool validates and records the supplied conclusion without calculating it from telemetry; a \emph{keep}, \emph{rollback}, or \emph{uncertain} judgment is therefore attributable reasoning, not an independently established process result. A keep judgment closes the record and can mark a good state, whereas rollback and uncertain judgments leave it open; restoring a setpoint requires a separate rollback operation, and uncertainty must not be read as successful optimization.

An independent backstop periodically evaluates eligible open records, waiting at least 120\,s by default and rechecking every 30\,s. Acquisition channels matching the control node's primary-device alias are preferred, with selection otherwise falling back to the line; historical query results are compared with configured acquisition monitoring windows, and at least three accumulated breaches trigger a rollback judgment. The queried observations, aggregation, and data availability constrain this evidence; the intervals alone prove no worst-case physical recovery deadline.

For an automatic-rollback policy, the backstop executes recovery only when the node's count of records marked \texttt{rolled-back} is below $K=2$. The count spans retained records for that node---not merely the current run---and includes rollbacks irrespective of initiator; nor is $K$ a universal limit on every explicit rollback route. At the threshold, or under an approval-required policy, it records an escalation instead of writing---a bound on the implemented backstop decision, not globally bounded agent behavior.

\subsection{Recipe Management and Rollback}
\label{sec:recipe}
Recipe management separates the definition of intended operation from the device state actually achieved: versioned edits and known-good snapshots preserve candidate parameter sets and their provenance, and reverting a definition creates a new version with restored metadata but does not by itself restore PLC values. Recipe application instead creates a run record and dispatches its parameters, while line start additionally establishes the active line context---operations not to be conflated. During dispatch, deleted or disabled nodes---and nodes no longer attached to the recipe's line---produce explicit unsuccessful outcomes while other parameters continue; the run keeps partial application distinguishable from complete application.

The ordinary active-window check resolves the recipe through the active run's recipe identifier and is not an atomic check against every frozen run field; application passes its run identifier into controller writes, skips that window branch, and retains runtime range validation. Version history documents intent but establishes no transactional consistency among edited definition, run metadata, and physical parameters.

Physical rollback selects a recorded baseline, anchor, batch-start, or known-good target and issues a new write, which the controller can reject; a rollback verdict therefore does not guarantee restoration. Across multiple nodes, recovery is compensating work---one restoration may succeed while another fails, and no distributed physical transaction erases intermediate process states---so operators must distinguish restored recipe metadata, successful individual compensation, and verified recovery of the production process.

\subsection{Human-in-the-Loop Control}
\label{sec:hitl}
Human intervention attaches to concrete bindings and operations: for an ordinary bound-agent control request, \emph{manual} mode suspends execution for approval, while \emph{auto} mode omits that wait but retains applicable controller and runtime checks. An unbound member is rejected, and on resumption after approval the tool verifies that the binding still exists before entering the controller. Approval thus permits a request to proceed; it reserves no device state and guarantees nothing about later checks.

Tool approvals have an explicit expiry timer and resolve as denied when unanswered; duplicate pending requests for the same agent and node are suppressed, and removing a binding can cancel outstanding requests. This timed approval object differs from an optimization record carrying a rollback judgment awaiting human action: a recorded escalation does not mean that recovery has executed.

Human decisions, agent proposals, and system recovery events provide complementary attribution, whose usefulness depends on retaining the distinction between intent, authorization, device outcome, and observed process effect. Four operator-facing surfaces make these distinctions inspectable (Fig.~\ref{fig:workflow}): node commissioning, device association, team deployment, and optimization-record inspection. Process-external engines also require deployment-level privilege and network restrictions: tool bindings govern sanctioned tool calls, not arbitrary I/O by a compromised local process.
