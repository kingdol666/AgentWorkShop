AgentWorkShop: A Modular Task-to-Device Integration Framework for Industrial Agents

Abstract--Deploying industrial agents across production scenes requires scene-specific signal and protocol mappings while keeping task context, device dispatch, and resulting evidence aligned. This paper presents AgentWorkShop, a modular task-to-device integration framework that composes task adapters, production context, named operations, semantic input/output, runtime checks, protocol drivers, and service-owned records. Registered task routes pass through the collaboration runtime; direct operation calls enter the shared dispatcher without creating a task record. The design keeps approval, command readback, and subsequent process observations distinct while linking them to the active production context. We evaluated registered task paths and direct operation calls in cast-film and annealing simulators with different signal and protocol mappings. Six sequential modelmediated task executions and two fixture-backed command-line tasks preserved their route-specific record links; direct calls retained operation, readback, and run-tagged sample records. Every current-route sample remained below its target band. A mock-state approval-context test refused 12 stale changes before writes, whereas an ablation allowed six product/run changes through. A separate v0.8.3 replay of one documented coatingline blueprint passed 23 functional verification checks and confirmed one simulator write. Together, these results demonstrate integration behavior for selected preconfigured paths, one simulated onboarding configuration, and a software dispatch guard. They do not establish process improvement, configuration reuse, general portability, or comparative platform benefit.
Index Terms--Industrial agents, industrial communication, industrial informatics, production systems, semantic data integration.
I. INTRODUCTION
I NDUSTRIAL-AGENT deployments must connect each task to its production context, process signals, and equipment interfaces. Existing work addresses end-to-end automation control, operator-reviewed control-sequence generation, modular factory skills, and production scheduling [1]­[4]. Other studies target programmable logic controller (PLC) code generation, context-aware control, resource capability discovery, shop-floor coordination, digital-twin fault handling, natural-language machine access, and robotic-line control [5]­ [10]. Across production lines, agent roles, signal maps, protocols, objectives, and product/run context vary. An integration architecture must accommodate these differences around shared task and operation services while keeping each action tied to its active production context. Recent industrial-agent architectures add Asset Administration Shell (AAS)-grounded OPC Unified Architecture (OPC UA) actions with signed approval, process and instrumentation diagram (P&ID)-grounded proposal checks, and governed sensor­manufacturing execution system (MES)­enterprise resource planning (ERP) evidence streams [11]­[13]. These works address asset-specific execution, process validation, or closed-loop analytics. At their software-integration boundary, this paper examines a specific

implementation requirement: task routes and direct tool callers should invoke one shared named operation handler while retaining evidence appropriate to each route. Task routes can link task, approval, command receipt, and process observation; a direct call has operation records but no task edge. The contribution concerns the implementation and evaluation of this contract; equivalent behavior may also exist in prior platforms.
Consider two production scenes with different process signals and interfaces: cast-film thickness control and annealingzone temperature control. An agent task in either scene needs production context, typed signal access, and a route from a named operation to the configured device protocol. The framework must also distinguish a command receipt from a subsequent process observation. The shared task and operation services can therefore be configured with scene-specific signal maps, protocols, and limits while retaining a common execution path. The evaluation examines this path in two simulator scenes and replays a documented coating-line onboarding workflow.
This paper presents AgentWorkShop as a modular framework for task-to-device integration in industrial agents. It connects collaborative tasks through a registered harness interface to production context, MES data, analysis and modeling services, data-acquisition (DAQ) and DCW write-control nodes, and protocol-specific drivers. Its interfaces include commandline, web, software development kit (SDK), Representational State Transfer (REST), Model Context Protocol (MCP), and Agent-to-Agent (A2A) surfaces. Task and chat routes enter the collaboration runtime, whereas a direct REST tool-invocation route can call the shared operation dispatcher without creating a task.
Scene blueprints define signal maps, objectives, and guards; channel profiles, tool policies, and agent bindings scope operations. Agents and callers invoke named operations through shared runtime checks; the framework does not choose routes autonomously and retains proposals, command confirmation, and process observations as distinct records. A. Industrial Agents and Plant Integration
Industrial-agent systems, including large language model (LLM)-based systems, span end-to-end automation control, supervisory services, programmable logic controller (PLC) interfaces, manufacturing coordination, and operator-facing machine access. Xia et al. present an LLM agent framework for end-to-end industrial automation control, using structured prompts and event-driven context for production planning and operation [1]. Huang et al. present a multimodal architecture whose stated focus is automated control generation for industrial cyber-physical systems [2]. Biskupovic et al. study agentbased supervision for service-oriented industrial systems [14];

Agents4PLC and InstructMPC address PLC code generation and human­LLM context-aware control, respectively [5], [6]. Manufacturing studies consider dynamic resource-capability exploration [7], multi-agent shop-floor coordination [8], and digital-twin-supported fault handling [9]. Natural-language machine access [10] and real-time LLM control of a robotoperated serial line [4] extend this work to operator interfaces and robotic-line control. Together, these studies address different operational contexts, interfaces, and allocations of responsibility between agents, operators, and controllers.
The closest architecture-level comparison is Xia et al., who connect cognitive, digital-twin, and physical-automation layers and organize twin information as state snapshots, event messages, and plan sequences [15]. Other nearby designs expose factory-module operations through MCP with state-based tool filtering, constrain manufacturing plans, or compose semantic recipes from OPC UA skills [3], [16], [17]. Several recent systems also combine agent execution with approval, industrial data, or audit records. Graul et al. ground proposals in the Asset Administration Shell (AAS) and route approved actions through OPC UA Methods, with signed approvals and audit logging [11]. Schall separates advisory language-model agents from process and instrumentation diagram (P&ID)-grounded verification and execution, and evaluates structural checks across five simulated process scenarios [12]; its context includes supervisory control and data acquisition (SCADA) and standard operating procedure (SOP) information. Lin and Chen build a governed sensor­MES­ERP digital thread for closedloop monitoring and control on real manufacturing records [13]. These works address asset-specific approval, process validation, or closed-loop analytics. The complementary question here is whether a modular task-to-device implementation can route registered-harness and command-line task paths and a direct caller through a shared named handler while preserving the records applicable to each route; its approved recipe path also rechecks the line­product­recipe­run tuple before software dispatch. The route study examines two preconfigured simulator mappings, and a separate blueprint replay checks one documented coating-line onboarding workflow through the existing interfaces. III. SYSTEM DESIGN
AgentWorkShop is designed for industrial tasks whose agents, production contexts, interfaces, and process signals vary between deployments. Its architecture organizes these variations around shared task and operation services, checks each proposed operation against the active production context before device routing, and retains route-specific evidence that distinguishes a command receipt from a measured process response.
A. Design Rationale and Requirements
Five requirements--scene variability, harness variability, operation authority, outcome observability, and extensibility-- organize six design rules (D1­D6). These are deployment constraints drawn from the target workflows. D1 stores scene settings as versioned data; D2 provides registered harness, tool, and driver interfaces; D3 separates proposal from execution; D4 treats the tool catalog as discovery rather than permission; D5 routes actuator writes through the common DCW admission point; and D6 retains evidence by operation.
The requirements trace to implementation as follows. Scene variability maps to D1, scene blueprints, and context resolution; harness variability and extensibility map to D2, the registered harness and driver interfaces; operation authority maps

to D3­D5, the shared dispatcher, grants, bindings, and write admission; outcome observability maps to D6, route-specific receipts, and observations. These interfaces are design extension points; Section V tests selected task and direct-operation routes and one documented blueprint-onboarding workflow. AgentWorkShop supplies task and operation services; agent strategy and independent process protection remain outside this design.
B. Layered Architecture
Fig. 1 summarizes the access routes, shared dispatch path, production services, semantic I/O, configured drivers, and service ownership of records. Task and chat routes enter the collaboration band, which contains workspaces, channels, task queues, shared memory, mailboxes, task templates, and harness adapters. A task route is an execution path through this runtime; a harness adapter connects an agent engine to its task execution interface. Direct REST tool calls and the stdio MCP operation bridge bypass task execution in that band (the upper-right direct-operation entry in Fig. 1) and enter the shared governance block without creating a task or starting a harness turn; MCP management and task methods remain on their service routes. Direct calls resolve current route state at invocation, without an agent-turn prompt or a task record. The governance block projects the operation catalog and applies the per-call checks; write routes add the approval card and the admission interval. IV. MODULE FUNCTIONS AND INTEGRATION
The design in Section III is realized through three cooperating functions: task and context assembly, shared operation dispatch, and controlled device access with route-specific evidence. We follow one agent action through them.
A. Task, Harness, and Context
Task and chat entry points create or join a workspace channel. The task runtime manages membership, task state, and shared execution context; a harness registry adapts each supported agent engine to a common execution interface. At each agent turn, the prompt builder assembles the task, active scene description, production context, channel profile, agent binding, and retrieved memory. This keeps engine-specific interaction behind the harness interface while preserving the current line and operation context for the agent.
Direct REST and selected stdio-MCP operation calls reach the same dispatcher without a task or harness turn. REST authentication and identity resolution follow Section III-C; each handler reads live route state at invocation. Handlers do not branch on the entry route: they receive the resolved actor, channel, and operation arguments, and the records they write are keyed by the identifiers that request supplies. B. Shared Dispatch and Device Admission

The dispatcher is the shared operation boundary. It checks invocation scope and current channel policy, then verifies the agent binding, runtime grant, and ownership of referenced resources before selecting a handler. In the notation of (1), scope and policy apply to every call; grant is skipped only for a grant-exempt tool, and binding applies only when references are declared. Handlers revalidate route-specific state at execution time; a previously displayed tool catalog does not preserve authority after a policy or grant changes. Scene blueprints define device and signal maps, objectives, and process guards. Capability profiles and tool policies narrow available operations, while bindings constrain accessible nodes, controls, and recipes. Optional DAQ, MES, analysis, retrieval, optimization, and digital-twin services are invoked through registered handlers; the framework does not prescribe a single optimization strategy.
Actuator writes converge on the shared DCW write-control admission point. For an online node write, the admissible value interval is

Inonline(t) = Hn  Bn  Pn(t)  Rn(t),

where Hn is the hard engineering range and Bn, Pn, and Rn are the baseline, active-product, and active-recipe limits. Missing optional limits impose no restriction; an empty intersection rejects the request and identifies the excluding layer. Recipe dispatch validates the replacement recipe against the hard, baseline, and product limits rather than the previous recipe window. Step, interval, and hold-window checks also constrain each route. These software checks bound commands but do not replace independent programmable-logic-controller or safety-instrumented protection.

C. Approval, Execution, and Evidence
Routes add timing and approval checks appropriate to their operation. Online node writes enforce a 60 s minimum spacing; recipe trials use a per-line cadence (300 s by default), and recipe intervals are anchored to approval. Manual approval binds an actor and proposed operation to candidate values, applicable limits, expiry, and the active line­product­recipe­run tuple. After approval, the handler rechecks authority and compares the current tuple with the approved tuple before entering DCW dispatch. The default approval wait expires after 180 s. A changed recipe definition requires a new recipe_apply proposal. These checks reject stale requests at the software dispatch boundary; they do not lock equipment state across network or device I/O.
Fig. 4(a) illustrates the four-layer value interval in Eq. (2) using an archived RPM configuration. Panel (b) shows a symbolic approval followed by authority and context rechecks; its values are illustrative, not experimental measurements.
A recipe_trial illustrates the operation sequence: the handler checks the bound recipe, active run, candidate parameters, and route timing; if required, it requests approval; after revalidation, it submits a bounded batch through the configured driver and returns a per-parameter receipt. The caller obtains later DAQ observations separately and may then update, apply,

or roll back a recipe. A trial neither saves nor applies a recipe version. The driver registry maps semantic controls to configured protocol drivers, keeping protocol details out of agent operation arguments.
Receipts and observations answer different questions. A command result is graded as readback-verified, transportacknowledged, or unverified; a readback mismatch can trigger up to three reads at 2 s intervals. Recipe batches retain per-parameter verification outcomes. DAQ stores subsequent timestamped process observations, while recipe versions, approvals, and task records remain service-owned records linked where a route supplies the corresponding identifiers. A verified setpoint confirms the command path, not target attainment. This distinction defines the evidence chain evaluated in Section V.
V. EXPERIMENTAL EVALUATION
The experiments examine four questions: (Q1) whether the tested execution routes retain task, approval, receipt, and sample records across two configured simulator scenes; (Q2) whether one documented blueprint-onboarding workflow completes on a fresh application home; (Q3) whether a stale approval context is rejected before software dispatch; and (Q4) what process samples accompany the tested routes. These outcomes are kept separate. All plant-facing checks used software simulators; none involved a physical plant or independent process replication. Sections V-B to V-D report the current-version outcomes; Section V-E reports the separate historical record. The evidence is complementary and is not pooled into a single score.
A. Test Design and Protocol
For a registered task, the integration criterion is a task linked to its approval, readback-verified receipt, and a runtagged sample. A direct call has no task edge; its criterion is a verified receipt/readback and a run-tagged sample. The fixed-call replay checks record links, not task completion; the context guard is assessed by whether a changed line, product, recipe, or run is refused before a driver write.
The route-continuity study exercised four entry paths on the v0.8.0 application: registered-harness tasks, a fixed-call harness replay, direct REST, and a fixture-backed commandline task. Two simulator scenes covered cast film (screw speed over OPC UA; thickness over MQTT; target 48­52 µm) and continuous annealing (zone-3 setpoint over Modbus TCP; strip temperature; target 700­760 C). The registered-harness path ran three sequential tasks per scene on one persistent simulator; each task used its own production and task context, while process state carried forward. After each verified receipt, the runner waited 20 s, probed and ingested one sample, queried it by active-run ID, and then checked task state; the task-completion-to-sample latency is consequently unavailable. The fixed-call replay, direct REST call, and fixturebacked command-line task ran once per scene in separate isolated environments.

The ablation isolates the tuple comparison within the tested software state. It does not demonstrate atomicity during network or device I/O, safe physical operation, operator effectiveness, or end-to-end DAQ integrity.

VI. DISCUSSION
This section interprets the results against the design contract and then states what the evidence does not cover.
A. Interpretation
AgentWorkShop composes collaborative-task services, production context, named operations, semantic signal access, configured device drivers, and service-owned records into a shared task-to-device path. The current experiments trace this design through task or direct-operation entry, approval-bound dispatch, readback receipt, and a later run-tagged process sample. Registered task routes preserve the task, approval, receipt, and sample associations; direct REST preserves operation, readback, and sample records without a task edge. The two simulator scenes use different signal and protocol mappings, so the observed joins support the tested composition and routespecific record contract.
The v0.8.3 onboarding replay answers a different question from the route runs: it exercises protocol access, heterogeneous MES data, channel construction, acquisition, and an approved write inside one workflow, which single operation calls cannot show. Because the workflow was not repeated under a changed profile or binding set, it supports workflow execution for the documented blueprint while leaving configuration reuse open. A replay with a pinned revision and a changed binding set would separate those two readings.
The process results bound the interpretation of that evidence. Cast-film samples range from 45.69 to 46.69 µm, or 1.31­2.31 µm below the 48 µm lower bound. Annealing samples range from 674.40 to 679.60 C, or 20.40­25.60 C below the 700 C lower bound. These measurements are single snapshots taken 20 s after an operation, so they cannot establish a response curve, convergence, or the cause of the observed shortfall.
Fig. 5 pairs requested setpoint changes with the resulting observations in four archived seed-42 missions. Their terminal readings lie inside their own windows, but each panel is one historical scripted direct-node trajectory; the figure explains those action­response records and does not establish attainment by current routes or repeatability.
This gap between command evidence and process evidence is central to the framework's execution model. A verified readback confirms that the requested setpoint reached the configured device; it does not show that the process variable entered its target band. A task can therefore complete its approved operation path while its associated process sample

remains out of band. Keeping the receipt and run-tagged sample as separate, linked records lets the system report both facts without treating command completion as product attainment. The current results validate this distinction in the tested software paths, not an improvement in control quality.
The route evidence depends on each entry contract. The fixture replay, direct REST, and command-line (CLI) checks ran in separate isolated environments, and the model-mediated triplets shared a persistent simulator per scene. These pathspecific contexts and unequal sample counts mean their numerical similarity is not evidence of route equivalence. All route-study runs used the SQLite fallback because MQTT and Timescale were unavailable; the separate C01 onboarding replay exercised online MQTT/Timescale on isolated services. The results support the specified record contracts under two configured signal and protocol mappings and feasibility of one blueprint-driven simulated onboarding workflow.
The context-guard test identifies the software check's contribution under mock state: comparing the approved line­ product­recipe­run tuple blocked product/run mutations that the retained checks alone did not reject. This supports a bounded claim about software dispatch. It does not show atomicity across network or device I/O, safe physical operation, or operator effectiveness. Synthetic approval also does not measure human review performance [25]­[27].
B. Scope and Limitations
Only the reported adapter and scene configurations were exercised. The single C01 replay does not test repeatable onboarding, profile or binding reuse across lines, arbitrary unseen-scene configuration, or physical transfer, and it ran on a working-tree build whose source commit was not pinned. The evaluation also does not establish general adapter interchangeability, normal online DAQ operation in the route trials, or a platform baseline. The feature-level comparison positions the implementation question; it does not show that AgentWorkShop is more efficient or more capable than another platform. A comparative study would need a shared task set, explicit integration-effort or record-completeness measures, and matched deployments.
The route study used one simulator instance per scene, three sequential model-mediated trials per scene, and one post-trial process sample per trial. These samples are not independent replicates and cannot establish a process response curve. Follow-up evaluation should vary configuration profiles under a controlled onboarding protocol, use repeated process trials, report pre-task and post-trial process values so that command effects are separated from carried-over state, and compare against a defined alternative integration path. Operation restrictions do not establish security [28]­[30] or replace independent PLC/safety-instrumented system (SIS) safeguards [31].
Scope and channel-policy refusals are not uniformly persisted; auditability is limited to the records and denial classes described in Section IV.

VII. CONCLUSION
AgentWorkShop brings task adapters, production context, named operations, semantic I/O, configured protocol drivers, and service-owned records into a modular task-to-device framework. Tested task routes and direct calls used a shared operation boundary across cast-film and annealing simulator mappings while preserving route-specific records. A separate v0.8.3 replay completed one documented coating-line onboarding configuration with online DAQ checks and a simulator-confirmed smoke write. Route-study samples remained below target, and a mock-state ablation isolated the effect of an approval-bound context check. The study establishes selected integration, one simulated onboarding instance, and software-contract behavior; it does not establish process improvement, configuration reuse, physical transfer, general portability, or comparative platform benefit.
