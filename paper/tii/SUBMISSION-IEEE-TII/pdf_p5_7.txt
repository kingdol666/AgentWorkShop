IV. MODULE FUNCTIONS AND INTEGRATION
The design in Section III is realized through three cooper-
ating functions: task and context assembly, shared operation
dispatch, and controlled device access with route-specific
evidence. We follow one agent action through them.
A. Task, Harness, and Context
Task and chat entry points create or join a workspace
channel. The task runtime manages membership, task state,
and shared execution context; a harness registry adapts each
supported agent engine to a common execution interface. At
each agent turn, the prompt builder assembles the task, active
scene description, production context, channel profile, agent
binding, and retrieved memory. This keeps engine-specific
interaction behind the harness interface while preserving the
current line and operation context for the agent.
Direct REST and selected stdio-MCP operation calls reach
the same dispatcher without a task or harness turn. REST
authentication and identity resolution follow Section III-C;
each handler reads live route state at invocation. For either
entry path, prompt context and tool-catalog visibility describe
available information and capabilities; neither grants write
authority.

C. Approval, Execution, and Evidence
Routes add timing and approval checks appropriate to their
operation. Online node writes enforce a 60 s minimum spacing;
recipe trials use a per-line cadence (300 s by default), and
recipe intervals are anchored to approval. Manual approval
binds an actor and proposed operation to candidate values, ap-
plicable limits, expiry, and the active line–product–recipe–run
tuple. After approval, the handler rechecks authority and com-
pares the current tuple with the approved tuple before entering
DCW dispatch. The default approval wait expires after 180 s.
A changed recipe definition requires a new recipe_apply
proposal. These checks reject stale requests at the software
dispatch boundary; they do not lock equipment state across
network or device I/O.

A recipe_trial illustrates the operation sequence: the
handler checks the bound recipe, active run, candidate param-
eters, and route timing; if required, it requests approval; after
revalidation, it submits a bounded batch through the configured
driver and returns a per-parameter receipt. The caller obtains
later DAQ observations separately and may then update, apply,
or roll back a recipe. A trial neither saves nor applies a
recipe version. The driver registry maps semantic controls to
configured protocol drivers, keeping protocol details out of
agent operation arguments.
Receipts and observations answer different questions. A
command result is graded as readback-verified, transport-
acknowledged, or unverified; a readback mismatch can trig-
ger up to three reads at 2 s intervals. Recipe batches retain
per-parameter verification outcomes. DAQ stores subsequent
timestamped process observations, while recipe versions, ap-
provals, and task records remain service-owned records linked
where a route supplies the corresponding identifiers. A verified
setpoint confirms the command path, not target attainment.
This distinction defines the evidence chain evaluated in Sec-
tion V.
V. EXPERIMENTAL EVALUATION
The experiments examine four aspects of AgentWork-
Shop: route-specific record continuity across two configured
simulator scenes, completion of one documented blueprint-
onboarding workflow, rejection of stale approval context be-
fore software dispatch, and the process samples associated
with the tested routes. These outcomes are kept separate. All
plant-facing checks used software simulators; none involved a
physical plant or independent process replication. Sections V-B
to V-D report each outcome on its own terms; the evidence is
complementary and is not pooled into a single score.
A. Test Design and Protocol
For a registered task, the integration criterion is a task
linked to its approval, readback-verified command receipt, and
a process sample tagged to the active run. A direct operation
call has no task edge; its criterion is a verified receipt/readback
and an active-run-tagged sample. The fixed-call harness replay
checks record links, not task completion. The context guard is
assessed by whether a changed line, product, recipe, or run is
refused before a driver write.
The route-continuity study used the v0.8.0 application with
cast-film and continuous-annealing simulator scenes. Cast film
wrote screw speed through OPC UA and observed thickness
through MQTT (target: 48–52 µm). Annealing wrote the zone-
3 setpoint through Modbus TCP and observed strip temper-
ature (target: 700–760 ◦C). The registered-harness path ran
three sequential tasks per scene on one persistent simulator;
each task used its own production and task context, while
process state carried forward. After each verified receipt, the
runner waited 20 s, probed and ingested one process sample,
queried it by active-run ID, and then checked task state. Thus,
task-completion-to-sample latency is unavailable. The fixed-
call replay, direct REST call, and fixture-backed command-line
task ran once per scene in separate isolated environments.
All route-study records report unavailable MQTT and
Timescale endpoints; their samples used the local SQLite fall-
back, with online DAQ collection disabled. The route results
therefore assess invocation and application-record handling,
not the normal online DAQ path. Fixture-backed routes used
deterministic input; direct REST created no task and did not
invoke an external model.

blueprint configured one Modbus/TCP device with four set-
points and seven DAQ nodes, plus MES REST scalar, 48-
point vector, table, and image forms. Dedicated local MQTT

B. Registered and Direct-Call Route Results
All six model-mediated registered tasks completed and
passed the task, approval, receipt, and sample-link checks
(76 runner assertions). Cast-film settings of 125/130/125 rpm
produced single 20-s samples of 45.69/46.69/45.69 µm. An-
nealing settings of 745 ◦C produced 679.60/677.70/678.10 ◦C.
All six samples were below their target bands; they do not
describe a response trajectory, steady state, or the quality of
the model-selected settings.
The fixed-call harness replay linked both tasks to approval,
receipt, and active-run samples (31 assertions); task comple-
tion was not asserted. Its cast-film and annealing samples
were 46.37 µm and 674.80 ◦C, both below target. Direct REST
returned verified receipts/readbacks and run-tagged samples
in both scenes (19 checks); its samples were 46.37 µm and
675.20 ◦C, also below target. The fixture-backed command-
line adapter completed both tasks and linked their samples
(37 application and 28 isolation checks); its samples were
46.38 µm and 674.40 ◦C, also below target. The tested routes
reached the shared operation services under two preconfigured
signal and protocol mappings. They do not establish process
attainment, configuration reuse, general adapter interchange-
ability, or portability to an unseen scene.
