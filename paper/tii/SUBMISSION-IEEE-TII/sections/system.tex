\section{System Architecture}
\label{sec:arch}
\system{} links team coordination to plant interaction through industrial nodes
and production context (Fig.~\ref{fig:arch}). Channels coordinate deployed
members and tasks; controller services mediate node operations; production
objects identify the line, product, recipe, and run. This organization is a
deliberate separation of concerns: a team plane decides what to investigate and
propose, an integration plane presents devices as semantic nodes, a governance plane decides whether a specific request is admissible, an operations plane supplies production context and evidence, and an extensibility plane adds drivers and services through sanctioned registration points. Table~\ref{tab:capabilities}
summarizes the resulting functional surface and, for each plane, what remains
scenario-specific. The decomposition is what makes the framework reusable:
scenario knowledge is concentrated in blueprints, signal maps, objective
predicates, and driver configuration rather than spread through the team
scheduler, approval service, or persistence code.

\subsection{Supervisory Core and Nodes}
The Node.js core hosts channel routing, industrial services, and protocol
adapters. A channel contains a lead, workers, tasks, messages, and retrievable
memory, deployed through WebSocket, MCP, A2A, REST, CLI, or TUI entry points; engine adapters preserve
member and node identity across runtimes, and channel membership alone confers
no write authority.

DAQ nodes convert device readings to engineering quantities; DCW nodes translate
engineering setpoints into driver commands and, where supported, readback.
Per-node runtimes manage timing; gateway services supply
connection state, recipe context, and write bookkeeping. The built-in semantic
surface covers Modbus TCP, Modbus RTU-over-TCP, OPC UA, MQTT, and HTTP/REST.
The deployment reaches author-implemented dynamic simulators through the same
node and driver contracts a plant would use; they are deterministic per seed
but not validated digital twins. First reuse boundary: a scenario declares
signals, units, scaling, precision, and driver configuration, and the team loop
is unchanged; fast regulation and independent protection stay in plant
controllers.

Driver contracts are deliberately narrow: a driver declares how a semantic
quantity maps to its transport payload, whether the endpoint is writable, and
whether a readback is available; the controller resolves member authority and
active limits. Connection, transport, and protocol errors are stored with the
request instead of one success flag, so a timeout, a rejected frame, and a
written-but-unconfirmed value remain distinguishable. Register addresses and
byte order appear only here, so adding a fieldbus family leaves the loop
untouched.

Acquisition is supervisory rather than hard real-time: each DAQ node runs its
own cadence under a rotating sweep, so a slow endpoint delays only its own
samples. Every reading carries a timestamp, quality state, and freshness age,
and the response window used by a verdict is a query over that history, not a
blocking read---which is why a bucket average can lag the device by one cadence.

\subsection{Bindings, Context, and Reuse Boundaries}
A member--node binding grants access to a sanctioned tool on a specific node and
selects automatic or approval-mediated execution; line permissions (none,
read-only, operate) authorize binding creation and mutation, and runtime
invocation is authorized by the persisted capability, not channel membership.
Intervals are re-checked every request rather than cached: revoking a binding
or switching the recipe takes effect on the next request. The same path serves
a console, a harness, and an agent engine---authority does not depend on the
client; only the evidence record differs, carrying the acting member and
proposal origin.

Production objects are versioned rather than overwritten: a recipe is a
versioned named definition, dispatched against a known-good version, reverted
non-destructively, and compared with the values actually applied; an
intervention is read against the definition active when it was admitted.
Plugins register hooks, routes, agent tools, drivers, and panels only through
sanctioned services, so an added driver inherits admission, readback, and
evidence capture.

The second reuse boundary is a reference onboarding adapter
(Section~\ref{sec:onboarding}); the SDK exposes the same surface to ordinary
programs, and runtime settings are hot-reloadable.

The stores share identifiers rather than a transaction domain: platform state
uses SQLite and files, and measurement and object backends use TimescaleDB and
MinIO with local fallbacks. A device may accept a write even if bookkeeping
fails, and records lack a run identifier, so time-range queries can cross runs
unless bounded---boundaries disclosed rather than hidden.

A BOPET worker proposes casting-speed, fast-roll, or rail-width changes through
bound DCW nodes; the same mission pattern serves the other three scenarios with
only blueprint, guards, and policy differing. Task completion remains distinct
from device acknowledgment and target attainment.

\subsection{Reference Scenario-Onboarding Contract}
\label{sec:onboarding}
The reference integration follows a bounded onboarding contract: the engineer
declares a blueprint of devices, signals, units, roles, initial setpoints, and
plant-model parameters; a differential ``ensure'' pass creates missing devices,
repairs drift, verifies connectivity, and loads the model without disturbing
other lines, projects the blueprint into semantic nodes and a recipe, and tags
the line for idempotent reuse. A channel is instantiated from the common team
template with bindings to the required nodes; a mission supplies the objective,
guards, response windows, and policy, and every observation, write, and
judgment flows through the same governed services. The adapter demonstrates
reuse of platform services, not configuration-only commissioning of physical
plants; the pass is idempotent and the projection non-destructive to other
tagged lines.

\subsection{Governed Optimization Task Lifecycle}
\label{sec:tasklifecycle}
A governed optimization task is a life cycle rather than a single tool call, and \system{} exposes each transition separately. The task enters a channel carrying goal, line, product, recipe, run, and task identifiers; a lead member claims it and dispatches the work to a worker holding member--node bindings on the relevant nodes. The worker repeats one fixed job: read the controlled quantity over a bounded window, propose a setpoint inside the resolved interval, invoke the governed write, wait for the response, and record a verdict. Section~\ref{sec:procedure} shows this path in operation.

Every iteration leaves more than a written value: the write opens an
optimization record with the prior and requested values, the admitting
interval, the acting member, and timestamps; readback, where supported, closes
the command path. The parameter journal attributes the change to its source;
attainment is evaluated against the scenario predicate, and the task closes
with a workflow terminal state (Section~\ref{sec:mech} gives the underlying
semantics).

This separation bounds what ``automatic optimization'' means: the framework
automates the loop---reading state, admitting and applying setpoints, waiting
for a response, recording evidence, accepting or compensating---and does not
prescribe a search algorithm or claim that a language model autonomously
selects the best action. A controller, a scripted policy, a conventional
optimizer, or an agent engine may occupy the strategy slot; authority,
evidence, and closure remain platform responsibilities. A mission can reach its
terminal state while missing the process objective, and the two are never
merged.
