\section{System Design}
\label{sec:design}
The runtime exposes named services through two entry paths. Task-mediated calls pass through the collaboration runtime and a registered Agent harness. Direct calls through the Representational State Transfer (REST) API or the standard input/output (stdio) transport for the Model Context Protocol (MCP) enter the shared dispatcher without creating a task turn. Both paths use the same scene configuration for production context, semantic-node mappings, protocol endpoints, objectives, and write limits.

\subsection{Design Rationale and Requirements}
\label{sec:principles}
The runtime must preserve process meaning across heterogeneous drivers,
provide a stable operation contract for registered harness adapters, and check
current authority and process limits before each write. It must also distinguish
command acceptance from later process observations. Scene configuration,
registered adapters, shared dispatch, route handlers, and service-owned
records enforce these boundaries.

At task start, the context builder assembles the active production tuple and
relevant process summaries. This context informs a proposal but does not grant
write authority; each operation resolves live state again at invocation.

\subsection{Layered Architecture}
\label{sec:layers}
Fig.~\ref{fig:arch} shows the system layers and their interfaces. Task and
chat routes use the collaboration runtime, which provides workspaces,
channels, task queues, shared memory, mailboxes, task templates, and harness
adapters. An adapter connects an agent engine to its task interface; its
binding and channel policy constrain the tools available to that agent.

Direct REST calls and the stdio-MCP operation bridge bypass task execution
and enter the shared dispatcher. They create neither a task nor a harness
turn; MCP management and task methods remain on their service routes. The
scene configuration has two consumers: the task route receives active context
and objectives, while operation services resolve node mappings and guards
when an operation executes. The service band provides data acquisition (DAQ), write
control, analysis, retrieval, and optional model services. At the field layer,
input/output (I/O) mappings connect semantic nodes to built-in or plugin
drivers for a plant or simulator. Each
owning service retains its task, command, observation, or configuration
records and associates them with the actor and production context where
supported.

\subsection{Scene Configuration as the Integration Boundary}
\label{sec:scene-config}
Scene-specific process semantics are represented in configuration before an
agent task begins. The active line identifies the production context; product
and recipe records supply applicable targets and limits; the run record
provides the current operating state. Semantic nodes bind process variables
to direction-specific acquisition or control mappings, and the driver
registry resolves each mapping to a supported protocol implementation. Here
\emph{semantic} denotes a named process variable with a direction, unit, and
configured mapping; it is not an OPC UA or Asset Administration Shell
information model. The
agent-facing operation remains named and typed, so a harness does not need to
construct protocol-specific messages. A scene using an already registered
driver can supply different context and node mappings behind the same
operation contract. A protocol not present in the registry still requires a
driver adapter; configuration alone does not implement a new protocol.

Table~\ref{tab:scene-config} summarizes how the scene description is consumed
along the execution path. It distinguishes configuration-time bindings from
checks against live state. The context assembled for an agent turn is
descriptive: before a write, the handler resolves the active context again
and applies the current limits. Approval is bound to the proposal and to the
context where that route supports context snapshots; the command receipt
remains separate from subsequent DAQ observations.

\subsection{Cross-Module Execution Flow}
\label{sec:executionflow}
For a task-mediated call, the registered adapter presents a scoped tool
catalog and current task context to the Agent. At the operation boundary, the
shared dispatcher checks the predicates declared for the named operation
before selecting its handler. The handler resolves live production state,
applies route-specific guards and limits, and requests any required approval
before device I/O.

For an industrial operation $u$ by agent $a$ in channel $c$, define the
shared dispatch condition as
\begin{equation}
\mathcal{A}(a,c,u)=\bigwedge_{X\in\mathcal{C}(u)}X(a,c,u),
\label{eq:dispatch-contract}
\end{equation}
where $S$, $P$, $G$, and $B$ denote invocation scope, current channel policy,
applicable industrial grant, and the agent's binding to referenced resources,
respectively. $\mathcal{C}(u)\subseteq\{S,P,G,B\}$ is the set of predicates
declared for operation $u$; it always contains $S$ and $P$. The grant predicate
$G$ is included when the resolved channel, target line, and owner/grant policy
require it; explicit exemptions omit it. The binding predicate $B$ is included
when the operation declares resource references. A declared no-reference
operation omits $B$. Each included check must pass before
handler selection. The policy predicate includes channel tool selection,
profile, and duty-separation checks where configured. After these predicates pass, the selected route applies its operational
guards and any required approval. The checks performed after approval depend
on the route; Section~\ref{sec:modules} specifies the single-node and
recipe-operation paths.

For a direct REST call, the service establishes $a$ and $c$ before applying
these checks. An agent token must match the requested agent identifier; an
authenticated user must be the channel owner or an administrator. The manager
loads the channel-agent record and rechecks scope and policy, followed by any
applicable grant and binding checks. Handlers resolve live production state
from request identifiers and owning services.

Section~\ref{sec:modules} specifies route-level admission, timing, approval,
and evidence rules for both task-mediated and direct calls.
