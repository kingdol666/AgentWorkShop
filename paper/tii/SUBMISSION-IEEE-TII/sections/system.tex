\section{System Design}
\label{sec:design}
The architecture links an agent collaboration runtime to a production-scene
configuration. The runtime supplies task context and scoped operations. The
scene configuration maps process semantics to acquisition and control nodes,
drivers, targets, and guards. Named operations carry requests from the runtime
to shared dispatch and governed device access. Task execution remains separate
from operation dispatch, and command receipts remain distinct from measured
process responses.

\subsection{Design Rationale and Requirements}
\label{sec:principles}
The design must preserve process meaning across heterogeneous drivers, allow
harness changes without altering the operation contract, and check current
authority and process limits before a write. It must also keep command
acceptance distinct from subsequent process observations. Scene configuration,
registered harness adapters, shared dispatch, route handlers, and
service-owned records provide these boundaries. The registry allows agent
engines and protocol drivers to be added without changing named operations.
Section~\ref{sec:eval} evaluates selected configured simulator paths.

Commissioning links each line to its products, recipes, active-run rules,
signal meanings and units, driver mappings, and admissible limits. For a task
turn, the context builder assembles the current line--product--recipe--run
state and relevant process summaries. Before a write, the handler resolves
live state again; prompt context informs a proposal but does not authorize it.
Direct operation calls resolve the current context at invocation.

\subsection{Layered Architecture}
\label{sec:layers}
Fig.~\ref{fig:arch} shows the access routes, shared dispatch path, production
services, semantic I/O, configured drivers, and ownership of records. Task
and chat routes enter the collaboration runtime. It contains workspaces,
channels, task queues, shared memory, mailboxes, task templates, and harness
adapters. A \emph{task route} is an execution path through this runtime; a
\emph{harness adapter} connects an agent engine to its task interface.
Multiple registered agents can work through shared tasks and channel context,
but each agent's available tools are constrained by its binding and channel
policy.

Direct REST calls and the stdio-MCP operation bridge bypass task execution and
enter the shared dispatch block (upper-right route in Fig.~\ref{fig:arch}).
They create neither a task nor a harness turn. MCP management and task methods
remain on their service routes.

The scene configuration supplies the active production context, semantic
node mappings, objectives, and guards to the operation path; the dashed line
in Fig.~\ref{fig:arch} marks this link. The service band provides data
acquisition, write control, analysis, retrieval, and optional model services.
Field I/O maps semantic nodes to built-in or plugin drivers for a plant or
simulator. Each owning service retains its task, command, observation, or
configuration records and associates them with the actor and production
context where supported.

\subsection{Cross-Module Execution Flow}
\label{sec:executionflow}
Fig.~\ref{fig:runtime} shows the task-to-device sequence. The runtime gives
the registered adapter a scoped tool catalog and assembles the current task
context. For each returned call, the shared dispatcher evaluates its declared
scope, channel-policy, grant, and binding checks before selecting a handler.
That handler resolves live production state and applies the route's guards,
active-run requirements, limits, and approval rules before device I/O.
The result returns to the caller; the owning services retain the operation
receipt and any later process observations separately.

For an industrial operation $u$ by agent $a$ in channel $c$, define the
shared dispatch condition as
\begin{equation}
\mathcal{A}(a,c,u)=\bigwedge_{X\in\mathcal{C}(u)}X(a,c,u),
\label{eq:dispatch-contract}
\end{equation}
where $S$, $P$, $G$, and $B$ denote invocation scope, current channel policy,
applicable industrial grant, and the agent's binding to referenced resources,
respectively. $\mathcal{C}(u)\subseteq\{S,P,G,B\}$ is the set of predicates
declared for operation $u$; it always contains $S$ and $P$. The grant predicate
$G$ is included when the resolved channel, target line, and owner/grant policy
require it; explicit exemptions omit it. The binding predicate $B$ is included
when the operation declares resource references. A declared no-reference
operation omits $B$. Each included check must pass before
handler selection. The policy predicate includes channel tool selection,
profile, and duty-separation checks where configured. After these predicates
pass, the selected route applies its guards, active-run checks, admission
limits, and any required approval. If approval is required, the handler
revalidates its context before device dispatch.

For a direct REST call, the service establishes $a$ and $c$ before applying
these checks. An agent token must match the requested agent identifier; an
authenticated user must be the channel owner or an administrator. The manager
loads the channel-agent record and rechecks scope and policy, followed by any
applicable grant and binding checks. Handlers resolve live production state
from request identifiers and owning services.

Direct REST and stdio-MCP operation calls bypass the task runtime but enter
the same shared dispatcher. Section~\ref{sec:modules} specifies route-level
admission, timing, approval, and evidence rules.
