\section{Discussion}
\label{sec:discussion}
\subsection{Interpretation}
In the integrated run, both scene configurations used the shared operation
boundary while retaining their own signal and route mappings. Five protocol
endpoints returned acquisition samples, and the tested negative probes were
rejected in both scenes. The result supports integration for these
configurations; it does not show that an arbitrary plant can be connected
without commissioning or route-specific setup.

The deterministic OpenCode task route completed three-step sequences on four
writable cast-film routes with the model loop disabled. Modbus TCP and OPC UA
returned actuator readbacks; MQTT and HTTP recorded accepted operations and
DAQ checks without readback. The second scene was exercised for acquisition
and guard checks only, so this run does not establish harness portability or
a cross-scene write-response chain.

The objective cases and BOPET task are separate simulator activities from the
same run. The former were compared with an offline simulator reference; the
latter ended inside its configured thickness band, while its associated
parameter-change record remained open and unjudged. Neither activity provides
a matched controller comparison or shows that a write caused a process change.

Prior work grounds industrial actions in digital-twin state, asset models,
process diagrams, or supervisory checks
\cite{gehrmann2020dtiacs,graul2026aas,schall2026safe}. This paper focuses on
the interface between task or harness execution, scene-specific signal and
driver mappings, and the shared device-operation path. The run tested selected
links across that interface. It did not measure whether configuration reduces
integration time, maintenance effort, or operational risk; those questions
require matched deployments and workload measurements.

\subsection{Scope and Limitations}
The evidence comes from one deterministic simulator run, with the platform
and simulators already running. There was no active language-model loop,
cold-start commissioning, matched comparison of task and direct calls,
multi-harness test, approval ablation, controller baseline, or physical
equipment. The three seeds are cases within that run, not independent system
repetitions; seed 43 stopped before any update, so they do not establish
convergence across initial conditions.

The negative probes exercise recorded software guards only. They do not
measure approval effectiveness or establish plant safety, and the missing
denominator of legal-write attempts prevents an estimate of false blocks.
Supplementary File~S6 retains latency summaries as diagnostics because the run
did not preserve event-level timings. Its delivery manifest was created after
execution and does not establish that the runtime configuration was frozen.

To test effectiveness, a follow-up should repeat the run with a frozen
configuration, record complete request-to-readback traces, and compare matched
controller and approval-policy conditions. Hardware-in-the-loop evaluation
can then test whether the software results transfer to equipment.

\section{Conclusion}
\label{sec:conclusion}
We presented a configuration-driven architecture that connects task-level
industrial agents to scene context, signal mappings, and device routes through
a shared governed interface. In one deterministic simulator run, configured
acquisition and write-guard paths operated in two scenes; 76 of 77 workflow
checks passed, with one warning. These results document the integration in
simulation; portability across harnesses and control effectiveness remain open
questions.
