\section{Governed Execution Mechanisms}
\label{sec:mech}
A supervisory intervention must preserve distinctions that are often collapsed
in an agent tool call: permission to propose, admission of a value, driver
acceptance, readback, process response, a caller's verdict, and compensation. \system{} exposes these as separate, distinguishable evidence states (Figs.~\ref{fig:chanloop} and~\ref{fig:walkthrough}).

\subsection{Task, Observation, and Admission}
\label{sec:objective}
The strategy receives a task and goal in production context and decides what to propose and when to stop. The platform governs execution; decision variables are semantic node parameters---pressure, dosing rate, line speed, rail width---in engineering units. Authority belongs to deployed member--node bindings, not the channel, prompt, or task template.

Before a proposal, \texttt{daq\_query} obtains a baseline or response window and
reports freshness. For an ordinary agent setpoint request on node $n$, the
implemented admission interval is
\begin{equation}
\mathcal{I}_n(t)=\mathcal{H}_n\cap\mathcal{B}_n
                 \cap\mathcal{P}_n(t)\cap\mathcal{R}_n(t),
\label{eq:admission}
\end{equation}
where $\mathcal{H}_n$ is the hard engineering range and the remaining terms are
applicable baseline, active-product, and active-recipe limits. Missing optional
limits add no restriction. This intersection constrains submitted values; it is
not a learned feasibility region or a physical safety certificate. Availability,
binding state, and approval policy are checked separately.

\subsection{Semantic Write and Source-Specific Routes}
\label{sec:nodeexec}
\label{sec:writepath}
\label{sec:paramlayer}
A semantic card exposes quantity, unit, precision, range, current value,
freshness, and recipe context. The controller resolves the member binding and
active limits, then the driver serializes the command; readback is attempted
only when supported and closes the command path, not the process-response path.

After a successful agent or manual write, the node installs a configurable
post-write hold window, \texttt{writeLockSeconds}, whose default is
\resWriteLock: a further agent/manual request for the same node during that
window receives HTTP 429 \texttt{WRITE\_FREQUENT}. The lock is installed only after the driver reports success; recipe-dispatch and rollback writes are exempt because they use separate operational routes, zero disables it, and \texttt{AW\_BENCH\_MODE=1} bypasses it for benchmark harnesses. The hold is per node and applies only to agent-origin requests: it guards a supervisory loop whose response window may be comparable to the sampling cadence, and it is not a rate limit on the plant.

Guards vary by source, as shown in Fig.~\ref{fig:chanloop}: ordinary agent writes use the full binding and admission path; recipe dispatch supplies run context and applies its route-specific checks; hold heartbeats share runtime write exclusion but establish no member authority; line start installs active context before dispatching recipe parameters individually, and stop clears that context and closes retained open records. These multi-step operations are not atomic with device state.

For a request $u_n$, the framework stores the attempted actor and context,
executes the driver call, and stores write/readback status, so a driver error,
missing readback, or bookkeeping failure remains visible rather than being
recast as process success. Agent-origin ownership and cooldown checks reduce
some conflicting updates but are not universal guards for manual, recipe, or
system routes.

\subsection{Observation, Judgment, and Compensation}
\label{sec:agentloop}
An accepted write opens an optimization record containing the prior and
requested values, applicable limits, actor, and timestamps. The strategy then
queries process observations over a response window.
\texttt{dcw\_judge} records \texttt{keep}, \texttt{rollback}, or \texttt{uncertain} plus a reason; it performs no actuation and does not independently validate the evidence, so a scripted \texttt{keep} can coexist with a missed objective. The verdict is stored with the record it closes and with the response window that was actually queried, so a later reader can see what evidence was in front of the caller at the time, and a verdict is never rewritten in place: a compensation or a backstop action adds a new record instead of editing the previous one.

Compensation is a new, separately admitted write to a stored baseline or anchor-derived value; it may fail after the original command succeeded, and a multi-node sequence may only partially complete. Recipe rollback restores a definition, not physical PLC values. These separations keep command status, record status, and process recovery independently inspectable.
Fig.~\ref{fig:walkthrough} shows the resulting observe--write--judge path end to end, from device export through binding, channel deployment, and the recorded verdict.

A stored-policy backstop periodically evaluates open records: in the
implemented default it waits at least 120\,s, checks no more often than every
30\,s, and triggers after at least three returned points or bucket averages are
outside the stored window; automatic recovery is attempted only while fewer than two retained records for the node are already marked rolled back. Asynchronous queries, retained-history counting, and later record changes mean this cadence is neither a deadline nor a formal run-time assurance bound.

\subsection{Human Approval Boundary}
\label{sec:hitl}
Manual bindings insert a timed approval wait before an agent setpoint or
physical compensation request; automatic bindings omit the wait but retain
applicable checks. The pending request shows member, node, requested value,
request-time interval, and expiry. Approval reserves neither the interval nor
the device state, so binding and admission are checked again before execution.
Expiry and refusal are recorded separately, and duplicate pending requests are
suppressed.

The current decision endpoint authenticates a user but does not enforce a
line-scoped approver role, and reads, verdict recording, and some configuration
operations do not use physical-write approval. Thus this mechanism demonstrates
workflow mediation, not segregation of duties or certified human supervision.

\subsection{Design Rationale and Reuse Boundary}
\label{sec:rationale}
The strategy engine is replaceable rather than trusted as a control primitive;
authorization, readback, task termination, and process attainment remain
distinct. The stable plane retains bindings, semantic I/O, evidence, approval,
compensation, and backstop handling, while a scenario supplies its blueprint,
limits, objective, response window, and policy. This confines scenario-specific
work without claiming physical portability.

Two rules keep that boundary stable. First, scenario code may declare and configure but may not execute plant I/O: blueprints, signal maps, guards, and policies are data and strategy, while every write still passes through admission, driver dispatch, and evidence capture. Second, the platform never infers a process objective; attainment is computed by the scenario predicate, so the same records can be re-evaluated against a revised predicate without rewriting history.
