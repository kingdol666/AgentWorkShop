\section{Introduction}
\IEEEPARstart{I}{ndustrial} agents can propose parameter changes, but a proposal becomes an industrial operation only after the system resolves its production context and signal meaning. Each write must be tied to the active line, product, recipe, and run; mapped to a configured control point; and checked against current authority and process limits. The process measurement used to assess a response is distinct from the command signal. In the cast-film scene studied here, line speed is the writable setpoint and film thickness is measured separately, although both use Message Queuing Telemetry Transport (MQTT). A command receipt or setpoint readback therefore does not establish the film response. Fig.~\ref{fig:control-path} illustrates the distinction.

Research on industrial agents addresses service supervision, control generation, programmable logic controller (PLC) programming, and multi-agent manufacturing workflows \cite{biskupovic2025supervision,xia2025control,huang2026made,koehle2026llmdriven,liu2026agents4plc,wu2025instructmpc,lim2025llmenabled,zhao2026shopfloor,hofmann2025nlc,liu2026semanticcommissioning}. Other work exposes manufacturing capabilities through standardized tools and semantic skills \cite{silva2025mcpmanufacturing,koehle2025semanticrecipes,xavier2026industriConnect}, or combines agent proposals with asset models, approval, audit, and process verification \cite{graul2026aas,schall2026safe,lin2026agentic}. Together, these studies address agent organization, plant-facing tools, and operation governance. The design problem is to carry the active line--product--recipe--run context and signal meaning through authorization and protocol dispatch, then return evidence that separates the command outcome from the process response.

We implement this path as a configuration-driven runtime. A production-scene description binds the line--product--recipe--run context to semantic acquisition and control nodes, registered protocol drivers, process objectives, and write limits. Task-mediated and direct operation calls enter a shared dispatcher, where route handlers resolve live state again before device access. Service-owned records keep the requested command, optional device readback, and later process observation distinct. Through a registered harness, the Agent decides whether to request another task-level step; the runtime applies the configured checks to each operation. The paper contributes an implemented system-integration architecture; it does not propose a new control law or agent-reasoning algorithm.

The contributions are:
\begin{enumerate}
  \item A production-scene configuration model that binds operational context to semantic signal acquisition and control, registered protocol drivers, process objectives, and engineering limits behind named operations.
  \item A task-to-device path that exposes the same named operations through registered Agent harness adapters and direct callers. Both paths use shared dispatch checks; route-specific handlers apply current admission and approval rules and retain command evidence separately from process observations.
  \item An evaluation of selected scene--protocol mappings, admissible writes, structural rejections, and available readbacks across four simulator scenes, followed by a five-seed deterministic-mission comparison and a process-window interlock ablation. Each block uses its own unit and denominator, so simulator outcomes remain separate from mock-driver results.
\end{enumerate}

Section~II reviews industrial-agent and plant-integration work; Section~III presents the architecture and scene configuration. Section~IV traces a task-level operation through its feedback path, and Section~V specifies write governance and evidence. Section~VI reports the simulator and mock-driver evaluation. Section~VII discusses what the results support and what remains untested.
