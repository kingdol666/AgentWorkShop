\section{Introduction}
\IEEEPARstart{I}{ndustrial} agents can propose process changes, but a proposal becomes an industrial operation only after the runtime resolves the active production context and maps the request to the intended control signal. This mapping is scene dependent. For example, a cast-film line-speed setpoint may affect measured film thickness, but the setpoint and measurement are distinct process variables even when both use MQTT. Command acceptance, device readback, and a later process measurement also provide different evidence: acceptance records the service outcome, readback reports the actuator value, and the process measurement records what followed. Fig.~\ref{fig:control-path} illustrates this distinction.

Industrial-agent research has addressed planning, control generation, PLC programming, and fault recovery. Other work exposes industrial capabilities through protocol adapters or semantic commissioning, while plant-facing systems apply approval and verification mechanisms. These studies address different tasks and report different evidence, so their results are not directly comparable with those of the runtime studied here. This paper examines how these concerns meet at the boundary between a task-level proposal and a device operation. At that boundary, the runtime must preserve production context and signal meaning across task-mediated and direct calls, recheck applicable authority and limits at execution, and distinguish command evidence from subsequent process observations. Agent planning, protocol access, approval, and range checks are not individually new contributions of this work.

We implement this boundary in a configuration-driven runtime. A scene binds the line, product, recipe, and run to direction-specific acquisition and control nodes, registered protocol drivers, process objectives, and write limits. Task-mediated and direct calls enter a shared dispatcher; route handlers resolve live state and apply the checks required for that route before driver dispatch. For example, when approval is required, a recipe operation rechecks its active production context after approval, whereas a single-node operation rechecks its binding and any applicable grant and applies current limits without using the same context snapshot. These checks address different stale-state risks; they do not make validation and device I/O atomic. The contribution is the integration of process meaning, route-specific authority, and execution evidence, rather than a new control law or agent-reasoning algorithm.

The contributions are:
\begin{enumerate}
  \item A production-scene configuration model that links operational context and direction-specific signal mappings to registered drivers, objectives, and limits for use at the operation boundary. (Section~III.)
  \item A task-to-device path for registered Agent harnesses and direct callers that combines shared dispatch, route-specific revalidation and conditional approval, and common write guards. It keeps command outcomes, optional readbacks, and later process observations distinct. (Sections~III--V.)
  \item An evidence-bounded evaluation of configured mappings and pre-dispatch guards across four simulated scenes, with command readback, process observation, and live-Agent outcomes reported as separate evidence. (Section~VI.)
\end{enumerate}

Section~II reviews industrial-agent, interface, and operation-governance work. Sections~III--V describe the runtime configuration, operation path, and write controls. Section~VI reports the evaluation by evidence type, and Section~VII discusses the limits of the results.
