\section{Introduction}
\IEEEPARstart{I}{ndustrial-agent} deployments must connect a changing process
context to heterogeneous equipment without giving a language model unrestricted
access to control points. A line-speed proposal, for example, depends on the
active product, recipe, run, engineering limits, and node that represents the
control. It must also reach the correct device through a configured protocol,
and its receipt must not be confused with a later process response. When these
elements are implemented separately for each agent and production scene,
integrating a new engine or line requires repeating substantial interface and
context work.

Prior work has advanced industrial-agent supervision, language-model control
and programmable logic controller (PLC) code generation, modular manufacturing
skills, and digital-twin and shop-floor integration
\cite{xia2025control,huang2026made,koehle2026llmdriven,waseem2026pretrained,biskupovic2025supervision,liu2026agents4plc,wu2025instructmpc,lim2025llmenabled,zhao2026shopfloor,gill2025llmdt,hofmann2025nlc}.
Related platforms ground approved actions in Asset Administration Shell (AAS)
or process and instrumentation diagram (P\&ID) models, and integrate sensor,
manufacturing execution system (MES), and enterprise resource planning (ERP)
evidence streams \cite{graul2026aas,schall2026safe,lin2026agentic}.

The deployment problem addressed here is how to map distinct industrial scenes
to a common operation interface, provide active production context to agent
tasks, and translate a proposal into a bounded, traceable device operation.
We present a configuration-driven integration architecture, not a new control
law, optimization algorithm, or experimentally validated multi-agent
controller. Its central design choice is to keep harness execution,
scene-specific signal and driver mappings, and device-write governance modular
while connecting them through named industrial operations.

The contributions are threefold:
\begin{enumerate}
  \item A scene-integration model binds production context
  (line--product--recipe--run), semantic acquisition and control nodes,
  protocol drivers, objectives, and engineering guards. Distinct processes can
  therefore be represented through configuration and a common operation
  interface, while protocol-specific access remains in drivers.
  \item An integration runtime registers replaceable harness adapters against
  a common task-operation interface, assembles current production context at
  each turn, and scopes available operations to channel policy and resource
  bindings. Multiple engines and task roles are supported by the architecture;
  the experiments evaluate a narrower set of routes and configurations.
  \item A governed write path combines shared dispatch checks with
  route-specific admission, conditional human approval, post-approval context
  revalidation, and device-side receipt grading. Owning services retain
  command receipts separately from later process observations.
\end{enumerate}

Fig.~\ref{fig:control-path} follows one task proposal through operation

They verify selected software paths; they do not validate all agent--scene
combinations or establish multi-agent performance or physical-plant behavior.
