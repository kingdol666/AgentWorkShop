\section{Experimental Evaluation}
\label{sec:eval}
The evaluation addresses four questions. RQ1: do configured node--driver mappings accept admissible values, reject structural violations, and return matching readbacks? RQ2: does a governed write path separate a no-write condition from a scripted mission that reaches the target band? RQ3: does the process-window guard block targeted excursions before the driver? RQ4: do approval and authorization routes reach their expected branches? A separate block reports a live-Agent pilot as a negative result. Each block retains its own unit and denominator; counts are not pooled across blocks.

\subsection{Experimental Design}
\label{sec:eval-design}
Table~\ref{tab:eval-design} summarizes the six blocks. The design uses a negative control wherever a positive claim is made: the no-write condition (C0) writes nothing, the guard ablation removes one guard at a time, and the approval pilot includes a rejection branch. E1 is a census of the configured writable nodes rather than a sample. E2 pairs conditions by seed and scene but does not time-match them. E4 repeats each arm three times. E5 is a feasibility pilot, not a performance comparison.

\subsection{Execution Protocol}
\label{sec:eval-execution}
All blocks ran against the same recorded platform snapshot: the run manifests identify source commit \texttt{da627d21}, Node 24.19.0, Windows 11, an isolated service on port 3005, and a scenario simulator on port 4011. The experiment runners were uncommitted at execution time and were later committed as \texttt{40533741}; the recorded commit therefore identifies the platform source, not a hermetic tree. The probe manifest records configuration hash \texttt{a66769851fa03de5}; the ablation manifest records \texttt{3a57e722d4764b98}. Two platform lifecycles were used. E1, E2, E4, and the approval and authorization calls ran with \texttt{AW\_BENCH\_MODE=1}, which relaxes normal timing and hold-window guards. The production-guard checks ran in a separate process with the variable absent, and the runner asserted its absence before issuing calls. The two lifecycles were never combined in one result block; consequently, E1, E2, and E4 do not exercise the 60-s interval or hold-window guards.

The run order was: two integrated pipeline executions; E1 probes; E2 C0 and C1 for seeds 42--46; E4 four arms with three repetitions; production-guard branches; approval and authorization calls; and the E5 pilot. The C0 and C1 conditions used the same seed list. C0 held for 60~s without writes; C1 ran the scripted mission through the shared governed-write service and queried DAQ after configured settling intervals. Each C1 seed was executed once and no seed was discarded. The two pipeline executions used the same command and seed, and the comparison tool reported identical decision fields.

Outcomes were taken from independent data planes: HTTP status and response bodies for probes, the platform write ledger for command outcomes, actuator readbacks for control values, and DAQ samples for process observations. Agent transcripts and terminal logs were not used as outcome evidence. For E2 we recomputed band membership from the raw \texttt{pv}, \texttt{target}, and \texttt{tol} columns because the runner's \texttt{attained} field combines different criteria across conditions. The runner commands, seeds, run identifiers, and raw CSVs are preserved in Supplementary File~S7.

Five deviations are reported rather than smoothed over. First, one biaxial-line structural case was not collected, so the structural denominator is 219 rather than 220. Second, HTTP endpoints expose no actuator readback, so 216 of 220 accepted requests have a readback value. Third, the auto-mode approval calls used the same starting values as the manual calls but crossed runner labels, so the four calls are not a matched approval-on/off design. Fourth, the cast-film probe record was excluded: its manifest declared four scenes but recorded only cast-film, and its simulator endpoint did not match the reproduction command. Its 24 admissible requests, 24 structural probes, and 20 readbacks are not pooled. The film-line preset check (nine selected negative probes rejected without code changes) is a configuration check, not matrix coverage. Fifth, one C0 control began from residual state; this is reported with the target-band results.

\subsection{Integration and Mapping Results}
\label{sec:eval-mapping}
Two integrated executions each returned 77 passing assertions, zero warnings, and zero failures across 17 phases. The unit is an assertion within a run, not an independent trial, so the two runs support reproducibility of the configured path but not a success rate.

Table~\ref{tab:scene-probe-results} reports the collected scene--protocol subset. The 55 configured writable nodes span five configured protocol variants across four families: Modbus over TCP and RTU, OPC UA, MQTT, and HTTP. Each scene used four of the five variants. Each node received three interior values, the tested upper boundary, and four structural-range requests. All 220 admissible requests were accepted, all 219 collected structural probes were rejected, and all 216 available readbacks matched. The admissible and structural values are computed from the same configured minimum and maximum used by the guard, so this is a consistency check of the configured mapping, not an independent estimate of range correctness. In the simulator, a readback is an echo of the configured value; it demonstrates transport and register mapping, not actuator application. Because the probes are a census of the configured nodes, clustered at node level, we report counts rather than a population-level interval.

The biaxial line contributes 120 admissible requests, 119 structural probes, and 116 readbacks; its HTTP endpoint has no readback, and one structural case was not collected. The film-line preset check reused the running platform, so it is not an independent cold-start deployment. The selected mappings therefore passed their configured checks, but the full scene--protocol matrix remains incomplete.

\subsection{Target-Band Comparison}
\label{sec:eval-optimization}
C0 and C1 used seeds 42--46 in the injection, wastewater, and annealing scenes. C0 made no writes for 60~s; its endpoint is the mean of the final five process samples. C1 ran the deterministic scripted mission through the \texttt{recipe\_trial} batch route, not the single-node \texttt{optimization\_explore} route described in Section~\ref{sec:closed-loop-operation}, and queried DAQ after configured settling intervals. The mission stops at the first in-band reading, so its endpoint is the stopping value, not a fixed-horizon measurement. C1 took 150.41--172.90~s per seed, so the conditions differ in exposure time and mission logic. C1 is a positive control, not a competing industrial controller; the experiment contains no PID or model-predictive baseline.

For injection mass, the target was $32.5\pm0.35$~g (32.15--32.85~g). C0 endpoints were 31.206--31.272~g (mean 31.244~g), while C1 endpoints were 32.173--32.340~g (mean 32.241~g). For wastewater dissolved oxygen (DO), the target was $3.4\pm0.6$~mg/L (2.8--4.0~mg/L). C0 endpoints were 0.198--0.268~mg/L (mean 0.219~mg/L), while C1 endpoints were 3.576--3.864~mg/L (mean 3.714~mg/L). For annealing, the target was $95\pm6$~HV (89--101~HV). C0 endpoints were 134.36--134.90~HV (mean 134.64~HV), while C1 endpoints were 97.44--99.90~HV (mean 98.22~HV).

One C0 control began from residual state: seed 42 started at 32.378~g injection mass and 2.894~mg/L DO, both inside their bands, rather than at the blueprint state used by C1. Seeds 43--46 began from the blueprint. Across the 12 blueprint-matched pairs, 0/12 C0 and 12/12 C1 endpoints were in band; including the warm-started seed-42 control gives 0/15 and 15/15. We report counts rather than a p-value: the conditions are not time-matched, the C1 endpoint is the stopping value, and the 15 pairs are clustered within three scenes. A paired test would overstate the design. Across the five C1 seeds, the missions issued 12 writes in 17 rounds for injection, 56 in 59 for wastewater, and 41 in 50 for annealing; these are workload counts, not an efficiency comparison. Fig.~\ref{fig:latest-evaluation} shows each endpoint and its band.

\subsection{Process-Window Guard Ablation}
\label{sec:eval-ablation}
With the full guard, 18/18 negative probes were rejected before the mock driver and 0/6 targeted window violations reached it. Removing only the process-window guard reduced negative-probe rejections to 12/18: all six targeted violations reached the driver, while the 12 structural probes remained blocked. The no-readback arm retained the process-window guard and produced the same 18/18 rejection result. The combined no-window/no-readback arm matched the \texttt{no-interlock} arm on these stimuli. Each arm also accepted 9/9 nominal legal requests without a false block and met its configured boundary expectations in 9/9 checks. These are three technical repetitions of deterministic stimuli, not independent trials; the inferential unit would be the stimulus type (six negative and two targeted), not the 18 submissions. We therefore report counts and do not attach p-values.

No readback-mismatch stimulus was included, so the experiment isolates the process-window predicate but says nothing about readback-check effectiveness or interaction between the two checks. The ablation ran in benchmark mode against a mock driver and therefore assesses the software guard in that fixture, not plant-level protection. In a separate production-mode run, the legal baseline value 190 was accepted and one example each was rejected for interval (429, \texttt{WRITE\_INTERVAL\_NOT\_ELAPSED}), step (409, \texttt{STEP\_LIMIT\_EXCEEDED}), node range (400, \texttt{NODE\_RANGE\_EXCEEDED}), recipe window (400, \texttt{RECIPE\_LIMIT\_EXCEEDED}), and hold window (429, \texttt{WRITE\_FREQUENT}). These single-case checks confirm expected branches; they are not rejection-rate estimates.

\subsection{Approval and Authorization Path Checks}
\label{sec:eval-approval}
A four-call simulator pilot exercised the approval route. In manual mode, the approved case changed the control value from 202 to 204.8, while the rejected case left it at 216. The two auto-mode calls began at 202 and 216, the same starting values as the manual calls, but their runner labels were crossed relative to the manual decisions. The decisions came from a test fixture, no operator made them, and the calls do not form a matched approval-on/off comparison. We therefore treat these records as a path check rather than an estimate of the approval effect. A separate three-call authorization probe rejected one unbound write and one cross-node write while accepting one write to a bound control node (240 to 241). These examples show that the configured checks returned their expected outcomes in the tested routes; they do not establish a general safety rate or live-Agent decision quality.

\subsection{Agent-Route Pilot and Negative Result}
\label{sec:eval-agent}
The live-Agent orchestration path was exercised in a separate pilot with an omp lead--worker team on the injection scene; no governed write reached the dispatcher. Four setup attempts were made, and two produced recorded episodes. Both recorded episodes issued zero governed writes. The first ended at 301.48~s with terminal state \texttt{COMPLETED} while the process variable was 31.28~g, outside the 32.15--32.85~g band; this exposed a platform defect in which goal completion was not checked against the goal criterion. The second ended at 902.84~s with \texttt{BUDGET\_TIMEOUT} and a process variable of 31.23~g. The two earlier attempts did not produce result rows: one task remained queued and one worker lacked the host-tool mount. The pilot also exposed task-artifact addressing and lead-queue draining defects, which were bypassed in the runner.

We report this pilot because omitting it would overstate the evidence; it is not used for any performance claim. It shows that the deterministic blocks characterize the runtime path, not an autonomous Agent policy. A confirmatory study requires the platform fixes in Section~\ref{sec:discussion} and a larger episode budget.

\subsection{Scope of Inference}
\label{sec:eval-scope}
Four limits bound the claims. Construct: band membership is a task-level endpoint, not a control-performance metric; settling time, overshoot, and stability were not measured. Internal: C0 and C1 differ in duration and mission logic, the C1 endpoint is the stopping value, the ablation isolates one predicate against a mock driver, and the approval decisions were scripted. External: the evidence covers four simulator scenes, one mock driver, and no physical plant, cold-start deployment, or competing controller. Statistical: the study reports descriptive counts; because stimuli are clustered in nodes and scenes and the conditions are not time-matched, we do not attach population-level intervals or p-values. These limits are reflected in the claims and in the conclusion.
