\section{Experimental Evaluation}
\label{sec:eval}
The frozen core blocks ran against already-running platform and simulator services; most used benchmark mode, which relaxes normal timing and hold-window controls. Separate production-mode guard checks are reported on their own. No cold-start deployment or physical-plant run was performed. Results are presented in the order an operation crosses the runtime: configured mapping, authorization and write admission, process observations, and Agent-level execution. The blocks use different units—mapping requests, fixed stimuli, per-seed endpoints, a single simulated-twin execution, and Agent episodes—so counts are not pooled.

Table~\ref{tab:evidence-scope} connects each evaluation block to the question it can answer. A matching readback checks the actuator value returned by the simulator; it does not establish a process response. Conversely, an in-band process observation does not by itself establish which write caused it. The route and guard checks address pre-dispatch behavior, whereas the live-Agent episodes address whether a task reached a governed write. These distinctions determine the scope of the conclusions below.

\subsection{Configured Mapping and Integration Checks}
\label{sec:eval-mapping}
Two integrated executions each passed 77 assertions across 17 phases. These repeat checks of the configured service path; the assertions are not independent trials.

The two executions used seed 42, started with the platform and simulator already running, and did not activate an Agent harness. A separate preset check within the integrated film-line path configured five endpoint types and rejected nine selected negative probes. It reused the same runtime, so it is not a cold-start deployment or an independent replication of the mapping matrix.

The scene--protocol probes covered 55 writable nodes across four simulated scenes and five configured protocol variants. Each node received three interior-value requests, one upper-boundary request, and four structural-range requests. All 220 admissible requests were accepted; 219 collected structural-range requests were rejected; and all 216 available readbacks matched. These probes check the consistency of configured mappings: the tested values and guards use the same configured limits. Simulator readback echoes the configured value and does not verify physical actuation. One structural request was not collected, HTTP nodes do not expose readback, and the full scene--protocol matrix remains incomplete. The excluded cast-film run and other deviations are documented in Supplementary File~S7.

\subsection{Write-Guard and Route Checks}
\label{sec:eval-ablation}
The ablation used one scene, direct API calls, a mock driver, and three deterministic repetitions per guard setting in benchmark mode. Each repetition submitted four structural-range violations and two process-window violations, as well as three legal and three boundary requests. The timed writes used for latency summaries were excluded from these counts. With all guards enabled, all six targeted process-window violations returned HTTP 400. With the process-window check removed, all six returned HTTP 200; structural violations continued to be rejected. The archived records contain neither response bodies nor independent per-request driver-call logs, so HTTP 200 alone does not establish driver invocation. The four structural violations were rejected in every repetition and setting; the nine legal requests per setting were accepted and the nine boundary expectations were met. These counts describe the tested fixture, not independent trials or a safety rate. No readback-mismatch stimulus was included, so this experiment does not assess that check.

Separate scripted probes reached the expected approval and authorization branches. In the manual approval fixture, the approved request changed the simulated value from 202 to 204.8, while the rejected request left it at 216. The corresponding automatic calls did not form clean matched pairs because their labels and values did not align with the manual arms. No operator made the approval decisions. The probes show route handling in the tested fixture, not the effect of human approval or a general safety rate.

In a November 5 follow-up, a separate four-scene probe batch returned \texttt{RECIPE\_LIMIT\_EXCEEDED} for all 110 tested requests outside their configured recipe windows but within structural limits. The deterministic inputs and checks derive from the same configuration, so the count assesses the selected cases rather than a population failure rate. In a separate simulated injection-node fault injection, a 230-unit command produced a 251-unit readback against a 0.7-unit tolerance and was reported as \texttt{unverified}; one baseline and one recovery returned \texttt{readback-verified}. This tests one injected mismatch, not physical-device behavior. The later batch is not pooled with the frozen core results; its records and provenance limits are in Supplementary File~S7.

In a separate production-mode check, one legal baseline was accepted and one case each was rejected for interval, step, node-range, recipe-window, and hold-window constraints. A three-case authorization probe rejected an unbound request and a cross-node request and accepted a bound write. These individual branch checks complement the benchmark-mode ablation but do not measure coverage across configurations. Full call records are listed in S7.

\subsection{Process-Target Outcomes}
\label{sec:eval-optimization}
In the no-write control, each simulator ran for 60~s and the endpoint was the mean of its final five samples. The scripted setpoint policy recorded a final process value after scenario-specific steps. The recorded 150.41--172.90~s range is the wall time of each three-scene parallel batch, including setup, rather than a per-scene time to target. Because the horizons and endpoint rules were not matched, the comparison describes these tested routines and does not isolate a control-policy effect. There was no PID or model-predictive-control baseline.

Across the injection, wastewater, and annealing scenes, the scripted policy ended in the target band in 15/15 runs; the no-write control ended in the band in 0/15. The no-write seed-42 injection and wastewater runs began from residual states (32.378~g and 2.894~mg/L, respectively), both already within their target bands; the scripted runs began from blueprint states. The 12 blueprint-matched pairs therefore use seeds 43--46 across the three scenes, with 12/12 scripted endpoints and 0/12 no-write endpoints in band. The 15-run totals include the seed-42 records. We report counts rather than a significance test because the runs share three scenes and the routines have different stopping rules. Fig.~\ref{fig:latest-evaluation} shows the seed-level endpoints and the guard-ablation stimuli; neither panel estimates a population-level effect.

Band membership was recomputed from each recorded process value, target, and tolerance, rather than from the runner's condition-specific \texttt{attained} field. The policy used the \texttt{recipe\_trial} batch route. Across its five seeds it issued 12 writes in 17 rounds for injection, 56 writes in 59 rounds for wastewater, and 41 writes in 50 rounds for annealing. These counts describe the tested missions; they do not compare efficiency with another controller. Seeds are simulator initializations, not independent production lines.

Exact per-seed endpoints and recomputed band membership are listed in Table~3 of Supplementary File~S7.

\subsection{Follow-Up Injection-Twin Pilot}
\label{sec:eval-followup-pilot}
An acceptance script later ran one end-to-end experiment on an isolated platform connected to a PLC-based simulated twin; the manifest records \texttt{realPlant=false}. At 50~bar, the structured record gives a baseline product weight of 31.503~g, below the 32.00--32.30~g band. Its accompanying report instead gives 31.508~g; the discrepancy remains unresolved. A three-level plan tested 50, 55, and 60~bar. The saved ledger labels its contrasts \texttt{no\_resolvable\_effect}, \texttt{underpowered}, and \texttt{identifiable\_effect}; it stores effect, minimum detectable effect (MDE), and verdict fields. The archive lacks the sample series and the rule used to calculate MDE and assign the labels. The final 55-to-60~bar contrast stores an effect of 0.2517~g over a 5-bar step; 0.05035~g/bar is that single-run ratio, not a replicated or independently verified process model.

The subsequent governed write changed the setpoint from 60 to 63.7~bar, and the device readback matched. After 60~s, the mean of the three latest 15-s process samples was 32.224~g, within the band. The reported 15/15 counts assertions within this one execution, not trials. The record lacks a platform commit, simulator/configuration snapshot, and runner-source hash. This pilot demonstrates one scripted simulator path only; its records and provenance limits are in S7.

\subsection{Live-Agent Pilot}
\label{sec:eval-agent}
Four setup attempts produced two recorded live-Agent episodes, and neither issued a governed write. One episode ended with a \texttt{COMPLETED} status while the process value remained outside its target band; the other timed out. The first result shows that orchestration status alone did not verify the process goal. The positive process results above therefore characterize scripted or configured runtime paths, not autonomous-Agent performance. Two additional November 5 episodes were canceled after 371.63 and 372.24~s, respectively; both recorded zero rounds and zero writes. These follow-up episodes do not establish why execution stopped. S7 records the episodes and the earlier setup attempts that produced no result rows.
