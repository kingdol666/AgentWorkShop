AgentWorkShop: A Modular Task-to-Device
Integration Framework for Industrial Agents
Abstract—Industrial agents must turn task goals into device
operations across changing production contexts and heterogeneous interfaces, while preserving evidence of both commands
and process responses. AgentWorkShop connects registered agent
harnesses and direct-operation calls to a shared dispatcher. Scene
mappings link semantic controls to configured drivers; command
receipts remain separate from later process observations. When
approval is required, the handler checks that the line, product, recipe, and active run still match the approved context.
In simulation, one registered harness completed six sequential
tasks across two scenes, each with three prevalidated candidate
settings, synthetic approval, a verified trial receipt, and a runtagged sample. All six single post-trial probes fell below their
target bands. A mock-driver test rejected injected stale contexts
before writes. Four deterministic direct-node missions reported
final primary values within their target bands without modelselected setpoints. These results cover selected configurations;
repeatability, comparative optimization performance, humanreview effectiveness, and physical-plant performance remain
unverified.
Index Terms—Industrial agents, industrial communication,
industrial informatics, production systems, semantic data integration.

I. I NTRODUCTION

I

NDUSTRIAL-AGENT deployments translate task-level
goals into operations over production signals and equipment. A line-speed adjustment, for example, depends on the
active product, recipe, run, applicable limits, and the control
node mapped to the line. If that context changes while a proposal is awaiting approval, a formerly admissible request may
no longer be appropriate. Device access also needs evidence at
two distinct points: what the command interface reported and
what the process was later observed to do. Connecting these
steps across task and device interfaces is therefore a central
industrial integration problem.
Recent work explores end-to-end automation, controlsequence generation, modular factory skills, and robotic-line
control [1]–[4]. Other studies address programmable logic controller (PLC) code generation, context-aware control, resource
discovery, shop-floor coordination, digital-twin fault handling,
and natural-language machine access [5]–[10]. Recent platforms further connect proposals to Asset Administration Shell
(AAS) models and signed approval, validate actions against
process and instrumentation diagrams (P&IDs), or organize
sensor–manufacturing execution system (MES)–enterprise resource planning (ERP) evidence streams [11]–[13]. The cited
work covers agent reasoning, production context, and operation constraints.
An integration question remains: how can task engines and
direct calls share an operation boundary while accounting for
scene-specific devices, production context, and route-specific

evidence? AgentWorkShop connects registered harnesses to
task context and direct representational state transfer (REST)
calls to the same named-operation dispatcher. Scene blueprints
map semantic signals to configured drivers and define targets
and guards. The experiments evaluate selected routes; they do
not establish that all entry paths are equivalent.
Fig. 1 summarizes the control path. Task goals and production context inform an operation proposal. Shared checks and
route guards precede writes through the device write-control
(DCW) subsystem. When approval is required, the handler
rechecks the approved context before dispatch. Command
receipts and subsequent data-acquisition (DAQ) observations
remain distinct: a readback can verify a setpoint, while a
later observation describes the process state without, by itself,
establishing causation.
AgentWorkShop implements this path through a collaboration runtime and a shared operation dispatcher. Registered
harness adapters connect agent engines to task context; direct
calls invoke the dispatcher without creating a task. Scene
blueprints and channel profiles define deployment signals,
objectives, guards, tools, and agent bindings. Fig. 2 shows
these relationships, and Fig. 3 follows one registered task
through execution.

A. Industrial Agents and Plant Integration
Industrial-agent systems address control at several levels.
A large language model (LLM) framework for end-to-end
automation [1] and control generation for industrial cyberphysical systems [2] complement agent-based supervision
[14], PLC code generation, and human–LLM control [5], [6].
Manufacturing studies also explore resource capabilities [7],
shop-floor coordination [8], and digital-twin fault handling
[9]. Natural-language machine access [10] and real-time LLM
control of a robot-operated line [4] extend this work to
operator interfaces and robotic-line control.
Xia et al. connect cognitive, digital-twin, and physicalautomation layers and organize twin information as state
snapshots, event messages, and plan sequences [15]. Other
nearby designs expose factory-module operations through the
Model Context Protocol (MCP) with state-based tool filtering,
constrain manufacturing plans, or compose semantic recipes
from OPC Unified Architecture (OPC UA) skills [3], [16],
[17]. Several recent systems also combine agent execution
with approval, industrial data, or audit records. Graul et al.
ground proposals in the Asset Administration Shell (AAS)
and route approved actions through OPC UA Methods, with
signed approvals and audit logging [11]. Schall separates
advisory language-model agents from process and instrumentation diagram (P&ID)-grounded verification and execution,
and evaluates structural checks across five simulated process
scenarios [12]; its context includes supervisory control and
data acquisition (SCADA) and standard operating procedure
(SOP) information. Lin and Chen build a governed sensor–
MES–ERP digital thread for closed-loop monitoring and control on real manufacturing records [13]. These designs address
different parts of the integration problem: asset-grounded
approval, action validation, and the organization of industrial
evidence. The present paper describes a complementary taskto-device path in which registered tasks and direct calls reach
named operation handlers and route-specific records remain
with their owning services. The cited studies’ reported descriptions do not permit a matched comparison of that entry-path
arrangement; Table I therefore presents their mechanisms and
evaluation contexts rather than inferring missing capabilities.
The operation checks complement safety-aware decision
support [18] and operate alongside the plant’s configured
process protection.

B. Production Context, Agent Interfaces, and Automation
Industrial integration also depends on abstractions that
are not specific to agent architectures. The Model Context
Protocol (MCP) specifies interoperable tool discovery and
call mechanisms [19]; the operation-level scope, policy, grant,
and binding checks discussed here are AgentWorkShop’s own
dispatcher rules, distinct from MCP transport authorization. In
parallel, ISA-88 and ISA-95 describe recipes and production
operations [20], [21]. Run-to-run methods connect process
observations to successive production runs [22]. Human–
automation research also formalizes the allocation of information acquisition, analysis, decisions, and actions between
people and automation [23]. At the agent level, AgentSpec and
CaMeL address tool behavior and capability-based information
flow [24], [25]. These standards and agent-level mechanisms
describe interfaces for production context, tool interaction, and
information flow. AgentWorkShop focuses on how registered
tasks and direct calls reach named handlers while scene mappings and owning services retain their context and operation
records.
III. S YSTEM D ESIGN
AgentWorkShop separates task execution from operation
dispatch while allowing both to use current production context.
Shared and route-specific checks govern device routing, and
service-owned records distinguish command receipts from
measured process responses.
A. Design Rationale and Requirements
Five requirements—scene variability, harness variability,
operation authority, outcome observability, and extensibility—
shape the design. Scene variability is represented by blueprints
and semantic driver mappings; harness variability by registered
adapters; operation authority by shared dispatch checks and
route-specific guards and admission; outcome observability by
service-owned task, receipt, and observation records; and extensibility by registered interfaces for agent engines and device
drivers. Tool visibility is separate from write authorization, and
actuator writes converge on the shared DCW admission point.
A scene blueprint bundles the process preset, signal inventory, DAQ/DCW driver mappings, and target and guard rules;
judged operation records and later observations remain distinct
evidence.
During setup, the integrator binds a validated blueprint to
the active line–product–recipe–run tuple, maps semantic nodes
to drivers, and declares target bands and guards. At runtime,
the dispatcher checks current authority before the handler
issues a command; the handler returns a receipt, and DAQ
records subsequent observations.

The architecture in Section III assembles task context,
dispatches operations, and connects device access to separate
records of commands and observations. The following subsections explain the handoffs between these functions.

A. Task, Harness, and Context
Task and chat entry points create or join a workspace
channel. The task runtime manages membership, task state,
and shared execution context; a harness registry adapts each
supported agent engine to a common execution interface. At
each agent turn, the prompt builder assembles the task, active
scene description, production context, channel profile, agent
binding, and retrieved memory. This keeps engine-specific
interaction behind the harness interface while preserving the
current line and operation context for the agent.
Direct REST and selected stdio-MCP operation calls reach
the same dispatcher without a task or harness turn. REST
authentication and identity resolution follow Section III-C;
each handler reads live route state at invocation. Handlers
receive the resolved actor, channel, and operation arguments
through the same interface for either entry route; records are
keyed by the identifiers supplied in each request. A registered
task additionally receives prompt context and a scoped tool
catalog. Catalog visibility alone does not grant write authority:
the dispatcher checks authority at invocation.
B. Shared Dispatch and Device Admission
The dispatcher is the shared operation boundary. As specified by (1), it checks invocation scope and channel policy
for every call; grant is skipped only for a grant-exempt
industrial tool, and binding applies when the operation declares resource references. Applicable checks precede handler
selection. Handlers revalidate route-specific state at execution
time; the dispatcher applies grant checks when required. Scene
blueprints define device and signal maps, objectives, and process guards. Capability profiles and tool policies narrow available operations, while bindings constrain accessible nodes,
controls, and recipes. Optional DAQ, MES, analysis, retrieval,
optimization, and digital-twin services are invoked through
registered handlers. The application supplies its optimization
strategy while the framework coordinates operation execution.
Actuator writes converge on the shared DCW admission
point. For an online node write, the admissible value interval

Receipts and observations answer different questions. A
command result is graded as readback-verified, transportacknowledged, or unverified; a readback mismatch can trigger

applied it, and an unverified result does not establish a matching readback. DAQ stores subsequent timestamped process

change. Section V evaluates selected parts of this evidence

V. E XPERIMENTAL E VALUATION
The evaluation examines selected parts of the task-to-device
integration path using local simulators and a mock driver. A
registered-harness test examines task execution and its retained
operation records; Fig. 6 shows the associated process probes.
Other checks examine protocol and node access, directoperation records, and approval-context rejection. Separately,
four deterministic direct-node missions illustrate how requests
and observations are recorded across different process scenes.
They cover injection molding, biaxially oriented polyethylene
terephthalate (BOPET) film production, continuous annealing, and anaerobic/anoxic/oxic wastewater treatment. Table III
summarizes their primary outcomes; their trajectories appear
in Fig. S2 of the supplementary evidence bundle. The missions
and harness tasks address different evaluation questions and

use different setups; neither is a control or repetition of the
other.
A. Test Design and Evidence Rules
All process experiments use local simulators, not physical
equipment. The four missions use deterministic scenariospecific routines, a fixed random seed, and the direct-node
interface; no language model selects their setpoints. In the
available benchmark source, an automatic keep judgment
follows a write and precedes the next observation, except
in BOPET, where it follows the response. Annealing and
wastewater logs also record later reversion decisions. These
are software events, not human pre-approval. The full executed
runtime snapshot was not retained, so the records cannot be
replayed as a complete trace.
Each mission contributes one trajectory, with its initial
observation as a within-trajectory reference rather than an
independent control. A requested setpoint is an action, not a
device readback; subsequent process values are observations.
The primary outcome is the mission-reported final value
relative to its target band. Intermediate observations are not
independent repetitions.
B. Protocol and Node Integration
The protocol test configured simulator endpoints using
Modbus TCP, Modbus RTU, OPC UA, MQTT, and HTTP;
its contemporaneous report records successful connectivity
for each. In a Modbus TCP check, seven samples were
collected and the simulated process reached within 3 ◦ C of
a requested 182 ◦ C setpoint after 24 s. In a separate fault
case, a 185 ◦ C write was read back while the process value
remained frozen at 150 ◦ C; monitoring raised an alarm within
2 s. A reported link-fault exercise detected loss of connection
and recovered after simulator restart. The complete per-sample
protocol trace was not retained, so these results are limited to
the contemporaneous summary.
The BOPET line had nine devices and 49 signals: 30
writable setpoints and 19 measurements. Its four requests

separate environments and did not trace both calls to the same

F. Direct-Node Missions: Annealing and Wastewater
The direct-node annealing mission measures hardness,
whereas the registered-harness tasks record strip temperature
(Fig. 6). The annealing mission combined a 95 ± 6 HV
hardness target with a line-speed increase. From 134.9 HV,
a zone-2 temperature request from 710 to 850 ◦ C preceded a
structured observation of 99.18 HV; a speed request from 140
to 152 m/min preceded 99.74 HV. A 164 m/min candidate was
reverted after event text reported 101.0 HV, at the upper target
boundary with no remaining hardness margin. The summary
separately reported final hardness of 99.5 HV and retained
speed of 152 m/min, 8.57% above the initial setting, not a
measured throughput gain. A zone-3 read failed before the
zone-2 action. Final tensile-strength and surface-defect measurements were not archived, so the record cannot establish
that all quality constraints were met.
The wastewater mission targeted dissolved oxygen (DO)
at 3.4 ± 0.6 mg/L. Five blower-frequency increases from 26
to 34.1 Hz accompanied a rise from 0.194 to 3.567 mg/L
in the structured aeration sequence. Subsequent alkali and
coagulant dosing addressed pH and phosphorus; observed total
phosphorus fell from 0.662 to 0.5507, 0.4607, and 0.413 mg/L.
A later blower reduction was reverted after insufficient margin.
The summary separately reported final DO of 3.54 mg/L and a
simulator-defined cost index changing from 182.6 to 180.2, not
a measured operating cost. The complete final effluent vector
was not archived, so these values do not verify all discharge
constraints.
G. Evidence Synthesis
The six registered-harness tasks retained operation records,
and each single post-trial probe fell below its target band. Separately, the four direct-node missions reported final primary
values within their respective target bands. Neither evaluation
establishes repeatability, causal effects of individual actions,

comparative performance, human-approval effectiveness, or
transfer to a physical plant.
VI. D ISCUSSION
A. Interpretation
Protocol connectivity and the onboarding replay test different parts of device integration: communication with configured
simulator endpoints and access to declared acquisition and
control nodes. They do not show that arbitrary equipment
can be integrated without adaptation. The entry-path checks
document which records were retained for each tested call.
Because the calls used separate environments and no handlerlevel trace was retained, they cannot establish route equivalence or confirm that both reached the same handler. In the
approval-context test, stale product and run identities reached
mock writes when tuple comparison was removed and were
rejected when it was enabled. This isolates the comparison’s
contribution within that setup.
The six registered-harness tasks and four direct-node missions answer different questions. The harness tasks link approvals and receipts to single post-trial probes; the missions
record one process trajectory per scenario. They use separate
setups, including different film target bands and different
annealing measures, so mission endpoints do not benchmark
the harness probes. Across the missions, requested actions
precede measured responses, including a reverted annealing
candidate. In wastewater treatment, the structured aeration
sequence and final mission summary also refer to different
observations. These records describe trajectories, not isolated
effects of individual commands.
The missions also illustrate the role of scene-specific configuration. Part weight, film thickness, hardness, and dissolved oxygen have different units, target bands, and available actuators. The operation–response structure accommodates these differences, but the trajectories do not identify

IEEE TRANSACTIONS ON INDUSTRIAL INFORMATICS, SUBMITTED MANUSCRIPT

which architectural component caused an outcome. Related
approaches likewise connect industrial operations to semantic
skills, equipment context, or process validation [11], [12], [17].
The present study complements those designs by describing a
shared operation path and showing recorded responses in four
simulated scenes; the studies use different tasks and do not
provide a matched performance comparison.
B. Scope and Limitations
The optimization evidence comprises one deterministic simulated trajectory per scene, without independent replicates or
a matched alternative controller. It cannot establish statistical
repeatability, superiority to another platform, or the effect of
individual controls. The missions use direct-node operations
and do not test the full range of entry routes or languagemodel decisions described by the architecture. Final tensilestrength and surface-defect readings for annealing and the
complete final wastewater effluent vector are missing, limiting
conclusions about secondary constraints. The process model
and simulator configuration also limit transfer to physical
production.
The mission records show automated judgments, not human pre-approval. The approval-context test uses simulated
decisions and mock drivers; it tests a software condition, not
operator performance or the effectiveness of human review
[26], [27]. Software operation restrictions are not a complete
security or safety assessment [28]–[30]; independent plant
protection remains necessary [31]. Future work should repeat
missions across initial conditions, preserve all terminal quality
measurements, compare matched controllers and entry paths,
and evaluate the system with suitable physical equipment and
operator oversight.
This modular separation is a property of the implemented
software structure. The current evidence does not measure
whether it reduces engineering effort, operating cost, or reliability; those outcomes require matched deployments.
VII. C ONCLUSION
AgentWorkShop links industrial task context to scenespecific device operations through shared dispatch, configured drivers, and separate command and observation records.
Simulator and mock-driver checks exercised selected integration and approval paths. Four direct-node missions reported
final primary values within their target bands, while all six
registered-harness probes remained below target. These results
do not establish repeatability, comparative benefit, humanreview effectiveness, or physical-plant performance; those
questions require repeated and matched evaluations, complete
terminal measurements, and testing with physical equipment.
