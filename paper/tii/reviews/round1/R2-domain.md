# Review R2 — Domain Reviewer (Industrial Automation)

**Manuscript:** AgentWorkShop: A Node-Native Integration Framework for LLM Multi-Agent Closed-Loop Control of Heterogeneous Industrial Production Lines
**Venue:** IEEE Transactions on Industrial Informatics
**Reviewer profile:** Senior industrial control engineer (20 years, batch process industry), following LLM-agent research.
**Scope of this review:** PLC/SCADA supervisory practice, ISA-95/ISA-88 batch & recipe models, ISA-18.2 alarm management, IEC 61511 / IEC 62443 positioning, OPC UA / Modbus / MQTT / HTTP realism, alarm rationalization, and correct positioning of "LLM agents in industrial control" against the domain state of the art.

---

## 1. Mental-Model Reconstruction and Comprehension Breakdown Points

### 1.1 Reconstruction (what I believe the system is, from the paper alone)

To deploy this system, an engineer starts one Node.js platform process that hosts both an agent runtime and an industrial runtime. Per device, the engineer exports an integration descriptor from which the driver configuration is derived, tests connectivity against the live protocol stack, creates one or more nodes (choosing acquisition and control roles), provisions the line/product/recipe objects, and binds the nodes to an agent team. Each node carries a *semantic card* — engineering unit, hard range S(n), batch-scoped recipe window W_r(p), warn band, freshness, and a 2 %-of-span step limit — which is the agents' only view of the plant; register addresses are hidden. Binding mode sets the authorization posture: *manual* (every agent write queues for human approval), *auto* (interlock plus backstop only), or *unbound* (no write path exists). A channel is the team room; its lead supervises workers on a 1 s tick with a deterministic rule-engine fallback. The loop: the bound agent observes via `daq_query`, proposes a setpoint via `dcw_control` (opening an optimization record that freezes a pre-write baseline), the governed write path checks availability, serialization guardrails (one open record per agent; 300 s same-direction cooldown), and the soft interlock against C(n,r)=S(n)∩W_r(p); it then writes, reads back within τ(n), and journals a signed anchor. `dcw_judge` judges without actuating; the backstop rolls back to the recorded baseline after B=3 out-of-window samples, capped at K=2 automatic rollbacks per node lifetime, then escalates to a human. The whole system sits at the supervisory tier; PLCs retain basic control and safety functions.

**Verdict:** I was able to reconstruct the deployment end-to-end and map nearly every object onto plant practice (node ↔ tag/device faceplate; semantic card ↔ asset description/AAS; binding ↔ loop mode + write-permission model; line/product/recipe/run ↔ ISA-95 hierarchy with an ISA-88-style formula binding; governed write path ↔ a single, journaled setpoint-write service). This is well above the clarity standard for this class of paper.

### 1.2 Comprehension breakdown points (what a controls engineer cannot map onto their plant)

1. **"8 % warn band" has no defined reference.** 8 % of span? of target? one-sided or two-sided? From which state does `warn` transition to `alarm` — at the recipe-window edge? (Sec. IV-D, p. 5). I cannot engineer a faceplate or an alarm sheet from this.
2. **Acquisition only while a batch is active** (Sec. IV-D; restated Sec. V-D as the reason the Modbus RTU gel counter is a "satellite"). Between batches, the platform has no historian coverage, no alarm coverage, and the alarm state machine's between-batch behavior is undefined (does a sampled-then-batch-stopped node read `offline`?). In a running plant, monitoring is continuous; this design reads as benchmark-driven and needs explicit justification.
3. **The "integration export" is a self-defined artifact.** Real commissioning maps device descriptions — GSD (PROFINET), EDS (EtherNet/IP/CANopen), IODD (IO-Link), OPC UA companion specifications — onto the platform. The five-step flow is measured only against the authors' own simulator export, so I cannot estimate effort on my floor (Major Issue M5-related; see Minor Issue 7).
4. **The "recipe" carries no procedure.** In ISA-88 a master recipe is procedural (procedure, unit procedure, operation, phase) plus formula. Here a recipe is a versioned parameter set with windows only; nothing dispatches phases or sequential logic. This is legitimate — it is a *formula-level* governance model — but the ISA-88 citation oversells it (Major Issue M4).
5. **The "optimization record"** (open record, frozen baseline, T_bl = 600 s baseline statistics, judge classes keep/rollback/uncertain) is novel bookkeeping, but it is learnable and analogous to a supervisory tuning/optimization case file; no objection beyond naming.
6. **Batch vocabulary on continuous lines.** Cast-film extrusion and a coating-oven line are continuous processes; "active batch" would normally be "active campaign/run/order" on my floor. The tree is fine; the vocabulary will jar with continuous-plant readers.

## 2. Domain Strengths

1. **Supervisory-tier positioning is correct and consistently maintained.** P2 (Sec. III-A, p. 2: "supervisory, soft-real-time tier; hard real-time control and safety functions remain in PLCs, mirroring the IEC 61511 separation of basic control from safety instrumented functions") is exactly how a controls engineer would bound such a system, and the paper does not quietly abandon it later — Sec. VI-A ("engineering properties, not certified safety functions... does not replace certified instrumentation") and the fail-safe deferral of rollback when the gateway is paused both honor it. The distinction is also used operationally: "PLC-side protection persists between batches per P2" (Sec. IV-D).
2. **The bounded-write framing is the right abstraction.** "Judgment is not execution," single-entry writes, and constraining the *accepted-action language* rather than the LLM is the correct lesson from shielding/CBF literature transplanted to SCADA practice. The judge/execute separation (`dcw_judge` cannot actuate; rollback is a separately invoked, fully re-governed write) matches how one would actually implement operator-proposed corrections under management-of-change discipline.
3. **Layer separation is honest where it matters.** The process-freeze drill (Sec. V-D): "the governed write still passes (readback verifies the register, not the process) while the independent recipe-window monitor catches the failure within 2 s" — this is a genuinely domain-aware statement. Many papers would have claimed the readback as verification of the process; this paper explicitly says it is not.
4. **Protocol realism is credible.** Modbus TCP/RTU (RTU-over-TCP for the gel counter satellite is authentic film-line flavor), OPC UA exact-echo readback, MQTT treated as publish-only, HTTP as echo-only, with the no-readback property *recorded as degraded, never silently confirmed* (I2). Write latencies (19–112 ms p50; Modbus TCP p95 dominated by first-connection setup) and readback deviations (≤0.04 °C) are physically plausible. Process values are realistic for cast film (melt 195–225 °C, pressure ≤22 MPa, 50 µm gauge, gel counter on Modbus RTU) — this reads like someone who has seen an extrusion line.
5. **The alarm chain mechanics are plausible.** Hysteresis (2 %) + frame debounce (3) against chattering, edge-triggered recipe-window violation alarms (latching on the event, not the level — correct), watermark-based out-of-order defense, human-only acknowledgment with 15 min escalation. The elements chosen are the right ones, correctly implemented in principle (Sec. IV-D).
6. **The HITL binding model maps onto plant authorization practice.** manual/auto/unbound per node, team-scoped authorization, approval decoupled from execution with full stage re-run after the decision (closing the stale-approval hole), lapse of unapproved requests, dedup per node+record, and human decisions attributed in the same journal anchor as machine ones. This is a sound per-tag write-authorization boundary in the spirit of DCS loop-mode/permission models, and the Parasuraman/Sheridan/Wickens anchoring is apt.
7. **IEC 62443 positioning is stated within honest limits.** "Trading zoning isolation for in-process enforceability within one zone" (Sec. IV-G) openly concedes the single-zone problem rather than claiming zone isolation it does not have. Likewise the related-work boundary claim — "in none does an agent team's decision become a governed write on a protocol-heterogeneous plant" — is, to my knowledge, accurate against Hofmann et al. (single machine, OPC UA, NL control) and Vyas et al. (simulated FTC): the contribution is correctly positioned as an integration/governance substrate, not as better control intelligence, and the measured LLM shortfall (median 0.76 of optimum) is reported as a negative rather than spun.
8. **The K=2 / B=3 / T_cd=300 s bounded-autonomy envelope** is the kind of engineering cap (per-node, monotone, escalation-at-K) that an operations-review board could actually sign off; the fail-safe direction (paused gateway defers rollback actuation) is correctly chosen.

## 3. Major Issues

**M1. Title and headline framing overclaim "Closed-Loop Control" by the LLM agents; the evidence supports supervisory closed-loop *optimization* under governance.**
*What/where:* Title (p. 1), Abstract ("LLM Multi-Agent Closed-Loop Control"), Contributions 4; contrast Secs. V-F/V-H.
*Why:* On my floor, "closed-loop control" means the regulatory layer; here the PLC/temperature controller keeps that role (correctly, per P2), and what closes over the governed path is a slow supervisory setpoint/optimization loop (seconds-to-minutes cadence). Moreover, the paper's own strongest measurement shows the LLM teams *failing* at this loop (median 0.76 of optimum; thickness window missed) while a fixed deterministic controller achieves 0.97 — the demonstrated contribution is the governed loop, not LLM control. The paper is candid in body text ("closed-loop optimization benchmark," "propose/dispose"), but the title and abstract lead with the overclaim a TII controls readership will punish.
*Fix:* Retitle to reflect supervised/optimization scope (e.g., "…Governed Closed-Loop Optimization/Supervisory Control of…"), and qualify the abstract's first sentence about what closes the loop (setpoint-level supervisory optimization, not regulatory control). One sentence in the introduction distinguishing supervisory optimization loops from regulatory loops would inoculate the whole paper.

**M2. Writes with no readback (MQTT publish-only, HTTP echo-only) execute under *auto* binding with no compensating authorization policy.**
*What/where:* Algorithm 1 lines 26–29 (Sec. IV-C, pp. 4–5): `degraded → ok ← false`, yet the write has already executed and is journaled; Sec. V-D / Table II ("a driver property the write path records rather than conceals").
*Why:* Executing an unverified actuator command and merely flagging it is a policy decision, not a neutral driver property. In alarm/HAZOP terms, an unverified write removes the feedback half of the command path; today the only compensations are the backstop (which needs B=3 out-of-window *process* samples and spends the node's K=2 budget) and the alarm chain. An agent under an auto binding on a no-readback node can actuate blind, repeatedly (reverse-direction moves are exempt from T_cd), with nothing verifying the actuator followed. I would not sign off that configuration on a running line, and the paper never discusses it as a risk.
*Fix (any one suffices, first preferred):* (a) make binding mode and readback capability coupled — a no-readback node defaults to (or is restricted to) *manual* binding, with auto requiring an explicit engineer override recorded in the journal; (b) refuse agent-source writes on degraded channels in auto mode; (c) add a per-node degraded-write counter to the I3 envelope. State the chosen policy explicitly in Sec. IV-C and exercise it in Sec. V-D.

**M3. The claim "oscillatory overwrites are impossible" (Sec. IV-C, stage 2, p. 4) is technically wrong.**
*What/where:* "within a cooldown T_cd = 300 s a same-direction rewrite is rejected while a reverse-direction correction stays allowed, so oscillatory overwrites are impossible."
*Why:* Alternating-direction writes (+v, −v, +v, …) are allowed at ≥300 s spacing by the stated rule; that *is* oscillation, and a misbehaving agent can walk the actuator back and forth indefinitely within the window, spending nothing from K=2 while the value stays in-window. What the rule actually prevents is same-direction ratcheting/overwrite chatter.
*Fix:* Weaken the sentence to what the mechanism proves ("same-direction ratcheting is prevented; alternating corrections remain allowed and are bounded only by the window, step rule, and backstop"), or add a net-displacement bound per record/window if the stronger property is wanted. As written, an invariant-minded reader will distrust the other invariant claims.

**M4. The ISA-95/ISA-88 grounding is thinner than claimed, and the batch-scoped acquisition policy is practice-questionable.**
*What/where:* Sec. II-A p. 2 and Sec. IV-D p. 5 ("line/product/recipe/run tree … combines ISA-95 with the ISA-88 recipe/batch model"); "acquisition samples only nodes on lines with an active batch"; recipe = versioned parameter set + windows only (Sec. IV-F).
*Why:* (a) The tree maps to ISA-95 equipment/product *hierarchy* notions, but ISA-95's substance (Levels 3–4 integration: production scheduling, operations activity models, product definition) is untouched; as written the citation is decorative. (b) ISA-88 recipes are procedural models + formula; the paper governs only the formula half (parameter windows bound to a run/batch). That is a legitimate design — a batch-scoped interlock envelope is plausible and the batch-stopped branch of Eq. (1) is correctly exercised in Sec. V-C — but claiming the ISA-88 "recipe/batch model" invites a batch-control expert to ask where the phases are. Scope it. (c) Suspending platform acquisition between batches leaves the supervisory tier blind between runs (no historian, no alarming, alarm-state semantics undefined), while PLC-side protection continues; monitoring gaps between batches are exactly where unplanned work happens. If this is a benchmark resource constraint, say so; if it is the design, defend it.
*Fix:* Scope the ISA-88 claim to "ISA-88 formula/parameter limits bound to a batch/run identity (procedural/phase control out of scope)"; either map the tree to ISA-95 activity models or soften the ISA-95 citation; justify or drop the acquisition-gating rule (or acquire at reduced cadence for monitoring when no batch is active).

**M5. The hardest attack path — a compromised harness engine writing the protocol stacks directly, bypassing the governed path — is acknowledged but carried by assertion, in tension with the one-process design principle.**
*What/where:* Sec. III-B ("Co-residency … does not contain the harness engines, which remain privileged local processes"), Sec. IV-G ("allow-list probe, least-privilege service account, and IEC 62443 zoning to keep the governed surface the only reachable write path"), Sec. VI-A.
*Why:* The paper's central thesis is that governance is "enforceable rather than merely declared" (Abstract, Introduction). For the platform-internal path that is demonstrated; for the engine path it is not — no drill shows a rogue process or a prompt-injected engine being denied a direct write. The mitigations named (allow-list probe of executables, service account, zoning) are plausible but unmeasured, and P1's co-residency is exactly what IEC 62443 zoning guidance would warn against (agents that ingest untrusted text share a zone with the write drivers). The honesty is appreciated; the asymmetry — every other invariant gets negative tests, this one gets prose — remains.
*Fix:* Either (a) add a measured drill (rogue write attempt outside the governed path denied by service-account/zoning policy in the L1 rig) to Sec. V, or (b) temper the enforceability claim to "enforceable for the sanctioned tool path; engine containment is a deployment property, not a measured guarantee." Cite IEC 62443-3-3 (security levels) when discussing what the single zone forgoes (see Missing References).

## 4. Minor Issues

1. **Warn-band definition (Sec. IV-D).** Specify the reference (span? target? window edge?), sidedness, and the warn→alarm relation. Also state the alarm chain's behavior when acquisition is suspended between batches (ties to M4c).
2. **"Hard interlock" naming (Sec. IV-A).** Both "hard" (driver-layer range validation) and "soft" (window) enforcement live in platform software, not in the PLC. "Hard" suggests hard-wired/PLC-side protection to many readers. Recommend "driver-enforced hard limit" and an explicit sentence that neither is a safety function (Sec. VI-A already says this — connect it).
3. **ISA-88 citation (refs. [18]).** ANSI/ISA-88.01:1995 is the outdated edition; the current part is ISA-88.01:2010 (Batch Control Part 1: Models and Terminology), with IEC 61512-1 as the international equivalent. Update.
4. **ISA-18.2 scope statement (Sec. II-A).** "The alarm chain follows alarm-management practice (ISA-18.2)" should be scoped: the paper implements detection mechanics (deadband/hysteresis/debounce), edge-triggered window alarms, acknowledgment, and escalation — i.e., a slice of the ISA-18.2/IEC 62682 lifecycle. No rationalization, prioritization, shelving/suppression, or flood management is claimed or present; say so to preempt the objection.
5. **Escalation timeout (Sec. IV-D).** "Default 15 min" — tie escalation targets to alarm priority/response-time philosophy (ISA-18.2 § operating procedures/monitoring) rather than a single flat default, or state that priorities are future work.
6. **Backstop worst-case timing (Sec. IV-E).** With acq = 5 s, T_win = 120 s, T_re = 30 s, B = 3, worst case to a completed automatic rollback is on the order of 3–5 minutes, plus rollback latency. State the bound; supervisory engineers size windows and operator workload from such numbers.
7. **Integration-export ecosystem (Sec. IV-A).** One paragraph mapping the proprietary "integration descriptor" to real device-description mechanisms (GSD, EDS, IODD, OPC UA companion specs, CIP profiles) — even as future work — would substantially raise deployment credibility (see also Sec. 1.2 point 3).
8. **"Digital twin" dual use (Index Terms; Sec. IV-D; Sec. V-F).** The device-twin registry/3D scene (Ditto-style shadow) and the ODE plant simulator ("cast-film twin") are two different senses. The paper keeps them distinct locally ("the twin observes, never actuates" is exemplary), but the index term and headline "on a cast-film twin" blur a simulator with a twin of a real asset. Consider "plant simulator (twin-style model)" or cite ISO 23247 to anchor the terminology.
9. **"Gateway" terminology (Sec. IV-A).** In ICS vocabulary "gateway" connotes a protocol/network gateway (Purdue-level boundary device); the platform's acquisition "gateway sweep" is an internal scheduler. A renaming or one-line disambiguation avoids misreading Fig. 1.
10. **τ(n) configurability (Sec. IV-C, Eq. 2).** The max(0.5 LSB, 0.5 % span) default is sensible; state whether τ is engineer-per-node overridable (coarse-resolution actuators and precision lab nodes both exist), and note that τ bounds *register echo*, not process response (Sec. V-D already makes this point — good).
11. **"Both log surfaces … are queryable views over the journal substrate" (Sec. IV-D)** is written as if the journal lives in Sec. IV-C's write executor; it does — fine — but the cross-reference "Sec. IV-C" after the storage stack sentence reads as if SQLite/TimescaleDB back the journal; clarify which store holds the signed anchors (immutability claims matter for audit).
12. **Abstract numbers.** "29 seeded out-of-window/range writes intercepted (Wilson [88 %, 100 %])" pools 9 (Sec. V-B) + 20 (Sec. V-D) but omits the 6 from the live-instance tier (Sec. V-C); a parenthetical on composition would prevent readers from reconstructing the denominator incorrectly.

## 5. Missing References

Standards and domain literature an expert would expect:

1. **IEC 62682 / ISA-18.2 lifecycle detail** — the ISA-18.2 entry mentions IEC 62682 only in a bib note; cite it properly when scoping the alarm-chain claim (Minor Issue 4).
2. **EEMUA 191** (*Alarm Systems: A Guide to Design, Management and Procurement*) — the standard companion to ISA-18.2 in alarm work; expected wherever hysteresis/debounce/rationalization is discussed.
3. **IEC 62443-3-3** (System security requirements and security levels) — the paper's zoning and "only reachable write path" claims need the SL vocabulary that Part 3-3 provides; the umbrella "IEC 62443:2018" citation is too thin for the load it carries in Sec. IV-G/M5.
4. **NIST SP 800-82** (Guide to Operational Technology/ICS Security) — expected positioning for any framework writing to PLCs across zones.
5. **ISO 23247** (Digital twin framework for manufacturing) — the index term "digital twin" currently hangs on IEC 63278 (AAS) and Eclipse Ditto only; ISO 23247 is the manufacturing-twin reference.
6. **ISA-95.00.03 / IEC 62264-3** (Activity models of manufacturing operations management) — needed if the line/product/recipe/run tree is to support its ISA-95 claim beyond hierarchy (ties to M4).
7. **ISA-88.01:2010 / IEC 61512-1** current editions (see Minor Issue 3).
8. **Uncited entries already in refs.bib:** `liu2026embodied` (LLM-enhanced embodied multi-agent manufacturing system) and `ren2025agentic` (agentic AI in manufacturing) are directly relevant to the related-work boundary claim and are present in the bibliography but never cited in the text; also `xu2024company` (TheAgentCompany) belongs beside τ-bench [13]. Use them.
9. **Deployed industrial LLM copilots** (e.g., Siemens Industrial Copilot and peers) — the advisory-boundary family the paper claims to go beyond is currently represented only by academic prototypes; one citation to deployed industrial assistants would strengthen the gap statement.

## 6. Recommendation

**Minor Revision.**

**Rationale.** From the industrial-automation standpoint this is an unusually well-grounded paper: the supervisory-tier contract (P2/IEC 61511) is stated and kept; the governed write path, judge/execute separation, bounded-rollback envelope, and manual/auto/unbound binding model map cleanly onto plant authorization and management-of-change practice; protocol handling (including the honest publish-only/echo-only degraded treatment and the "readback verifies the register, not the process" observation) is credible; the alarm chain's mechanics are sound as far as they go; and the numbers (temperatures, pressures, latencies, RTU gel counter) are authentic to film extrusion. The contribution is correctly positioned against the LLM-for-industry state of the art, and the negative LLM result is reported honestly.

The required revisions are tractable and none requires new experiments beyond (at most) one added drill: (M1) fix the title/abstract overclaim of LLM "closed-loop control" to the supervisory-optimization scope the evidence supports; (M2) define and enforce an authorization policy for no-readback nodes under auto binding; (M3) retract the "oscillatory overwrites are impossible" claim or add the mechanism that would make it true; (M4) scope the ISA-88/ISA-95 claims to the formula/hierarchy subset actually implemented and justify the between-batch acquisition blackout; (M5) either measure or soften the engine-containment/62443 claim, with the 62443-3-3 vocabulary. The minor issues are definitional (warn band, ISA-88 edition, ISA-18.2 scoping, backstop timing bound, terminology) and improve engineering usability without touching the architecture. With these addressed, the paper would be a solid and welcome TII contribution on governed agent-plant integration.
